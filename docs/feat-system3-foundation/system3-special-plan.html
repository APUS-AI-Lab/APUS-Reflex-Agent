01

产品定义：一个本地优先的智能体系统

System3 的主体是 DSH 驱动的任务闭环。本地 APUS 9B 同时提供通用生成与 Jev 式决策能力，专业智能体按需协作，最终结果回到本地验收。

普通工作，本地完成。
私密数据，本地处理。
专业工作，按需委派。
每一步，都有证据与预算。

System3 = System1 快速判断 + System2 深度工作 + 可验证的协作闭环。System1／System2描述工作方式，不按本地／云端划线：本地9B的生成模式也可以承担轻量推理；Claude Code、Codex是包含模型与工具的专业智能体产品，并非单一模型名。

组件主要责任明确边界
APUS 9B · Generate普通问答、私有资料整理、受限工具操作、局部Draft与摘要只承接经过专项验收的任务；“9B”不保证通用能力达标
APUS / Jev · Decide分类、候选排序、路由、证据选择、进展判断与升级建议不生成权限、不替代确定性验收；允许unknown
DSH · System3控制层目标、任务状态、预算、数据边界、工具执行、专家调度、结果整合复用上游loop和Session，不让模型绕过策略
Claude Code / Codex · 专家层复杂代码修改、跨文件工程、难题分析和独立复核只收到允许外发的工作包；返回结果必须验证
首发是本地优先的任务平台；日志压缩只是其中一个优化模块。同一9B权重实现双模式是目标，不能成为交付整个产品的前置阻塞。
02

整体架构：本地拥有任务，专家承接工作包

用户只提交一次目标。DSH持有任务真相和原始数据，Jev给出决策建议；确定性策略决定哪些工作能执行、由谁执行、哪些信息能离开本机。

数据平面

原始文件、完整日志、私有记忆和映射表保留在本地。模型可见的摘要与监督消息通过Session事件记录，可恢复到源证据。

控制平面

DSH控制任务状态和权限。Jev只对合法候选做建议；规则先执行，模型不确定则按既定策略回退，不通过重试绕过用户选择。

03

核心目标优先级：先打通分工，再优化智能

首个产品切片必须同时证明本地能做事、专业工作能交付、数据不会越界。训练优化在这条闭环产生真实数据后推进。下表是设计排序，不是已测收益排名。

顺序目标与交付优先原因完成证明
1 · P0本地9B能力接入＋数据策略＋本地工具构成“我的本地助手”，并决定云端可用边界本地普通与隐私任务真实完成；禁云任务不产生外发
2 · P0DSH→一个专业智能体→本地验收先证明专业委派有用；默认先做Codex垂直闭环，可按部署可用性调整允许的工作包交付patch，独立测试通过，能取消和恢复
3 · P1Jev智能路由、证据筛选、进展监督让高频判断便宜且可控；从影子运行到选择性接管对比规则路由：成功率不降且总成本或时延改善
4 · P1Claude Code＋Codex多任务协作第二provider、任务图、工作区隔离与集成者至少两个独立任务并行，依赖顺序正确，冲突由单一集成者解决
5 · P2高性能9B双模式专项训练与端侧优化让普通任务承担率提高，减少非必要专业调用最终部署版本同时通过decide和generate测试，量化后复验
6 · P3模型–Harness一体化RL与自动晋级有可信反馈后再学长期策略，避免优化错误目标独立holdout证明质量与成本收益，更新/重载/回滚完整
第一里程碑：一台本地设备、一个9B推理入口、一个专家provider、三类任务、一个验收器。Jev接口与影子日志从第一天接入，但不阻塞规则基线工作。

三类首验任务：①本地公开资料问答；②本地私有CSV整理；③允许外发的代码修复。先完成这三个真实纵向流程，再拓宽任务种类和自动化权限。

04

任务分流：隐私与能力是两个独立维度

隐私决定允许去哪里，能力决定谁能做。普通任务不一定简单，专业任务也不一定允许出云；“本地失败就自动上云”不符合这个产品目标。

  1. 确定性预检：读取用户数据策略、工具授权、预算与本地资源；明确标记的local-only不需要模型再判断。
  2. 形成任务状态：从目标和可访问资料生成最小任务说明、验收条件和合法执行候选。信息足够就行动，只对真正阻塞的缺口提问。
  3. Jev分类与路由：选择local-tool、local-9b、expert、clarify或unknown；结合能力档案与校准结果，禁止凭单个概率阈值放行。
  4. 本地执行或最小委派：本地9B负责已验收能力；专业worker只能获得受允许的工作包，不拿完整聊天或整个私有仓库。
  5. 本地验收：检查产物、测试、证据、费用与数据边界。未通过则有界重试或升级；预算到期和用户停止优先。

路由策略演示

预设规则 · 不调用模型

切换案例与数据策略，观察预期路由。它用于解释方案，不代表已运行的Jev分类结果。

“按清单协作”仍需检查每次实际工作包；它不是允许外发所有数据，也不会授权绕过local-only标记。

05

隐私设计：从“本地模型”扩展到“本地数据边界”

第一版必须让用户看得懂数据去向，也让代码能够执行限制。模型识别敏感信息提供辅助信号；用户标记、目录权限和外发策略具有更高优先级。

策略允许行为升级方式
Local-only本地模型、本地文件与被授权的本地工具；禁止外部模型调用能力不足时本地重试、请求更多信息或说明限制；原始内容不自动出云
受控协作仅允许外发清单内的公开或经审批材料构建最小工作包并核对文件、字段、引用、工具和目标provider
用户明确授权的云处理指定资料可供指定服务、指定任务使用不扩大到整机目录、历史会话、其他任务；传输记录可审计

外发工作包是技术边界

使用独立导出目录，复制允许文件与合成fixture，去除Git历史、secret、真实客户数据、未授权隐藏文件和符号链接。脱敏映射留在本地；专家返回通用逻辑或patch后，再在本地应用真实数据。摘要、文件名、错误栈、测试输出也可能包含敏感信息，必须一起检查。

Git worktree用于并行开发隔离，不是隐私沙箱。它可能共享仓库历史，对同一用户进程也没有天然读权限隔离。专家进程需要受限文件挂载、环境变量/凭据隔离，以及按部署条件实施的进程与网络策略；设置cwd和提示“不要读”均不够。

三个需要主动避免的外泄通道

  • 外部worker自行读取父项目、主目录、缓存、credentials或其他worker目录。
  • 本地工具通过搜索、MCP、遥测、崩溃上报或命令网络访问发送内容。
  • 模型把敏感内容改写为摘要后，误以为摘要已经匿名且可外发。

持续授权以“项目×资料范围×用途×provider”表示，可撤销；稳定范围内不用每次弹窗。出现新的敏感资料或新用途时，再进行定向确认。模型下载/软件更新与任务推理联网分别控制。

本地推理解决了模型服务的数据去向，但不自动解决整个工具链的数据去向。第一版以可观察的网络与文件访问测试证明边界，不以产品文案作保证。
06

多智能体编排：一个调度者，多个有范围的执行者

DSH持有任务图与唯一的最终状态。Claude Code和Codex按能力档案竞争或分工，角色不永久绑定厂商；先串行跑通，再并行处理真正独立的工作。

角色职责读写与结果
协调者 · DSH＋本地模型拆解目标、形成验收项、决策路由、预算分配拥有任务图；复杂规划可向专家征求方案，最终执行由策略控制
本地执行者 · 9B读取私有数据、普通问答、局部Draft、证据提取按授权访问本地资料；产物标注来源与验证状态
专业执行者 · Codex/Claude接收边界明确的工程或分析工作包独立工作区；提交patch/产物/测试记录，不能自批采纳
复核者 · 本地检查＋按需专家检查测试、回归、需求覆盖和可疑结论优先确定性测试；高风险时换独立上下文复核，不对每个小任务双重付费
集成者 · 唯一写入者检查base版本、合并patch、运行集成验收单点集成避免相互覆盖；通过后才更新任务为accepted

任务图与状态

TaskSpec包括目标、依赖、文件范围、只读/可写权限、数据策略、provider能力需求、预算、验收方法、base revision。独立节点可并行，依赖节点只能在前置产物被采纳后启动。

created → ready → leased → running → result_received → verifying → accepted
                         ↘ failed / cancelled / blocked
                                     ↘ 明确原因＋有界重试

每次尝试有attempt_id和租约；重启后确认旧进程是否仍在运行，不能重复启动造成双写。超时进入取消流程，收到终止回执后释放资源；晚到结果按版本和attempt拒绝。子任务正常停止不等于业务完成。

工作区、上下文与预算

公开代码可按任务使用独立worktree；含隐私的工程采用最小导出sandbox。每个任务只发送必要上下文与产物引用，禁止复制全历史。总预算覆盖9B、所有worker、reviewer、重试与工具成本；初期专家并发上限建议设2，本地推理由队列串行/小并发执行，阈值必须可配置并实测。

Jev快速请求优先于可暂停的长摘要，但不得承诺不可抢占engine能即时抢占；使用分块、分队列或经测量的独立服务解决队头阻塞。

08

Jev 在系统中的八个智能位置

Jev是重要智能组件，既能服务调度，也能服务普通业务分类。它的使用条件是候选明确、错误可纠正、证据可获取，而且增量收益能超过额外推理成本。

顺序Jev工作候选示例失败回退
第一批任务与能力路由local_tool / local_9b / expert / clarify / unknown规则路由或明确升级；不越过隐私策略
第一批工作包证据筛选keep / optional / irrelevant / unknown保留原文与必要字段；不允许模型删除唯一证据
第一批无进展与异常分类progress / same_failure / tool_fault / unclear提醒或升级，不因一次判断停止正确工作
第二批验收完整性辅助evidence_present / missing / contradictorycandidate_done交由测试和验收清单决定
第二批候选worker与工作拆分可用provider候选、独立/有依赖能力注册表与依赖图校验
第二批上下文与记忆选择retain / summarize / retrieve / unknown约束、用户授权与未完成项强制保留
第二批用户业务分类文档类别、票据类型、优先级、意图可解释标签与人工复核入口
后续模型深度与质量异常low / high / escalate；退化原因候选按实际部署校准，不归因供应商暗中降级

候选由系统生成并校验，未知必须是合法结果。候选召回率、误路由和弃权覆盖分别测量；不因为输出格式合法就认定判断正确。优先在任务开始、阶段切换、错误事件和验收点触发，避免每一步重复扫描完整历史。

先用固定high出口建立任务基线，再试low与动态升级。同一决策结果必须携带模型revision、adapter、量化、出口、prompt版本和证据引用；版本变化后重新评估阈值。

统一控制回路

01 形成状态DSH从Session、工具和环境构造可重放state_digest
→
02 生成合法候选代码先排除越权、过预算和不允许外发的候选
→
03 Jev判断请求带task、目标revision、证据引用、候选顺序和deadline
→
04 策略落地代码校验结果，执行或回退；不把分数当授权
→
05 外部验收测试、产物、退出码、数据策略与费用形成新事实

每次请求还带 decision_kind、model_revision、adapter、executed_depth、calibration_version、prompt_version、state_digest 和 evidence_refs。重复状态可复用时，缓存键必须包含候选与顺序、目标revision、摘要哈希、策略版本和部署身份；过期、权限和完成判断禁止跨状态缓存。

触发策略：事件驱动，绝不按步强制调用

首期触发四类事件：首次目标进入、阶段切换、工具/测试出现错误、停止前验收。正常工具成功与稳定重复读取不调用Jev；固定每N步调用会增加串行延迟，并可能让建议变成新的噪声。每次决定设置deadline和最大重试次数；Jev不可用时DSH仍能用规则和强模型完成既有路径。

四级回退协议

  1. 本地规则：确定性权限、候选合法性、退出码、路径和预算先判。
  2. Jev可用：在候选集中返回决定或unknown；记录完整分数与版本，不暴露为保证。
  3. Jev超时/错误：按场景安全默认；路由场景回到规则默认，完成场景保守续跑或人工确认，隐私场景禁止自动外发。
  4. 决策冲突：保留原始证据和两个意见，交由verifier/强模型/用户确认；不通过多数投票伪造真值。

本地9B路线：双模式契约，逐步统一权重

长期目标是一个高性能本地APUS 9B同时支持自然语言生成、工具使用和Jev式高速决策。工程首先统一接口与任务体验，再检验共享权重、共享engine和动态深度是否有净收益。

阶段模型/服务形态收益与取舍
V0 · 接入验证现有生成9B＋Jev决策能力，通过统一provider接口使用允许不同adapter或checkpoint；尽快验证分工，不冒称单模型双能力已完成
V1 · 双模式部署兼容同基座时尝试一个常驻engine＋两个adapter/读出路径不一定复制基座，但实际候选logits与adapter切换支持需验证；不支持则保留显式双服务
V2 · 单权重联合训练同一9B学习decision损失和generation损失用双侧holdout防止决策增强损害生成，或反向遗忘
V3 · 端侧优化量化、固定低深度出口、批处理、分队列、按需缓存针对真实硬件峰值内存、P95和任务质量验收；不预设共享KV/早退必然有效

接口分开，身份统一记录

decide()

任务状态＋合法候选＋证据引用
→ 选择、候选分数、unknown、模型/出口身份

短响应，无需生成长解释；分数不是天然校准置信度。

generate()

消息＋允许工具＋预算
→ 文本、摘要、Draft、受约束工具请求

通用生成单独验收；最终可见答案与推理字段分开处理。

“高性能”必须拆成可测指标

决策测固定输入长度下端到端P50/P95、准确率与弃权；生成测首token时间、tokens/s、质量、长上下文与峰值内存；系统测每成功任务费用、耗时与用户干预。现有96GB GPU上的决策延迟不能替代用户电脑上的表现。

9B理论权重载荷十进制GB不是整机配置要求
16-bit18不含激活、KV/混合状态、runtime和工作区
8-bit9不含量化元数据、未量化层和adapter
4-bit4.5两独立engine通常各自加载基座和cache，不能仍按4.5GB算总需求

目标设备先做Apple Silicon、消费级GPU各一档实测，再公布最低配置和建议配置。最长支持上下文、并发、量化精度和模型身份一并报告。低资源用户可选云端APUS，但该模式不继承“隐私数据留本地”的承诺。

模型–Harness 联合训练：先分角色，再学长期策略

复用Uni-Agent/Harbor/VERL的训练与验证链路；DSH拥有运行时，训练仓库拥有优化器。先冻结专业模型和执行器，训练9B控制策略；生成能力独立建立回归后再做联合实验。

阶段训练对象与数据准入条件
T0零训练基线：原DSH、规则路由、普通9B、Jev策略固定任务、模型、数据策略与费用口径，先证明问题存在
T1decide专项SFT：路由、证据、澄清、卡死、候选完成标签来自真实任务与独立验收；同轨迹及前缀按组隔离
T2generate专项SFT/蒸馏：私有任务范式、摘要、工具参数、局部patch保留通用生成集和Jev集，按角色mask；工具输出不当模型目标
T3固定执行器的controller优化：成本约束下的动作选择shadow校准与独立配对评测通过；先低风险决策再多步RL
T4联合/交替优化：controller与generator分批更新每次固定另一侧与verifier；同时验收质量、成本、遗忘和恢复

奖励顺序：先满足外部验证的任务质量与数据边界，再优化成本和时延。少花token但未完成不能算成功；模型不能改verifier、给自己打分或选择性丢弃失败任务。错误完成、证据遗漏、误外发单独记账。

训练数据按项目/任务族/来源划分训练、校准和封存集；私有项目默认只在本地运行，不自动进入训练。要做本地个性化学习，也需明确选择数据与可撤销策略。保留adapter可回滚，晋级要有独立reload与运行回执。

既有训练底座有真实更新与重载证据，也有工具任务负提升记录。它证明工程基础存在，不证明System3收益已成立。沿用sdk-minimal也不足覆盖压缩、skills和subagents；训练必须固定完整System3插件组合。

里程碑与验收：以完成条件排序

以下是依赖顺序和建议范围，不是工期承诺。每阶段都可独立评估，不把“做完训练”当作用户能用的替代证明。

里程碑交付范围验收证据暂不纳入
M0 · 固定底座通过原始代码门禁；固定DSH/SDK/runtime/model/profile版本；明确本地硬件Ruff与相关构建检查、baseline smoke、费用口径和数据策略用例训练GPU、新模型发布
M1 · 最小System3本地9B＋Codex一次性委派＋本地验收＋隐私边界；Jev shadow公开笔记、私有CSV、公开代码修复三流程；禁云无外发；取消/超时/失败回退双专家并发、持久专家会话
M2 · 专家协作Claude provider＋任务依赖＋隔离工作区＋唯一集成者并行独立子任务、冲突处理、重启避免重复执行、取消回执无边界自动改全仓
M3 · Jev主动策略按阶段路由、证据筛选、无进展与验收建议相对规则基线有可信收益；未达标能力继续shadow每步强制判断、未经校准的自动结束
M4 · 双模式9B优化任务专项训练、量化与部署优化，扩大本地任务承担率最终部署身份双模式回归、任务成功与资源测量先验宣称同权重无损
M5 · 有界联合RL完整轨迹、controller训练、独立晋级和回滚更新→保存→独立reload→任务holdout→canary模型自主改权限与奖励

主指标与实验对照

主指标：每次成功完成任务的总成本。并列报告成功率、P95耗时、用户干预、错误完成、隐私越界、峰值内存和专家返工量。本地成本含资源摊销，云端按真实usage，订阅额度体验单独记录，不把API美元与订阅扣量混算。

对照：原DSH → 规则分流 → 普通9B控制 → Jev控制 → 加本地生成 → 经训练策略。尽量只改变一个因素；相同任务和预算、随机运行顺序，报告缓存/服务波动。先做可行性pilot，再据方差规划正式封存样本，不用少量样本宣称统计优势。

建议待审批的产品门槛：成功率非劣界限2个百分点，每成功任务成本降低20%，P95不恶化超过10%；隐私策略违例为停止发布条件。统计区间不支持时结论是未证明，不能因平均值好看直接晋级。这些数值是目标，不是现有结果。

必须覆盖的故障

权限不足、9B超时、专家配额不足、工具失败、隐私字段漏检、相对路径/符号链接逃逸、工作包版本陈旧、worker晚到结果、重复租约、并发文件冲突、停机恢复、取消未确认、最终测试失败。用可重复fixture与真实进程分别验证。
