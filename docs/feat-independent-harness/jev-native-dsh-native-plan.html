评审结论与方案状态

可实现性：局部原生融合可行，完整混合调度分条件推进，产品收益尚未证明。现有 DSH 能承载有界的 System1 判断与同会话 Goal 跟进。自动模型联合调度、长期语义记忆、离线自治需要各自的额外契约和验证，不以统一架构名义一并启动。

本方案经过 DSH 生命周期源码审计、Pilot 实验事实核查，以及两轮独立反方 review。以下结论是本轮静态审计与既有报告分析，不代表完成了新运行时原型或新模型评测。

  • 保留：Jev Native + DSH Native；规则、System1、System2 分工；DSH 单一事实来源与执行权。
  • 撤回：将新增 pre-assembly 契约当作首期前提。现有事件能承载的场景先用现有事件。
  • 收敛：先做一个固定 route、有限有效候选的语义恢复试验；不裁剪工具、不自动改目标。
  • 条件性推进：联合路由、语义记忆和离线唤醒分别证明需求、工程可行性与收益。
  • 批准范围：当前仅交付设计文档和 README 架构说明；运行时代码实施仍需具体设计确认。

1. 两个 Native 分别意味着什么

层次原生职责不应承担
Jev Native / System1直接使用结构化 state + questions，输出 Choice、Score、Noul；在受限候选集内做语义判断，允许弃权。多问题可以共享同一有界证据。模拟聊天助手写长篇计划；生成任意 shell；宣告权限、预算或任务正确性。
System2理解开放任务、构造假设、规划、生成代码和工具调用；处理 System1 无法判别或缺少候选的问题。在已有足够证据与有限候选时，反复用完整生成解释每个中间选择。
DSH Native拥有 AgentLoop、Session、工具与 provider；原生安排决策时机、组织证据、限定候选、保留采用结果，并控制取消、权限与预算。把另一套 hook loop、JSONL 状态库或外部控制进程叠加成第二个事实来源。

“规则覆盖不了、完整生成又太贵”的位置必须同时满足三个条件：存在语义歧义、有可执行的有限候选、错误可被检测或恢复。Jev-like 是能力角色，不以模型参数量自动定义；低延迟、低成本及概率可用性都需实际测量。System3 的关键是分工与反馈，而不是每个步骤都调用两种模型。

2. 从 DSH 的真实执行结构推导设计

DSH 的 step 是一次模型请求及其工具调用；turn 是一个或多个 step。下列机制来自当前源码，不是通用 Agent 框架假设。

claim input → assemble prompt/tools → agent/pre-step
→ step/start → agent/request → prepareCall → log admitted input
→ freeze model history → stream System2 → execute tools → step/end
→ next step, or agent/turn-stopping → turn/end
DSH 特性对 System3 的直接影响
Session 为上下文事实来源；模型可见必须可从日志重建System1 与 System2 都使用有来源的输入。决策需要记录实际请求、建议、采纳动作与后续结果；哈希不能代替完整可重建输入。
typed events + waterfall / serial 不同语义在明确等待点决策；waterfall 必须继续委派。避免在广播观察器中异步抢改下一步状态。
请求先准备，后提交输入并冻结历史路由、上下文变更必须在请求冻结前完成。取消中的未提交用户输入不能被当作既有日志事实。
pre-step 发生在 prompt/tool assembly 之后它适合准入和待输入调整，不是任意修改当前工具 schema 的万能接口。工具候选集应在所属 registry/preset 与 assembly 机制中处理。
compaction、spill、Session projection 已有各自职责在原生机制中做证据选择和可恢复引用；不偷偷删历史。全局历史压缩必须遵守工具配对、压缩事务与请求缓存规则。
模型 provider 与 subagent provider 分开“换生成模型”与“委派 Codex/Claude Code 执行任务”是不同动作，不应混进同一个无差别 model 字段。
scoped Context、effect 注册与卸载决策策略按 agent/profile 组合，明确继承与卸载。不能全局监听后把子 agent 和父 agent 的目标、预算混用。

源码入口：DSH 架构、AgentLoop、原生生命周期接口、模型选择、Compaction 服务。

3. 五类原生能力与两种决策节奏

整体架构审视原子能力、场景能力、记忆、模型分配和长程目标；它们是候选领域，不是必须建设的功能清单。每个领域先证明存在可观测的语义歧义与有效动作，再决定是否引入 System1。接口原则可以共享，输入、评价标准、触发频率与预算所有权分别设计。

领域DSH 原生基础Jev / System1 负责判断System2 与宿主负责行动
原子能力tools、skills、fs、shell、web、browser 的注册与执行从已准入候选中选适用能力、判断结果是否相关或值得进一步读取System2 构造复杂参数与代码；宿主校验参数、权限及执行结果。精确文件读取不需要另过模型。
场景能力preset、skill、workflow、subagent有限场景识别、选择已有执行策略、下一阶段或专家组合System2 开放式分解任务或生成 workflow；宿主管理并发、生命周期和取消。场景未定义时不能强制分类。
记忆管理Session 历史、session-query、storage 是基础设施，不等于已具备语义记忆系统候选事实是否值得记、与目标是否相关、是否疑似冲突或过期、下一步该检索什么若独立产品需求成立，再设计有类型、来源、作用域与版本的记忆服务；宿主决定写入/撤销/失效，System2 生成摘要或解决复杂冲突。不能把模型推断覆盖为用户事实。
模型与专家分配LLM call config、model-selection、subagent providers在已准入候选中选模型、effort 或专家；评估升级是否值得同一步计划绑定 prompt 与 route；宿主预留并结算预算。模型切换与外部专家委派分别定义动作。
长程目标与跟进goal、command-goal、tool-goal、goal-round-driver；schedule 负责会话内提醒阶段进展/偏移、是否卡住、下一里程碑策略、继续投入还是请求重规划、何时值得复核System2 分解与重规划；宿主持久化目标、约束授权和续轮；完成需独立验收，不由判断分数批准。

步骤级决策发生在步骤之间：能力、证据、路由、恢复。目标级决策发生在里程碑、goal round 或明确的提醒事件：目标健康、长期记忆、资源重新分配。目标级评估不应每一步都调用一次，也不能靠 System1 的文字建议充当真实定时器。

长程 Goal：已有原生底座，需增加语义跟进

DSH 已有原生 /goal 相关包，而非需要复制其他产品命令。ctx.goals 持久化一个 session 的当前目标、阶段、版本和轮次；修改通过 compare-and-set 拒绝旧版本。goal-round-driver 在 agent idle 且目标已授权继续时预留并发起下一轮，并在输入实际进入历史后计数。这是 System3 长程目标的基础。

用户设定 Goal 与约束 → DSH 保存版本化目标
→ System2 提出里程碑和验收方案
→ DSH 续轮：提取本轮证据 + 当前目标/里程碑
→ 规则检查授权与资源 → Jev 判断进展、偏移和下一策略
→ 同策略推进 / 补证据 / System2 重规划 / 请求用户信息
→ 独立验收 → 保持、阻塞或完成当前目标
→ 仅在已有授权与调度条件下继续跟进

当前限制必须保留：goal 仅有轮次数预算，不等于 tokens/费用/时间预算；只有一个当前目标，不能宣称已有跨项目多目标树；goal 完成由调用者记录，尚无独立认证；resume/fork/restart 后目标虽然保留，自动继续会 disarm，必须显式授权恢复。

schedule 的提醒能持久化，但交付需要活跃 root agent；关闭 session 后提醒会等待恢复，不是离线后台守护进程。若产品需要跨天、进程退出后的自动唤醒，需要独立需求和授权，并另行设计持久任务执行宿主、唤醒授权、租约与去重、预算、通知和失败恢复。不能直接把 goal + schedule 宣称为全天候自治。

候选长期状态包括 goal revision、验收条件、里程碑及依赖、最新可信证据、阻塞原因、允许的后续行动与预算。状态由 DSH 保存；System1 对状态提出有限决策，不自行改用户目标。记忆和目标互相引用，但执行日志、可撤销的语义记忆、用户目标三者不混成一张自由文本表。

源码入口：Goal、续轮驱动、Schedule、Workflow、Storage、Session query。

4. 全流程中的 System1 位置与优先级

下表是场景假设与接入分析，不是将 Pilot 功能清单移植为 DSH 模块。第一轮一次只验证一个位置，避免无法归因。

环节规则先解决System1 的语义判断System2 保留职责 / DSH 落点顺序
失败后的下一步取消、权限、次数上限、明确的网络重试类别失败是否同因；新证据是否足以继续；补读、换假设、再试还是升级构造新假设并修改实现。工具结果与 step 事实先记录，下一 pre-step 决策；不把业务失败混入传输重试。首个控制试验
证据进入下一请求硬锚点、去重、大小限额、索引与按需读哪些候选片段与当前子目标有关，哪些应立即读回综合证据、解释与生成。接入 tool-result / spill / compaction 所属机制；先评估新增材料，后考虑全局历史。首批离线评测
验证选择明确要求的测试必须执行；失败不得放行目标与已有证据之间缺少哪类验证，哪一个候选检查最有信息量构造开放性检查并解释结果。候选完成时的 turn-stopping；“turn 完成”不等于用户目标完成。首批影子试验
生成模型 / effort隐私、provider 能力、模型白名单、预算可用性当前有限候选中的质量与代价取舍执行难题推理；通过 agent/request 和原生模型选择接口生效，真实目标输入需有所属状态。能力画像与收益数据后
专家委派可用专家、工具权限、并发与深度限制当前问题更适合本 agent、某专家还是用户补充信息构造委派任务并综合输出；通过 subagent 服务，不把外部 CLI 当普通聊天模型。路由之后
工具与技能候选选择安装状态、权限、显式用户选择候选工具/技能和任务的语义匹配生成参数与开放式调用策略；由 registry/preset/context 的所属机制在 assembly 前处理。按实际 schema 开销决定
记忆写入与检索来源、权限、容量、过期策略是否值得持久化或取回特定候选记忆先建立原生记忆语义与正确性要求；仅在产品需求成立时作为独立原生能力定义候选事实、检索、写入及撤销接口，不把 storage 误称为语义记忆系统。整体架构范围；独立切片

明确不交给 System1：权限授予、密钥外发、精确预算结算、取消处理、确定性工具结果真假、未经独立验证的最终完成。Jev 可以指出证据不足，但不能用自报 confidence 把证据不足变成通过。

5. 原生混合调度，而非外围裁判

统一决策过程

  1. DSH 在受控生命周期点构造 DecisionContext：agent/session、goal revision、turn/step、证据序号、限长语义片段、合法候选、权限和预算版本。
  2. 规则处理已知情况并判断是否值得调用 System1。没有语义内容、只有一个合法候选、已有有效缓存或任务已取消时，不产生模型调用。
  3. System1 在合法候选上作结构化判断。请求不要求 System2 先写一篇昂贵总结；使用事件投影、原始片段及已有计划事实。
  4. 宿主校验响应、时效、作用域和预算。System1 的弃权、失败或不确定性导致保守基线或 System2 深入判断；具体行为按决策类型定义。
  5. 由所属原生服务在安全位置采纳动作，记录 proposed / applied / rejected 及原因。建议“再试”不等于自动重放可能有副作用的工具。
  6. 把真实验证和后续结果关联到 decision id；回放只读记录，不重发 Jev 请求、不重复执行动作。

条件性扩展：何时才需要新的步骤准备契约

源码核查发现：现有扩展点不足以在同一步同时可靠决定输入、工具集合和 System2 路由。pre-step 已晚于 assembly；agent/request 没有当前 claimed messages；system-prompt/assemble 同样缺少该批输入。但这不意味着所有原生混合场景都需要新接口：失败恢复可用现有 pre-step，已落盘目标的路由可先验证 model-selection。只有具体场景要求用当前 claimed input 同时决定当次 prompt、tools 与 route，且现有机制无法安全表达时，才考虑 claim 后、assembly 前的 step preparation。下面是条件性候选，不是首期实现承诺。

claim 本次输入
→ prepare step（仅联合调度需求被证实后考虑）
    规则 → 必要时 System1 → 校验 → 不可变 StepPlan
→ assembly 消费同一计划的上下文 / 工具可见性 / 模型变量
→ pre-step 保留现有准入与 compaction
→ request 消费同一计划的 System2 route
→ System2 → tools → 完整结果提交 → 下一步

StepPlan 绑定 agent、turn/step、目标、claimed input 和证据版本；不能用全局可变“推荐模型”分别影响 prompt 和实际 provider。已有 installModelSelection() 在 assembly 捕获 selection、request 消费捕获结果，提供了同一步一致性的原生先例。

compaction 如果在 pre-step 改变上下文，必须使相关选择失效或重新验证；请求重试当前不重复 assembly/pre-step，需要明确哪些失败允许复用计划、哪些应重新准备。取消时分别记录 System1 决策尝试与 System2 输入是否被接受，不能提前把待提交输入写成已执行事实。

工具结果在 tools.finalize() 等待 post-execute 后才按模型顺序落盘。在每个工具 post-execute 中同步调用 Jev 会阻塞整批提交，并只看到半批证据。建议该处仅做轻量事实提取，读取完整批次后的下一受控准入点（首期可用现有 pre-step）再进行语义决策。session/event 是提交后的非等待广播，不拥有调度权；turn-stopping 也不覆盖所有工具循环。

二轮技术 review：新 hook 本身不解决一致性。现有 compaction 使用最新持久 route 和历史上下文进行压力判断；候选新 route 的较小窗口、当前 claimed input、prompt/tools 体积未因此得到最终容量保证。首期固定 route。将来路由切换必须验证最终 request envelope，明确路由撤回或有界重新准备，设次数上限，阻止“换路由→压缩→再选择”的循环。自动路由必须与现有 model-selection 使用同一个权威拥有者，用户显式选型优先；不能有两套并行可变 route。

最小原生接口草案

这是设计草案，尚未建立公开 API。先在已有 System3 服务附近聚合实现，不为图示拆出大量空包。

DecisionContext
  scope: session / agent / goal revision / turn / step / evidence version
  problem: decision kind + bounded semantic evidence + allowed candidates
  constraints: privacy / permission / deadline / authoritative budget

DecisionOutcome
  source: deterministic | system1 | system2
  result: selected candidate | abstain | unavailable
  evidence: exact input + provider/model + usage + elapsed time

DecisionApplication
  proposed action → revalidate → applied / rejected / expired
  resulting Session event references + independent outcome

Jev Native 保持现有 /v1/systemone 类型接口。Choice 用于有限策略选择；Score 评估有序语义等级；Noul 判断命题。三个接口存在不代表三个用途都已经校准。DSH Native 负责上下文与执行语义，两者通过类型化请求连接，不把聊天 completion 临时解析成决策协议。

加载与模块组织

运行时仍由 dsh profile / Cordis 配置组合。现有 Jev provider 承担模型接口；System3 原生协调服务承担共享状态、候选与决策；薄的生命周期消费者把结果接入所属服务。正式 System3 profile 最终统一装配它们，功能级模式决定规则、观察或有界采纳。这里的“插件”是 DSH 原生实现单元，不是安装 Pilot、MCP 包装器或每次事件启动 Python。

原生性来自状态、生命周期与执行权归属，不取决于是否修改 AgentLoop。优先使用现有扩展点；新增契约必须由一个无法安全表达的具体用例证明必要性，并配套架构、两套 SDK 和快照验证。

成本与失败语义

触发器、输入长度、调用次数、deadline、干预次数和同状态去重都由配置与宿主强制。多问题批处理只在相同证据版本与 deadline 下使用；缓存键必须包含目标、证据、候选、模型与策略版本。首期落实输入、调用次数、deadline 与干预次数上限；跨 provider 费用预算若另行建设，应由宿主预留再结算，不能假设现有 goal round cap 已覆盖。provider 未知用量保留 unknown。重定向、取消、晚到响应、卸载中的请求和并发子 agent 均需明确处理。

“低成本”必须包含语义输入构造、Jev 请求、网络排队、缓存破坏、额外补读和错误决策恢复。频繁改动模型历史可能损失 prefix cache；减少输入字符不是节省真实费用的充分条件。System1 服务不可用不应扩大权限，也不能被记录为任务成功。

controlled 模式仍是 proposal / dry-run；Context 显式 pack 由外层送入新宿主不能据此宣称已有可移入的自动控制器；System3 必须定义原生采用时机和真实采用证据。
18 次校准，Jev 4/6 严格成功；baseline/rules 各 5/6；每格只有一次运行这是工程与计量校准，不足以证明质量非劣、普遍收益或默认开启。
仅两个双方成功且用量完整的配对：tokens 分别下降 16.21% 和增加 34.03%，耗时均增加不能只选节省样本或把总 tokens 当真实账单；失败、回退和未知费用必须保留。
baseline/rules 在现有三题中输入一致，且未单列低成本索引对照DSH 应建立有竞争力的规则与按需读基线；不能靠弱化基线证明 System1 价值。

值得吸收的是实验问题与教训，不是功能和代码：候选是否有语义信息、采用是否真的发生、原文是否可恢复、收益是否来自 System1、故障成本是否完整计入。

7. 设计到实施的切片与验收

本次交付为架构评估与 README 图示，未实施下面的运行时代码。详细 API、配置和首个控制场景需在实施前确认。

阶段交付验收
M1 最小原生可行性验证一个恢复场景的原生事实投影、可执行候选、规则基线、调用与采用记录；固定 route，不筛掉工具。独立修复 supervisor 空检查及 evidenceRefs 缺口，不让其阻塞无关试验。输入可重建；目标变更、取消、并发、缺证据、无预算均不会错误采纳。
M2 单场景 System1失败后的恢复选择；先影子比较，再隔离任务中有界采纳。只有合适证据和候选时调用 Jev。真实 AgentLoop fixture、无密钥 snapshot、原生请求与动作关联、功能关闭后恢复基线。
M3 原生混合行为在证据支持下扩展上下文选择、验证选择，再扩展模型路由与专家委派。每个位置独立评测，避免跨模块同时上线导致无法归因。
M4 默认产品配置将通过验证的策略组合为 System3 profile 与可见决策记录。新任务 holdout、端到端质量与成本达标；可回滚、可恢复、安装与升级实际验收。

建议影响的文件与服务

实施候选包括 packages/experimental/system3/src/ 的决策与 projection、system3-supervisor/src/ 的验收规则、Jev provider 的请求生命周期，以及所选场景的 agent/tool/compaction 消费者。首期不计划改动 core loop；只有联合调度用例证明必要后，才评审 packages/core/agent 与 agent-loop 的最小契约扩展。SessionEventMap 变化同步 TypeScript/Python SDK 和真实会话 snapshot；本次没有这些代码改动。

可行性 review：技术、信息、收益分别判定

候选技术判定信息与收益前提本次建议
失败恢复、已有 Goal 的进展判断现有生命周期可承载；完整控制效果尚未实现验证失败原文/语义证据、目标、有效候选齐备；规则不能直接解决做一个固定 route 的受限试验
工具/skill 候选排序原生 registry 可提供候选需证明候选过多造成实际代价，排序不会隐藏必需能力先建议排序；无证据不做工具裁剪
场景策略选择有现成策略时可实现；workflow 没有跨重启 journaling/resume封闭场景有效；任务超出候选时可退出到 System2有真实重复场景再加入，不建万能分类器
证据与历史召回排序已有存储、检索和可恢复上下文基础须胜过廉价索引与按需读，并计入缓存/补读代价离线对照先行
自动模型/effort 路由局部可做；联合当次工具/上下文选择需额外契约验证需要候选能力/成本画像；模型名称不是成功率数据后置；先解决容量、重试与用户选择优先级
长期语义记忆需新领域契约；现有 storage/FTS 不足来源、作用域、时间、撤销、检索质量必须先成立独立需求，不作为 System3 首版依赖
离线持续 Goal / 多目标管理当前底座不足；live goal 续轮与离线自治不同持久唤醒授权、租约、资源预算和恢复机制独立设计，不由 Jev 判断代替基础设施

原型必须固定实际可采取的候选：读取指定证据集、运行已生成且准入的检查、委派已配置专家、进入明确的 System2 重规划。抽象的 change_strategy 标签若不改变实际下一步，只是多一条提示。候选生成成本必须计入；如果 System2 已做完完整诊断才得到候选，System1 可能已经错过节省位置。

Pilot 报告的四次成功判断耗时约 4.9–5.5 秒，两个 transport 失败约 10 秒；这是其部署路径观测值，不是 Jev 裸模型推理时延，也不能直接外推新部署。它足以否定“短输出必然适合每步实时调用”的假设。新部署须先测真实端到端延迟与 usage，再选择值得等待的决策点。

停止条件：没有语义证据；合法候选只有一个；候选中没有可行解；规则已经足够；实际采用率低；质量下降；延迟或成本超过减少的下游工作。命中这些条件应跳过或撤回 System1 接入，不以完善架构图为由继续增加组件。

实施前必须关闭的决策项

  1. 选择一个真实任务族，列出规则不能决定的具体分歧与有效候选；先确认是否存在正确候选。
  2. 明确所用 Jev 部署、端到端延迟、输入限额及计费口径；尚无实测就不设“低成本”承诺。
  3. 明确读取哪些 DSH 事实、哪些语义片段允许发给 System1、如何绑定目标和证据版本。
  4. 明确实际改变的下一步、错误后的恢复方式与独立验收；影子观察不等于控制试验。
  5. 冻结规则基线、调用预算、弃权与停止条件；先通过代表性 fixture，再开展授权的真实模型评测。

四臂对照

  1. A：原始 DSH，测量当前执行能力。
  2. B：同触发点、同证据、同候选的确定性规则；上下文场景加有效索引与按需读。
  3. C：B + System1，测量 Jev 的增量，而不是总工程收益。
  4. D：B + System2 对同一有限问题判断，检验 System1 是否以更小代价接近所需质量。

冻结未见任务，配对分配、每格重复并保留失败。指标包括独立任务成功率、错误完成率、有效恢复率、每成功任务总费用、真实端到端 p50/p95、额外补读、弃权和服务失败率。不同模型累计 token 不直接等价于美元；无法取得账单则分别报告真实 usage、估计及未知项，不声称已验证降本。

结论：推荐将 DSH 升级为拥有原生混合决策机制的 Harness。Jev 原生接口处理有限语义判断，System2 处理开放推理与生成，DSH 原生机制拥有状态与动作。是否默认采用某个 System1 决策，由任务结果与完整成本证据决定。
