# Reflex 前置决策：理论与评测框架

[English](README.md) | 中文

## 概述

Agent 靠交替调用模型和工具来回答，所以大部分时间耗在一条串行的往返链上。其中很多往返只是收集信息，而需要哪些信息往往从输入就能预判。Reflex 前置决策让一个小而快的决策模型（Jev）在主模型第一次调用之前选出这些信息和 Skill，同时用只读命令并行取回所有候选，主模型一开始就拿到事实。本文给出这一设计背后的延迟模型、由它推出的设计原则、待检验的假设、测试方法、目前的实测结果和后续迭代，是论文的工作框架；所有数字都注明日期和测试集。

<a id="problem-and-latency-model"></a>
## 问题与延迟模型

下面的模型说明前置决策在哪里省时间、什么时候省不了。一条用户输入视为一个任务。

**原生 Agent。** 一个 n 步的任务耗时 T_native = Σᵢ (Lᵢ + Xᵢ)，其中 Lᵢ 是第 i 步主模型的延迟，Xᵢ 是它随后调用工具的延迟。每一步都依赖上一步，所以这个和就是关键路径。

**可预测的收集。** 有些步骤只是收集信息（读文件、列文件、搜索、看 diff），其参数可以从输入和工作区推出。设这类步骤有 k 个，占 T_native 的比例为 f。它们之所以在关键路径上，只是因为主模型要先决定做这一步。

**前置决策。** 在第 1 步之前，规则生成器提出 m 个只读候选信息；m 条命令并行执行，耗时 max_j x_j，同时决策模型在 d 的延迟内回答 m 道是非题。这一步等待 d' = max(d, max_j x_j)。当选中的信息覆盖了任务所需（命中，概率 h），这 k 个收集步骤就消失：T_reflex ≈ d' + T_native − h·k·(L̄ + X̄) + ε，其中 ε 是注入信息带来的额外提示延迟。

**盈亏平衡与上限。** 当 h·k·(L̄ + X̄) > d' + ε 时前置决策才划算。取 L̄ + X̄ ≈ 1.5–3 秒、d' ≈ 0.3–0.6 秒，h·k 大约超过 0.2–0.3 就划算。与 Amdahl 定律同理，提速至多为 1 / (1 − f + d'/T_native)；没有可预测收集的输入（k = 0，例如闲聊）只会损失 d'。

**决策延迟。** 在已部署的网关上，一次请求约为 r + q·m，其中网络往返 r ≈ 125 毫秒、每道题 q ≈ 30 毫秒，并且并发请求会被并行处理。把 m 道题拆成 p 个并行请求，d ≈ r + q·m/p，候选越多，决策成本也基本不涨。

<a id="design-principles"></a>
## 设计原则

每条原则都对应模型中的一项，并且都已实现、可以测试。

| 原则 | 针对的模型项 | 规则 |
| --- | --- | --- |
| P1 重叠而非串联 | d' | 决策和所有候选取数同时启动，并与其他 pre-step 工作重叠 |
| P2 规则生成，模型选择 | h、m | 确定性规则提出带参数的具体候选；决策模型只对每个候选回答是或否 |
| P3 题目并行 | d | 题目拆成并行请求发送；绝不把多个决策合并成一个更大的请求 |
| P4 只增不限 | 失败成本 | 注入的信息只增加上下文；主模型保留全部工具，未命中的代价至多是原生路径 |
| P5 不改变内容时不挡路 | k = 0 时的 d' | 不会改变这一步消息的判断（例如只有意图）放到后台进行 |
| P6 原生兜底 | 失败成本 | 开关关闭、决策服务缺失或失败、超时，都保持原生路径不变 |
| P7 留痕可回放 | 可信度 | 模型可见的每条信息和每个决策都是会话事件，无需决策模型即可审计和回放 |

<a id="hypotheses"></a>
## 假设

每条假设都写成可以被一次测试确认或否定的形式。

- **H1** 在有可预测收集的任务上（k ≥ 1），前置决策降低端到端耗时，且不降低成功率。
- **H2** 收益随 k 增大：信息查询和代码定位收益最大，多步修改只省掉开头的收集步骤。
- **H3** k = 0 的输入至多损失 d'；没有决策挡在这一步之前时（P5），不损失。
- **H4** 把题目拆成并行请求后，d 大致按 r + q·m/p 下降。
- **H5** 只要候选不依赖 Git、搜索词覆盖用户使用的语言，这一方法能从代码仓库迁移到个人文件夹。

<a id="method"></a>
## 方法

测试在真实端点上运行产品自带的 Headless 配置；驱动脚本和覆盖配置位于 [`packages/experimental/system3/tests/fixtures`](../../packages/experimental/system3/tests/fixtures)。

- **对照组。** 原生 DSH，以及开启 Reflex 前置决策（预取、Skill 选择、每个 Jev 请求一道题）的 DSH。
- **模型。** 生成用 DeepSeek `deepseek-flash`；决策用已部署的 APUS Reflex 模型 `APUS-OpenJev-v1-9B-5949`。
- **隔离。** 每个任务在新进程、新会话、新工作区中运行，因此每次 Jev 连接都是冷启动；与常驻的产品相比，这会高估 d。
- **交替。** 每一轮内两组交替运行，使服务端的波动分摊到两组。
- **指标。** 从输入到最终回答的总耗时、主模型步数、工具调用、按回答或工作区确定性判定的成功、决策延迟，以及选中的信息和 Skill。
- **测试集。** `scenario-bench` 覆盖一个 40 个文件的服务（信息查询、代码定位、暂存改动、Skill、带测试的修改、中文输入、闲聊）和一个个人文件夹（日程、开销、待办、邮件、笔记、证件、闲聊、修改）；`prefetch-bench` 和 `skill-bench` 各自单独测一个机制。`skill-eval` 在 20 个 Skill 的目录上，用 48 条标注输入单独测量 Skill 选择，可带或不带 `whenToUse`。

<a id="results"></a>
## 结果

以下所有运行都在 2026-10-14，除非另有说明，每组各跑两轮。

| 运行 | 原生 → Reflex 总耗时 | 提速 | 主模型步数 | 成功 |
| --- | --- | --- | --- | --- |
| 上限：注入恰好所需的信息，5 文件仓库，6 个任务 | 79.4 秒 → 24.6 秒 | 3.2× | 44 → 12 | 12/12 → 12/12 |
| 预取，5 文件仓库，6 个任务 | 70.3 秒 → 30.8 秒 | 2.3× | 39 → 12 | 12/12 → 12/12 |
| 场景测试集，40 文件服务，16 个任务 | 319.8 秒 → 224.9 秒 | 1.42× | 150 → 76 | 32/32 → 32/32 |
| 个人文件夹，10 个任务，支持非 Git 之前 | 161.6 秒 → 171.7 秒 | 0.94× | 67 → 72 | 19/20 → 18/20 |
| 个人文件夹，10 个任务，支持非 Git 和中文搜索词之后 | 186.1 秒 → 179.2 秒（中位 8.8 秒 → 4.6 秒） | 1.04× | 71 → 29 | 18/20 → 20/20 |
| 场景测试集，40 文件服务，16 个任务，加入中文搜索词和不阻塞的意图判断之后 | 310.5 秒 → 189.5 秒 | 1.64× | 139 → 70 | 32/32 → 32/32 |
| 场景测试集，40 文件服务，加入文件登记已读、命中文件和 Skill 确认之后 | 365.9 秒 → 223.7 秒（中位 10.0 秒 → 4.1 秒） | 1.64× | 144 → 66 | 31/32 → 32/32 |
| 个人文件夹，10 个任务，同一轮 | 155.6 秒 → 93.9 秒（中位 6.9 秒 → 3.7 秒） | 1.66× | 69 → 24 | 19/20 → 20/20 |
| Skill 选择，48 条标注输入，20 个带 `whenToUse` 的 Skill（只测决策） | 正确 39/48 → 46/48 | — | — | 误选 1/15 → 0/15 |
| Skill 选择，同一批输入，Skill 不带 `whenToUse`（只测决策） | 正确 39/48 → 44/48 | — | — | 误选 1/15 → 2/15 |
| 带测试的修改，40 文件服务，2026-10-15，3 轮，单个文件写明所含搜索词、Skill 按明确请求提问 | 166.8 秒 → 83.7 秒 | 1.99× | 52 → 22 | 6/6 → 6/6 |
| Skill 选择，Skill 不带 `whenToUse`，按明确请求提问（只测决策） | 正确 44/48 → 43/48 | — | — | 误选 2/15 → 1/15 |

40 文件服务上的分类结果：信息查询 1.85×、代码定位 1.66×、Skill 1.49×、带测试的修改 1.42×、暂存改动 1.30×、中文输入 1.21×、闲聊 0.70×。冷连接下决策中位耗时约 0.6 秒；热连接下 7 道题作为一个请求约 340 毫秒，拆成 7 个并行请求约 260 毫秒。第二次迭代后，中文输入升到 3.51×、信息查询 2.51×、代码定位 2.11×；个人文件夹里待办达到 2.79×、开销 2.28×、证件查询 1.66×，但有一次个人修改任务的单次主模型调用耗时 60 秒，使文件夹总计停在 1.04×。

**解读。** 在服务上 H1 和 H2 成立：步数减半、所有任务仍然成功，收集占比越大的类别收益越大。在 P5 之前 H3 不成立：闲聊要等决策。在支持非 Git 之前 H5 不成立：个人文件夹没有任何候选，Reflex 只增加了延迟。第二次迭代后，H5 在收集类任务上成立：文件夹任务所需步数不到一半，且全部成功；H3 对闲聊仍不成立，因为预取决策挡在这一步之前，有时还会为一句问候选择搜索。第三、四次迭代中，目标文件被预取并登记为已读的修改任务直接调用编辑工具（3 步，原生约 9 步；待办修改 2 步）；决策没有选择预取时，修改仍按原生方式进行。Skill 选择取决于作者是否写了 `whenToUse`：确认后的选择在有 `whenToUse` 时达到 46/48，没有时 44/48，并且没有时评审或修改类输入仍可能被注入“写提交说明”Skill。闲聊和一步就能写完的邮件变慢（0.48–0.60×），原因是要等决策，以及多选的信息拉长了提示。第五次迭代中，预取的 `yes` 阈值（0.5、0.7、0.85）对任务总耗时的影响在噪声范围内；0.85 不再选择小文件夹的全部文件，使一次待办修改需要 5–7 步而不是 2–4 步。修改任务的收益来自另外两处改动：为修改任务提供的 README 写明其中包含的搜索词，于是 Jev 会选它；没有 `whenToUse` 的 Skill 按明确请求提问，退款修改不再被注入“写提交说明”Skill（该任务 0.98× → 1.93×）。Jev 仍会为“Review my staged change”给“写提交说明”打 0.99 分；另有两次主模型调用无报错地卡住 605 秒和 900 秒，这两次运行不计入总计。

<a id="threats-to-validity"></a>
## 效度威胁

以下限制适用于上面所有数字。

- 任务、工作区和判定标准由实现该机制的同一团队编写。
- 每组只有两轮，单个任务的波动较大；按类别汇总的数字比单个任务更稳定。
- 只测了一个生成模型和一个决策部署；主模型越慢，L̄ 越大，收益应当越高。
- 冷连接会高估常驻产品的 d。
- 没有与其他 Agent 产品对比；要说比它们更快，需要在同样的任务和模型上实测它们。

<a id="iteration-loop"></a>
## 迭代流程

每次迭代只改一个机制，重跑覆盖它的测试集，并把结果记入[结果](#results)。待做的迭代，按预期收益排序：

1. 彻底去掉闲聊的决策等待：主模型请求与决策并行发出，只在选中信息或 Skill 时重发。
2. 每次工具调用之后再次预取，让多步修改也省掉后面的收集步骤；文件登记已读和命中文件已经省掉了第一次读取。
3. 请 Skill 作者写 `whenToUse`，并测量缺少时加入 Skill 正文摘要是否有帮助。
4. 在标注输入上按候选类型校准 yes 阈值，在漏选和注入噪声之间取舍。
5. 在同样的任务上与其他 Agent 产品对比。

## 相关工作

- Speculative Actions（Ye 等，ICLR 2026）用更快的模型预测下一步动作，较慢的执行者认可时才保留；[论文](https://arxiv.org/abs/2510.04371)。

- Amdahl 定律用优化所能去掉的工作占比限制提速上限；在这里就是可预测收集的占比。

<a id="dev-note"></a>
## 开发备注

非权威。本文的“前置决策”指一条输入在主模型第一次调用之前做出的决策；执行过程中的 Reflex 控制决策（监督、完成核验）不在此框架内。已部署的决策模型对问题措辞很敏感：同一批输入上，换一种 Skill 问法会从 47/48 掉到 43/48，所以修改措辞必须跑一次评测。
