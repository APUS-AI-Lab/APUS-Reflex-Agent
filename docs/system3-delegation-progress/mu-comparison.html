mu 的判定点与 System3 的实现对照

mu：开源 Coding Agent pi 的扩展，判定内核 kyrn-judge（仓库 qybaihe/mu，2026-10-06 版本）。System3：DSH 内的原生插件，部署在 system3.xdan.work。mu 一栏来自代码和仓库文档；System3 一栏来自本仓库代码、单元测试和 prd 线上会话日志。

结论
  • 点数：文章说 35 个，代码里是 38 个（2026-10-05 起 README 改为 38）。其中 3 个默认关闭，另有若干只在调用对应工具或特定模式下运行。
  • 覆盖面：mu 宽，用 Jev 把大量琐碎判断外包出去；System3 窄，但每个点的动作更重：真正切换模型、委派给 Codex、在界面展示过程、全部写入会话日志可回放。
  • 对应情况：38 个点中，System3 有等价或更强实现的 5 个，部分覆盖 14 个，没有的 19 个；没有的多为记忆、Hive 多代理和浏览器这类我们没走的方向。
  • System3 独有：多供应商模型分档路由并验证实际使用的模型、线路健康、外部代理委派（进度、补充说明、停止、交接包）、隐私准入、过程提示上界面。
  • 最该借鉴的不是点数，而是骨架：统一的判定规格、off/shadow/active 三种模式、判定账本。今天线上发现的两处误报，正好说明确定性规则需要 Jev 这类语义判断来补。

#mu 判定点mu 做什么System3 / DSH 对应状态差异与实证
用户输入
1input.preflight一次 10 题：轮次类型、是否需澄清、是否先规划、复杂度打分；给主模型一行提示，可调 thinking 等级入口路由：Jev 在 Flash / Pro / GPT-5.6 / GPT-6 / Codex 委派 / 弃权之间选择，真正切换本轮模型；明确说“交给 codex”时不问 Jev更强mu 只给提示，System3 真的换模型并核对实际回答的模型。线上：路由决策 0.34–0.97 秒；Flash、Pro、GPT-5.6 各一轮路由正确。缺少 mu 的“需澄清 / 先规划”提示
2task.frame判断是新任务、约束、纠错还是子目标；有变化时由 LLM 改写任务框架（目标、原话约束、验收项）交接包只在委派时识别更早的约束并原文转交部分没有持续维护的任务框架。交接包实测：6 段标注对话召回率和精确率 1.0，单次约 0.3–0.9 秒
3input.interjection代理运行中收到消息，判断是纠错、补充还是旁支问题，改投为 steer 或 followUp委派运行中的“补充说明”由用户在卡片上主动发送，送达 Codex；主循环的插队方式由用户选择部分无自动分类。补充说明线上 0.6–1.2 秒送达，并在结果里复述给主模型
4skills.disclosure首条消息时隐藏无关技能，会话内固定以保缓存Skill 选择：Jev 选出一个最合适的技能并注入正文等价（方向相反）mu 做减法（藏），System3 做加法（选一个注入）。都有隐私和大小上限
5capability.disclosure按需开启工具包或 MCP，判为需要才启动进程无无DSH 工具在 profile 里静态配置

System3 有、mu 没有的能力

能力做了什么线上实证
多供应商分档路由同一会话内按输入切换 DeepSeek 官方 Flash / Pro、GPT-5.6 / GPT-6 中转；记录建议、采纳、实际回答三个事实会话日志显示实际回答者与路由一致：Flash 3 秒、Pro 11 秒、GPT-5.6 169 秒
线路健康测每条线路的首字延迟、输出速度、错误率，降级线路自动不参与选择，并写明原因阈值来自 prd 日志；本周尚未触发降级
外部代理委派全过程委派 Codex 后有进度卡、启动/停滞/超时提醒、运行中补充说明、停止；补充说明在结果里复述给主模型；输入框标明“已交给 codex”交接包 290 毫秒；Codex 56 秒；函数名遵守 snake_case、未建 README；8 个测试通过
隐私准入每次 Jev 请求和每条路由都按数据类别与执行位置准入单元测试覆盖拒绝路径
可回放与可审计所有判定是会话事件：完整请求、响应、结果，刷新或回放不再调用模型；进入模型的内容都能从日志重建每个新事件都有持久化类型变更记录

判定内核对比

维度mu（kyrn-judge）System3
判定规格统一 defineDecision：题型、带逃生选项的封闭选项、policy、fallback、对缓存的影响、延迟档位每个功能各自实现，没有统一规格 缺
运行模式每个点 off / shadow / active，默认 active过程监督有 observe / advise；入口路由和交接包只有开或关；另有独立的 shadowDecision API 部分
账本每次判定写一条记录（状态只存摘要），可在命令行和桌面端查看会话事件，保存完整请求和响应，投影到界面 更严格
判定后端Jev / 本地 Laya / 普通 LLM 等级联，前一级不确定才交给下一级只用 Jev，失败走确定性回退 单一
阈值是非题 ≥0.8 算是、≤0.2 算否；选择题 ≥0.6 且必须有逃生选项入口路由置信度 ≥0.8 且有弃权项；交接包 ≥0.3（依据实测数据定）
批量工具输出 16 块合一次请求；超过 32 题自动拆分交接包一次请求最多 16 题
连接与延迟HTTP/2 保活，每 50 秒 ping；热连接单题 0.31 秒、16 块 0.44 秒（作者一次性实测，无可重跑脚本）keepWarm 每 2 秒一次、轮后 5 分钟内；线上路由决策 0.34–0.97 秒，交接包 0.29–0.92 秒（prd 会话日志）
效果证据测试日志折叠 51%；按目标裁剪 40%、必需行零丢失；作者回测承认 tool.admission 零裁剪、净收益未证明；无与 Claude Code / Codex 的端到端对比入口路由三组对照与隐藏测试；交接包 6 段标注对话；委派门槛对照（委派准确率无提升、耗时 4–13 倍）；线上浏览器验收

建议：按证据而不是按点数补齐

先做（直接对应已发生的问题）

  1. 约束拦截（对应 tool.constraint）。交接包已经能识别用户约束，把它扩展到修改类工具调用前检查，违背就拦截并引用原话。直接防住“删掉用户要求保留的文件”这类事故。
  2. 用 Jev 复核过程监督（对应 turn.completion / turn.drift）。确定性规则今天线上误报两次；在规则触发时再问 Jev 一道是非题（约 0.3 秒），只有确认才提醒，误报会明显下降。
  3. 统一判定规格加 shadow 模式。把入口路由、Skill 选择、交接包、过程监督收拢到一套规格：题目、阈值、回退、模式、会话事件。新增判定点的成本会大幅降低，也便于先 shadow 量化再开启。

可以晚做或不做

  • 测试日志无损折叠：不需要模型，收益明确（mu 实测 51%），可作为小改动随时加。
  • 运行中消息自动分类（input.interjection）：现在由用户手动选择，体验够用。
  • 工具输出语义裁剪（tool.admission）：mu 自己的回测显示成本高、收益未证明，不建议照搬。
  • 记忆系统、Hive、浏览器判定：方向不同，演示前不建议展开。
