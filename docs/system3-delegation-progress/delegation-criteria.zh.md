# System3 委派判断依据：除了时间还看什么

[English](delegation-criteria.md) | 中文

## 摘要

Codex 和 Claude Code 只承接价值最高、最复杂、最长程的工作。时间只是四类因素中的一项成本，四类因素是收益、成本、风险和可控性。只有“成功率提升 × 任务价值”大于时间、费用、注意力和风险之和时，委派才划算。目前的实测数据只覆盖时间；[委派门槛校准](delegation-calibration.zh.md)没有发现委派提高成功率的任务。决策规则以[决策方法](decision-method.zh.md#entry-decisions)为准。

<a id="benefit"></a>
## 收益

| 维度 | 适合委派的情形 | 识别信号 |
| --- | --- | --- |
| 成功率提升 | 自有模型大概率做不出来，Codex 能做出来；这是委派的根本理由 | 只能靠评测得出；校准任务中没有一道需要委派 |
| 工程闭环 | 需要反复改代码、运行、看报错、再修改，要装依赖、跑构建或迁移 | 请求要求一直做到测试或构建通过；工作区里有测试或构建命令 |
| 探索 | 根因未知，需要在仓库中查证，例如偶发失败、性能问题或陌生代码库 | 请求问的是为什么、从哪里来，而不是把 X 改成 Y |
| 上下文隔离 | 读大量文件会撑满主会话的上下文，拖累后续轮次 | 代码库规模和涉及的模块数，可从工作区统计 |
| 并行 | 用户可以同时做别的事，回来再验收结果 | 任务独立、规格明确，运行中很少需要交互 |

<a id="cost"></a>
## 成本

| 维度 | 说明 |
| --- | --- |
| 时间 | 校准中委派的耗时是自己做的 4 到 13 倍；Codex 第一个步骤之前就要 20 秒以上 |
| 费用与 token | Codex 的用量尚未上报，记为未知而不是零 |
| 注意力 | 看进度、处理提醒、验收结果都消耗用户注意力；任务越短，这笔交换越不划算 |
| 交接损失 | 交出去的只有任务文本，主会话中已经商定的约束和偏好可能丢失 |

<a id="risk"></a>
## 风险

| 维度 | 说明 |
| --- | --- |
| 影响范围 | 生产代码、数据库迁移、删除操作需要沙箱、审批和交付前核验 |
| 隐私 | Codex 调用外部模型；不能出网的数据分级禁止委派，这是硬规则 |
| 权限 | 工作区写入、联网或凭据必须得到部署策略允许 |
| 可恢复性 | 处于版本控制下的改动风险低；不可逆的外部操作风险高 |

<a id="control"></a>
## 可控性

| 维度 | 说明 |
| --- | --- |
| 可验证性 | 长时间自主运行需要明确的验收检查，例如测试、构建或可复现的检查；目标模糊的任务不适合 |
| 规格清晰度 | 需要反复澄清的任务，应先在主会话中澄清并写下验收标准，再委派 |
| 中途纠偏 | 能接收运行中输入、能被停止的执行者更适合长任务；目前只有 Codex 支持运行中输入 |

<a id="decision-layers"></a>
## 决策分层

| 层 | 决定什么 | 谁来决定 |
| --- | --- | --- |
| 硬规则 | 不能出网的数据分级、权限不足，以及作为前置条件的工作区事实（代码库规模、是否有测试或构建命令） | System3 的确定性准入，不经过模型 |
| 语义判断 | 请求中可见的工程闭环、探索性和跨模块规模，即候选描述所写的条件 | Jev |
| 明确意图 | 请求文本看不出的价值和风险偏好：“交给 Codex”就委派，“你直接改”就不委派 | 用户 |

<a id="open-questions"></a>
## 待解决问题

- 成功率提升尚未测得，需要 Flash 做不出来的长程任务。
- 上下文隔离可以用主会话 token 增长和后续轮次质量来衡量，应纳入下一轮对照。
- 隐私和工作区规模应从 Jev 的判断改为硬规则。
- 对复杂但模糊的请求，先在主会话中澄清并写下验收标准再委派，也能减少交接损失。
