把 agent-jev-pilot 的前三项落到 System3

pilot 的前三项是上下文筛选、目标与进度裁判（含卡住监督）、中转线路监控。本稿把三项映射到 System3 已有的扩展点，给出范围、接口、测试与验收标准。确认后再开发。

总览

三项功能的落点

pilot 能力System3 形态接入点Jev 的角色估算
1 · 上下文筛选委派交接包：委派时把主会话里用户定下的约束带给 Codex委派指令的 pre-step 注入（delegation.ts）；工具参数按设计不可改写逐条判断早先的用户消息是“必须原文带上”还是“只列标题”1 天
2 · 目标与进度裁判 + 卡住监督过程监督：确定性卡住规则 + 交付前验收证据检查tools/post-execute（主循环）、Codex 活动新增失败结果、轮次结束检查第一版只用规则；Jev 只在规则拿不准时给建议，放到第二版1.5 天
3 · 中转线路监控线路健康：测首字延迟与生成速度，线路变慢时避开被动观察真实请求 + 空闲时小探测（ctx.llm.stream）；入口路由候选过滤不参与；健康状态是硬规则输入0.5–1 天
1 · 委派交接包

用户之前说过的约束，委派时一起带给 Codex

要解决的问题：Codex 只看到主模型写的那段任务描述，看不到主会话历史。用户早先说过的“不要改 README”“函数名用 snake_case”“先保证测试通过”，经常在交接时丢失。

  1. 规则先行：当前这条输入原文必带；最近 N 条（默认 12）用户消息进入候选；更早的只列标题。
  2. Jev 逐条判断：一次请求、多个问题，每条候选回答“约束：必须原文带上 / 背景：只列标题 / 无关”。超时或不可用时全部按“只列标题”处理（不阻塞委派）。
  3. 写进委派指令：注入的那条 system3-delegation 指令末尾附交接包，并要求主模型把“必须遵守的约束”原文写进给 Codex 的任务里。
  4. 事实记录：新增 system3/handoff-pack 事件，记录候选消息序号、Jev 请求与回答、最终分类；指令消息本身已在日志里，满足“进入模型的内容可从日志重建”。
[System3 交接包]
必须遵守的约束（用户原话）：
- 第 3 条：函数名一律用 snake_case
- 第 5 条：不要改 README
其他背景（可在主会话查阅）：
- 第 1 条：项目介绍……（标题）

验收：新增 6 道“约束题”（早先消息给出约束，之后说“交给 Codex 做”），隐藏测试检查约束是否被遵守；有交接包 vs 无交接包各跑 2 次，约束遵守率提升且耗时增加不超过 5 秒。

2 · 过程监督

自动发现卡住，交付前确认有验收证据

卡住规则（来自 pilot，确定性）

规则判定动作
同一错误重复同一工具、同一错误码或规整后的错误摘要，在本轮出现 ≥ 2 次给主模型一条提示：先换思路或向用户确认；界面显示提醒
反复失败本轮失败的工具调用累计 ≥ 3 次建议请求用户输入
没有新进展连续 K 步（默认 6）没有成功的写文件、成功的命令或新的有效结果建议换策略
Codex 内部反复失败委派运行中命令失败 ≥ 3 次（Codex 活动新增 outcome: failed）委派提醒新增“反复失败”一类，附补充说明与停止
缺少验收证据本轮改过文件或完成了委派，但之后没有成功的测试 / 构建命令轮次结束前提示主模型先验证；界面不显示“已复核”，改为“未见验收证据”
  • 介入方式：主循环用 tools/post-execute 的附加上下文给主模型提示（不阻断执行）；同时写入 system3/supervision 事件，进度卡片和状态栏据此显示。
  • 两种模式：observe 只记录不提示，advise 记录并提示；部署先用 advise。规则命中的次数和误报都可以从日志统计。
  • 与现有能力的关系：现有的启动过慢 / 停滞 / 超时是按时间判断；这里补上按内容判断（错误重复、无进展、缺证据）。guard/repeat-tool-reminder 只管完全相同的重复调用，保留不动。

验收：用固定的失败脚本复现三种卡住情形，规则在第 2 / 3 / K 步准确命中；正常任务（对照题库 10 题）误报为 0；“缺少验收证据”在去掉验证步骤的回放里命中。

3 · 线路健康

线路变慢时提醒，必要时自动换一档

  • 被动观察（零成本）：每次真实请求记录该线路的首字延迟、每秒输出 token 数、是否出错，保留最近 20 次。
  • 主动探测（只在空闲时）：某条线路超过 30 分钟没有真实请求时，发一个极小请求（最多 32 个 token）测一次。
  • 判定（阈值可配置）：最近样本的首字延迟中位数超过 ttftMs，或生成速度低于 minTokensPerSecond，或错误率超过 maxErrorRate，则标记为“变慢”。
  • 路由动作：入口路由把“变慢”的候选从可选集合中排除（所有候选都变慢时不排除），决策记录写明被排除的候选和原因；路由说明附一句“GPT-5.6 线路较慢，已改由 Pro 处理”。
  • 状态存放：内存中保存，重启后重新积累；第二版再考虑持久化。

验收：用可控的假线路（注入延迟）验证标记与恢复；线上记录各档真实指标，展示在执行详情里。GPT-5.6 中转每秒约 18 token 的实测值应被识别为“变慢”（以配置阈值为准）。

共同约束

三项都遵守的规则

  • 规则先行，失败即回退：任一检查超时或出错都不阻塞主流程。
  • 新事件都走持久化类型变更记录；进入模型的内容都能从日志重建。
  • 每项都有单元测试、组合测试和一次线上验收，改动文件覆盖率 100%。
  • 功能开关和阈值都在部署配置里，不写死在代码里。
需要你决定

开工前的三个问题

顺序：建议按 2 → 3 → 1 开发。过程监督最能体现“管得住”，最适合 8 号演示；线路健康改动最小、见效快；交接包需要新题库做对照，放最后。也可以严格按 1 → 2 → 3。
过程监督的力度：第一版只“提示”（主模型和界面都能看到），不自动停止或换执行者。自动介入等误报率测出来再开。
线路变慢时是否自动换档：建议自动避开并在路由说明里写明原因；也可以只提醒不换。
