委派补充说明（mid-run steer）

System3 过程掌控 · 2026-10-02 · 待审批，未开始实现

1. 目标

Codex 跑偏或超时时，用户现在只能“继续等待”或“停止”。停止会丢掉已完成的工作。本设计在进度卡上增加第三个动作“补充说明”：用户输入一句话，直接注入 Codex 当前正在执行的 turn，Codex 在下一步就能读到并纠偏，不中断、不重启。

  • 入口：进度卡的提醒条（超时、停滞）和卡片底部，只在委派运行中显示。
  • 反馈：提交后 1 秒内在卡片上显示“已补充：…”，失败时用 toast 说明原因并保留输入。
  • 边界：只支持声明了该能力的 provider（第一版只有 Codex）；不支持时不显示入口。

2. 用户流程

3. 架构

sequenceDiagram
  participant UI as System3 进度卡
  participant SC as session-controller client
  participant SS as SubagentService（host）
  participant R as SubagentRun（Codex）
  participant CX as codex app-server
  participant LOG as 父 Session 日志
  UI->>SC: session.steerSubagent(runId, text)
  SC->>SS: remote subagents.steerByParent(runId, parentSessionId, text)
  SS->>SS: 查 live run 登记表，校验 parentSessionId
  SS->>R: run.steer([{type:text}], signal)
  R->>CX: turn/steer {threadId, expectedTurnId, input}
  CX-->>R: {turnId}
  R-->>SS: resolved
  SS->>LOG: append subagent/steer {runId, content}
  SS-->>SC: {accepted: true}
  LOG-->>UI: projection subagentRun.steers → “已补充：…”

要点：

  • 能力挂在 run 上，不挂在 provider 上：SubagentRun.steer? 存在即表示支持，与现有 prepareContinuable? 的“方法存在即能力”惯例一致。
  • SubagentService 新增 live run 登记表：只在 subagent/start 与 subagent/end 之间登记 runId → {parentSessionId, run}，由已有的 observeRun 维护；不改变 run 由调用方持有的所有权约定。
  • 先提交、后记录：provider 接受后才写 subagent/steer 事件（“Publish state only at its commit point”）。Codex 拒绝（turn 已结束、expectedTurnId 不匹配）时不写事件，返回错误。
  • 可见 ⟺ 已记录：补充说明会进入 Codex 模型的输入，所以必须写进父 Session。事件对父模型不可见（见第 6 节问题 1）。

5. 接口约定

// dsh-subagent types.ts
interface SubagentRun {
  /** 可选：把补充输入注入正在执行的 turn。存在即支持。
   *  resolve = 子 agent 已接受；reject = 运行已不接受输入（已结束 / turn 切换）。 */
  steer?(content: readonly ContentBlock[], signal: AbortSignal): Promise<void>
}

// SessionEventMap（父 Session，ignorable: false，不进入父模型上下文）
'subagent/steer': { version: 1; runId: SessionId; provider: string; content: ContentBlock[] }

// remote
steerByParent(runId: SessionId, parentSessionId: SessionId, text: string): { accepted: true }
// 错误：gateway/bad-request（空文本或超过 2000 字符）
//      subagent/unauthorized（run 不属于该父会话）
//      subagent/not-steerable（run 不存在、已结束、provider 不支持或拒绝）

6. 需要你决定的问题

问题 1：父模型要不要知道用户补充过什么？
建议第一版不让父模型看到：事件只用于审计和界面。父模型交付前会重跑测试核验，仍依据原任务。代价是父模型的总结可能漏掉“用户中途改了要求”。后续可以把补充说明附在工具结果末尾，从已记录的事件推导，不需要新的事实。
问题 2：Claude Code 是否同期支持？
建议不同期。Claude Agent SDK 需要改成流式输入（AsyncIterable prompt）才能中途注入，改动面更大，而且目前还没有 Claude Code 委派候选。接口按可选能力设计，以后补上即可。

7. 测试计划

  • 单元：登记表的生命周期（start 登记、end 移除、HMR dispose 清空）；鉴权（父会话不匹配时拒绝）；provider 不支持或拒绝时不写事件；文本长度上下限。
  • Codex wire：fixture app-server 收到的 turn/steer 参数正确；turn 结束后的 steer 被拒绝。
  • 投影与 UI：steers 推导、steerable 开关；client spec 覆盖输入、成功、失败 toast。
  • Session 格式：persistence-change 记录、Python 与 TS SDK 期望输出、snapshot。
  • 真实验证：Web 中委派 Codex，运行中补充“改用 xxx 命名”，确认 Codex 后续步骤采纳，卡片显示“已补充”，刷新后仍在。

8. 不做的事

  • 不让 Jev 自动生成补充说明（自动纠偏属于卡住判定规则，后续单独设计）。
  • 不支持补充图片或附件，第一版只支持文本。
  • 不改主 agent-loop。
