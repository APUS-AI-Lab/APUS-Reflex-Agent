# System3 决策方法：入口决策、过程掌控与评测校准

[English](decision-method.md) | 中文

## 摘要

System3 的核心是两项能力：入口决策回答“这件事交给谁”，过程掌控回答“交出去以后怎么不失控”。两者共用一个底座：每次决策和结果都写成 Session 事实，再回流为评测集。本文记录这套方法的规则、已测数据和未证明的部分。实现状态以[统一架构](../feat-system3-g1/architecture.html)为准。

<a id="shared-principles"></a>
## 共同原则

- 规则先行：能由确定性规则判定的，先由规则判定；Jev 只在规则留下的合法候选中选择或弃权，不能推翻硬条件。
- 失败即回基线：Jev 超时、不可用、弃权或置信度不足时，回到 baseline，迟到的结果不生效。
- 建议、采用、实际执行、结果核验是四个不同的事实，分别记录，不互相代替。
- 速度是体验的一部分：用户在判断完成的瞬间就应看到说明，等待要有理由。
- 收益要用对照证明：没有三组对照数据之前，不声称 Jev 带来收益。

<a id="entry-decisions"></a>
## 入口决策

入口在模型启动之前决定输入交给谁。去向分三类：模型档位、本机模型、专业 Agent 委派。每档只放一个模型，档位之间拉开能力和成本差距，否则判断再准也抵不过它自身的延迟。

| 层 | 做什么 | 谁做 |
|---|---|---|
| ① 硬规则 | 人工固定模型时不路由；候选必须支持会话中出现过的输入模态（出现过图片才要求读图）；上下文容量与推理档位校验；委派候选只在 provider 已注册、工具对当前 Agent 可见时提供 | Session Controller 与 System3 准入 |
| ② 隐私 | 判断输入能否出网；不能出网时只保留本机候选，也不请求网络上的 Jev | 本机规则或本机模型（待实现） |
| ③ 选去向 | Jev 在剩余候选中选一个或弃权 | Jev 9B |
| ④ 后续消息 | Jev 弃权或置信度不足时沿用上一轮的模型路由；provider 失败仍回 baseline；委派不沿用 | System3 入口路由 |
| ⑤ 采用与说明 | 模型类切换本轮模型；委派类保留模型并注入一条指令，由主模型决定是否调用工具；决策记录到达即显示提前写好的路由标签 | Harness 与前端 |

**速度规则：**

- Jev 在热连接上判断约 0.45 秒，冷连接多约 1.5 秒。用长连接（HTTP/2、长 keep-alive）并在每轮结束后的一段时间内发轻量心跳保温。
- 判断完成即显示标签，例如“已判断：复杂专业任务 · GPT-5.6 Sol”；新提交等待判断时，不显示上一条输入的路由。
- 只有服务器实测 p95 仍明显拖慢轻问题时，才考虑“Flash 与 Jev 并行启动”或调整 Jev 的网络路径。

**委派规则：**

- 委派是入口候选的一类，不是单独的判断逻辑。
- 候选描述要写明适用的任务规模；单文件小修改不应委派（见[尚未证明](#not-yet-proven)）。
- 外部 Agent 不可用时，入口决策回落到自有模型。

<a id="process-control"></a>
## 过程掌控

交出去以后，过程掌控负责让进度可见、在卡住时介入、在交付前核验。

**进度可见：**

- 子 agent 的步骤以类别和阶段上报（命令、改文件、工具、消息、推理），不携带内容、路径、工具输入或凭据。
- 实时事件供 AG-UI 等直连前端使用；父会话中写入节流后的持久进度快照，Web 与 Desktop 由此显示进度卡片，刷新后可恢复。
- 子 agent 开始后可能 20 秒以上才有第一个步骤，界面要在此之前就显示“已开始”。

**卡住判定（确定性硬规则，来自 agent-jev-pilot 的验证经验）：**

| 条件 | 动作 |
|---|---|
| 同一错误出现 2 次及以上，或总尝试 3 次及以上 | 请求用户输入 |
| 没有产生新证据 | 更换策略或执行者 |
| 步数或时间超出预算且无进展 | 在继续、请求输入、更换执行者之间选择 |
| 缺少验收事实 | 不判定完成 |

Jev 只在这些规则之上给建议；规则判定的结果优先。真实测试中曾出现模型盲目搜索文件 6 分 11 秒后才询问用户的情况，这正是这些规则要覆盖的场景。

**交接：** 更换执行者时，用可恢复的上下文包交接：保留原文的片段与只留索引的片段分开，原文带 hash，可回读。

**交付前核验：** 主模型或独立检查必须复核委派结果（例如重跑测试）后再回复用户；没有核验证据时不显示“已完成”。

<a id="evaluation-and-calibration"></a>
## 评测与校准

评测方法来自 agent-jev-pilot 的校准流程，用来防止“工程跑通、价值未证实”。

- 三组冻结对照：固定基线（例如始终用 Pro，或始终不委派）、确定性规则、Jev。候选、材料、权限和预算三组相同。
- 独立验收：结果由与被测系统无关的检查判定，不以决策日志正确代替任务完成。
- 只比较完整配对：一组失败或缺数据时，该任务不计入收益比较。
- 证据不足不判通过；用量未知不记为 0。
- 指标：决策与标签一致率、实际回答模型一致率、弃权率、后续消息误路由率、延迟 p50/p95、任务通过率、每成功任务的总耗时与总成本。
- 弃权、超时、错误完成和关键证据遗漏单列。
- 标签由人判定时要说明，对抗输入要单列，规则组如果是对照着测试集写的，要注明其结果是乐观上界。

<a id="fact-foundation"></a>
## 事实底座

每次决策写入 Session 事件，界面和评测都从这些事实推导：

| 事实 | 记录 |
|---|---|
| 建议 | `system3/entry-decision`：完整 Jev 请求与响应、outcome、选中或沿用的候选与标签、委派目标、耗时 |
| 采用 | `model/automatic-selection`；委派时为来源 `system3-delegation` 的指令消息 |
| 实际执行 | 实际回答的模型；委派工具调用 |
| 进度 | 父会话的委派进度快照 |
| 结果 | 产物与独立检查结果 |

<a id="measured-data"></a>
## 已测数据

均为 2026-10-02 在本机对真实 Jev 和 Fidoo 代理的测量，服务器上尚未测量。

| 项目 | 结果 |
|---|---|
| 两档入口评测（50 条） | 决策与标签一致 48/50；后续消息 12 条中 11 条弃权 |
| 四档入口评测（30 条） | 29/30 一致；唯一不一致是一道严格证明题置信度 0.79 低于阈值 |
| Jev 热连接延迟 | 0.44–0.50 秒；low 与 high 档相差很小 |
| 产品内入口判断 | 保温前约 2 秒；保温后 0.49 / 0.86 / 1.22 / 1.25 秒 |
| 委派端到端 | 编码任务 0.69 秒判为委派 Codex；指令注入、工具调用、修复和补测试都完成，测试 5/5 通过，总用时 108 秒 |
| 真实用户流程 | 轻问题 4.3 秒；重设计题由 GPT-5.6 Sol 回答 21 秒；“继续”沿用上一轮模型 |

<a id="not-yet-proven"></a>
## 尚未证明

- 高档模型在对应任务上是否答得更好，以及每成功任务的成本：评测只给路由决策打分。
- 委派何时划算：[委派门槛校准](delegation-calibration.zh.md)中 Flash 自己做与总是委派的隐藏测试都是 20 / 20 通过，耗时中位数分别为 36 秒和 203 秒；Codex 候选描述现在只委派仓库级工作，但测过的任务没有一道需要委派，委派开始有帮助的门槛仍需用 Flash 做不出来的任务测量。
- 编码任务的档位路由：Jev 会把部分编码任务交给 Pro 或 GPT-5.6 Sol，在校准任务上它们比 Flash 慢，且没有测得质量收益。
- 服务器上的入口延迟分布。
- 本机模型与逐条隐私判断：尚未实现。
- Skill 自动选择在真实用户环境中的效果：用户级目录有 115 个 Skill，超过 32 个的上限，自动选择目前不会触发；需要先粗筛再由 Jev 精选。
- agent-jev-pilot 的数据显示，Jev 做上下文取舍没有带来净收益，因此不把上下文取舍作为 System3 的 Jev 决策点。
