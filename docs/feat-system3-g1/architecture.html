01

两项核心能力：入口决策与过程掌控

System3 希望让用户一句话开始工作，在过程中少走弯路，回来时知道接着哪里做。产品的核心是两项能力：入口决策回答“这件事交给谁”，过程掌控回答“交出去以后怎么不失控”。Jev 在有界节点提出选择；Harness 把合法选择变成实际模型请求、委派和工具执行，并保存可恢复的事实。

核心能力回答的问题包含现状
一、入口决策这件事交给谁在同一次决策里选择去向：模型档位（Flash / Pro / GPT-5.6 Sol / GPT-6 Sol）、本机模型（隐私数据）、专业 Agent（Codex / Claude Code）。后续消息沿用上一轮去向；判断完成即显示提前写好的路由说明。四档模型与沿用已实测；委派候选与本机模型目标接入
二、过程掌控交出去以后怎么不失控委派进度实时可见；执行卡住或跑偏时在继续、请求输入、更换执行者之间选择；结果经核验后交付。委派进度实时事件已实测；父会话进度卡片、收敛监督、结果核验目标接入

两项能力共用一个底座：每次决策与结果（建议、采用、实际执行、产物检查）都写入 Session 事实，回流为评测集与 Jev 训练数据。委派给 Codex 或 Claude Code 是入口决策的一类候选，不是单独的判断逻辑，只承接价值最高、最复杂、最长程的仓库级工作，自有模型一次对话能完成的不委派；自研编码 Agent 与多 Agent 工作台不属于核心，分别复用外部 Agent 与经 ACP 接入的现成工作台。外部 Agent 不可用时，入口决策回落到自有模型。

02

三层智能，表达为同一个任务体验

默认界面让用户能说出四件事：现在做什么、已经得到什么、还有什么未验证、我能怎样接管。技术细节放进展开层，重要方法变化留下可追溯记录。

入口智能

希望感受到：我一提交就得到回应；系统选择合适方法，缺关键资料时只问影响执行的问题。

当前落地：本地提交反馈、合格文本入口的自动选模、人工固定与恢复自动。澄清、附件及更多入口策略仍需接入。入口判断只读取当前这一条文本，不读取会话历史；指代前文的后续消息由 Jev 弃权（两组评测 18 条中 17 条），再由 retainOnAbstain 沿用上一轮选定的模型。部署配置的候选为四档网络模型：DeepSeek Flash / Pro、GPT-5.6 Sol、GPT-6 Sol。

过程智能

希望感受到：系统沿进展换方法，记住约束，遇错会先查证据，需要时让专家接力。

当前落地：自动选择并注入一个专业 Skill。取证、约束保护、压缩和专家策略还未形成 System3 闭环。

体感智能

希望感受到：等待中有清楚变化，成果逐步出现；离开再回来，状态可信、操作可达。

当前落地：已收到 / 决策 / 运行反馈，展开查看建议、采用、响应及 Skill 注入。完整任务、上下文与验收工作台仍是目标。

目标工作台：一条主线，按需展开

主区 · 工作与成果输入、原生 Conversation、工具结果、产物与下一步；任务回执就地更新。
上下文 · 实际使用已注入的方法、保留约束、来源原文、排除范围与数据去向。
目标 · 缺项与恢复阶段、检查结果、预算、等待原因；普通任务不强加长期 Goal。
记录 · 建议到结果默认简洁；展开核对建议、采用、请求、响应、证据和控制结算。

体感速度由真实变化支撑

  • 输入提交立即回显，Host 接收与准入分开报告；首次确认、首个有效成果和总完成时间分别测量。
  • 普通路由保持一条紧凑状态；Skill 加入、失败取证、专家交接、产物通过检查时才留下有意义的变化记录。
  • 成果显示草稿 / 待检查 / 已验证；未知进度不显示百分比。流式输出保持稳定布局，遵循减少动态效果偏好。
  • 停止请求已接纳与所有工作已收尾分别显示；恢复后先读记录，不用旧状态制造“正在运行”。
  • 入口判断的实测耗时是两次单独观测：Desktop 1403ms、服务器 933ms；Skill 判断 311ms 与 285ms。配置的入口总截止为 15 秒，判断结束前输入不准入。入口评测集 50 条的分布为 p50 467ms、p95 1211ms，据此确定目标预算。
待决策 · 工作台归属：任务工作台可以继续由自有 client-ui 扩展实现，也可以让 Harness 经原生 ACP profile 作为运行时接入已有的多 Agent 工作台。本页按自有扩展描述；决策前只做决策事实与委派进度两类视图，不扩大工作台范围。

03

Jev × Harness：当前融合与完整目标分别看

每个原生 Agent 的回合由自己的执行 owner 管理；Host 复用同一执行机制，多实例各有 Session。Jev 是其中的有界判断服务，System2 负责生成与工具请求；UI 消费事实，原生服务负责采用与结算。

能力演进：单模型执行 → 多模型 / 多能力协作 → 多智能体编排总管。N 是参数化执行对象数量，不指定拓扑或已验收并发数；采用、权限、取消、持久记录与可用预算控制由原生 runtime 落实，完整任务预算仍属目标。

展开原生 AgentLoop 流程细节
闭环分支与源码依据
  • 入口 Jev 只在自动选模且条件适用时请求；固定模型跳过。自动 Skill 在原生 pre-step 的 surviving 纯文本用户输入符合条件时请求，不是每 token 或每轮必调。
  • 工具判断取决于已结算的 assistant 消息；有工具请求交给原生调度，concluded 可以结束，否则结果进入后续上下文。没有工具只表示该 step 可以结束，不证明业务任务验收通过。
  • 待续判断抽象 step 结果、nextStep 和 agent/turn-stopping；回边进入下一次上下文组装 / pre-step，不返回入口选模。
  • request-error 处理器仅在返回 retry 时重试模型请求；不重复入口或 Skill。pre-step reject 为 blocked，max-tokens 保留截断结果。
  • 活动步骤合作取消与未恢复错误通过原生 turn/end 结算；取消不承诺撤销已经发生的外部动作。入口取消或准入失败尚未开启回合，不能补造 turn/end。
  • 模型可见输入和响应、工具结果按实际阶段写入 Session；图中记录箭头表示存储关系，不是第二个执行 owner。完成、阻塞 / 截断、取消、失败均是回合状态；独立成果验收在图外。

源码：AgentLoop · 工具调度 · 入口 router · Skill selector。虚线未来控制点仅为设计占位；当前没有新增通用过程控制器或内置万能回合预算。

融合要验证什么：Jev 的选择实际改变下一步方法；推理模型与工具结果反馈到后续判断；权限、取消和验收始终由原生 Harness 执行。只更换模型名或显示决策状态，不足以证明这一闭环。
当前发布 · 两套实例，各自运行原生闭环

04

从一句话到结果：六条可切换的穿透链路

切换场景查看调用者、实际 owner、日志事实与用户体感。前三条说明当前能力，后三条说明目标设计；此演示不连接后端、不调用模型、不执行工具。

输入 requestId→建议 / 原生采用→对应 turn / step→真实模型内容 / Skill 消息→工具与产物检查

代表性实测：Desktop 自动入口约 1.403 秒、Skill 约 311 毫秒；服务器入口约 933 毫秒后低置信度弃权，Skill 约 285 毫秒。均为单次公开任务记录，不是 p50/p95、SLA 或总体提速证明。UI 接收 5 毫秒、决策提示 15 毫秒也只是一条观察。

05

接口与事件：建议、采用和实际使用各有事实

使用原生 Session Remote、follow 流和 projection；不新增前端直调 Jev 的接口，不把设计字段写成已发布 API。

当前 API / 投影职责必须保留的语义

session.cancel / updateQueue / follow 与历史读取停止当前回合、管理队列、订阅与恢复普通 cancel 保留 pending inbox；不能代表所有未来任务、专家和提醒均已停止。

委派进度、提醒与补充说明 已实测

委派给 Codex 或 Claude Code 后，进度、提醒与用户的补充说明都按下表记录。子 agent 的内容（命令、路径、工具输入与结果）不离开 Host，这些记录也不进入父模型请求。

层记录语义与约束
provider 活动live 事件 subagent/activity，不持久化run id、provider、步骤类别与阶段；子 agent 自己写给人的进度消息作为 note（上限 200 字符）。只在 start 与 end 之间发布；Codex 与 Claude Code provider 上报，AG-UI 直接转发。
父会话进度父 Session 持久事件 system3/delegation-progress开始与结束各写一次，运行中按 intervalMs 节流；含步骤计数、当前步骤、最近步骤时间、note 与 steerable。Web 与 Desktop 的进度卡片由投影 subagentRun 得到，刷新后可恢复。
提醒父 Session 持久事件 system3/delegation-alert配置 monitor 后写入：启动过慢（startupMs 内没有第一个步骤）、停滞（每次超过 stallMs 没有新步骤）、超时（每到 overtimeMs 整数倍）。卡片提供继续等待、补充说明和停止。
补充说明Remote subagents.steerByParent；父 Session 持久事件 subagent/steer只送达实现了 SubagentRun.steer 的运行中 one-shot 运行，目前是 Codex（turn/steer，以当前 turn id 作为前置条件）。子 agent 接受后才写事件；拒绝、已结束或其他父会话的运行不留记录。文本最长 2000 字符；运行结束时委派工具在返回给主模型的结果末尾复述已接受的补充要求，让主模型复核时一并核对。卡片显示最近三条已补充的文本。
委派建议system3/entry-decision 与来源为 system3-delegation 的指令消息委派是入口候选的一类；pre-step 注入一条指令，是否调用工具由主模型决定。候选只包含已注册的 provider 和当前 Agent 可见的工具；建议、注入与实际工具调用分别记录。

06

记住什么、在哪里保存、回来怎样接着做

执行和模型可见输入以所属 Session 日志为依据；文件和原生业务存储由各自服务保存。Desktop 与服务器的 Session、工作区、凭据相互独立，当前没有已验收的自动同步。

Model-as-a-Harness（MAAH）· 后续研究命题

让小脑模型学习 Harness 的自适应控制策略：何时选方法、补证据、交接专家、继续或弃权。大脑模型负责生成与复杂规划；原生 Harness 保留准入、采用、执行、权限、持久化、取消和验收责任。模型控制建议进入原生执行，不替代这些确定性机制。

分三个阶段验收：设计时用模型帮助优化 Harness 代码与规则；运行时从有限合法策略中控制方法与下一步；执行后用任务轨迹和独立成果评分改进策略。代码优化、在线采用与轨迹学习分别交付，当前不声称已完成自动训练。执行后学习的数据前置条件尚未满足：shadowDecision 在产品运行路径中没有调用方，其记录按隐私设计不保存任务原文；从执行轨迹导出 Jev 训练数据的管道不存在。

这是本项目拟研究的产品定位，不声明术语首创或已证新颖性，尚未完成全过程训练或效果验证。近期聚焦执行时有限结构动作与原生采用。当前真实闭环仅为入口与 Skill；扩展节点应与规则基线及无 Jev 路径对照，比较成果通过率、重复失败、总耗时与全部调用成本。

论文工作定义：Decision-Native Harness Models（DNHM）

拟研究的决策原生 Harness 模型，以可观测执行状态和运行时提供的合法动作集为输入，直接对带类型及语言描述的候选打分，输出类型化选择或弃权；原生运行时重新核验、采用和执行，结果更新下一次观察。大脑负责复杂规划、生成及工作包，小脑负责控制选择，Harness 保留执行与状态责任。

可观测状态 + 合法动作描述→直接候选打分→类型化选择 / 弃权→原生核验与采用→执行反馈

这是工作定义与方法设计，不是新增公开 API、已证新颖性或已完成训练。有限候选控制不代替任意工具参数生成；动作覆盖不足和选择错误分别记录。

核心研究问题：Runtime Harness Generalization

冻结同一个 controller，封存未见任务族、控制节点及执行模型组合，检验它能否依据新的合法动作描述保持有效控制。任务迁移、节点迁移、执行器迁移及其组合分别报告；顺序、名称和同义描述扰动用于诊断位置偏差与标签记忆，不能单独证明跨节点泛化。

设计预期如何兑现：先补最小闭环，再贯通完整任务

当前发布切片包含原方案的底座、限定入口与首个过程节点；其“G1 发布”名称不代表原 G1—G6 只实施了第一步，也不代表六阶段整体完成。以下按能力和验收推进。2026-10-02 起顺序调整为：入口评测、专业 Agent 委派与进度回传、委派监督在前，约束、取证与记忆在后。

阶段 / 能力用户得到什么最小实现与文件范围必须通过
当前底座 + 入口 + Skill一句话开始，自动采用合法模型与专业方法，真实状态可查。当前 SessionController、System3、client-ui-system3、Frontend runtime、deploy/system3。已发布范围内通过；Skill 对规则的质量 / 总开销优势还需单独评测。
下一切片 0 · 入口评测集 已实测入口判断的收益和代价有数字可查。30–50 条带标签输入，包含多轮对话的后续消息；复用 createSystem3EntryRouter 请求真实 Jev；始终 baseline、确定性规则、Jev 三组对照。报告 outcome 分布、弃权率、选中非 baseline 的比例、延迟 p50 / p95。新增任何 Jev 决策点之前必须先有这组结果。
下一切片 1 · 专业 Agent 委派与进度回传（原 G5 最小版）任务交给 Codex 或 Claude Code 后，能看到它正在做什么，并能停止它。委派成为入口候选；子运行的步骤、工具调用、等待与结束状态投影到父会话前端；新增实现放在 packages/experimental/。至少一个真实委派任务；进度与最终结果关联同一 run；取消后子进程收尾；进度不进入父模型请求；与“主模型自行决定委派”对照。
下一切片 2 · 委派监督被委派的 Agent 卡住、失败或超出预算时，系统给出重试、换执行者或请求输入的明确动作。Jev 在执行循环之外对子运行状态做有限动作选择。文件缺失恢复方案的事件字段、去重时效规则和三组对照在此复用；该方案的单文件读取场景不再单独实施。真实采用且对照不降低任务通过率；迟到、取消、弃权不产生指令；每次失败最多采用一次。
后续切片 A · 约束与恢复不用重复关键要求；回来看到保留约束、已有成果和待办。原生上下文 / Session / 查询 + System3 来源关联；共享 UI 恢复卡。压缩后不丢约束；修改不回流、排除影响后续、原文可查；重启不冒充执行。
后续切片 B · 失败取证遇错先看关键证据，再决定下一步，少重复失败。tools 结算事实 + spill / read + System3 evidence 消费者与投影。实际读回进入请求；缺档、取消、迟到、跨会话隔离；不重放写动作；规则对照。
原 G4 · 受保护记忆与压缩材料有来源，重要事实保留，整理后能查回。Compaction owner 与必需事实检查；有限材料选择、来源版本与排除。真实 replacement、原文恢复、失败不提交，完整成本包含判断 / 摘要 / 查回。
原 G5 其余部分 · 多专家与持续 Goal明确交接、回收结果、有限续做，用户始终能暂停和接管。原生 Subagent / Goal owner / round driver；任务包、预算、统一完成检查。至少一个真实专家任务族；父子归属、取消收尾、CAS、无进展停止、独立验收、恢复 disarmed。
