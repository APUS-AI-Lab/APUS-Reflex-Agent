# System3 server deployment reference

English | [中文](deployment.zh.md)

## Scope

Since 2026-10-03 the independent `xdan-system3.service` runs on the `prd` host (SSH alias `prd`, Ubuntu 22.04, kernel 5.15, systemd 249, Docker 29.1, 32 cores, 123 GiB memory). It previously ran on `root@litellm`, whose four cores, 15 GiB memory and 17 GiB free disk left little room; that deployment was removed after the `prd` release passed, and its data archive is kept at `/root/xdan-system3-data-backup-20261003.tgz` on that host. Docker builds the Linux source and dependencies; the application runs as the dedicated `xdan-system3` system user. Other services on the host remain separate. The runtime starts the supported `dsh web` profile with `deploy/system3/runtime.patch.yml`. Release directories are root-owned and immutable to the service user; `/opt/xdan-system3/current` selects the active release.

## Access and isolation

The application binds `127.0.0.1:18731`. Connect with `ssh -N -L 18731:127.0.0.1:18731 prd`, then privately retrieve the native launch URL from the restricted service journal. The browser exchanges its launch token for the native signed, authority-bound cookie; anonymous API calls remain rejected. SSH authenticates transport access and the Harness cookie authenticates API access. No public Caddy route or DNS change is required.

The local installation is `~/Applications/xDAN System3.app`; double-click `~/Applications/启动 xDAN System3.command` or run `~/.local/bin/xdan-system3` to start Desktop. The first Web authentication URL is stored in the mode-0600 `~/.config/xdan-system3/launch-url` and opened in the local browser; never print this file in chat or shared logs. An authenticated browser can access `http://127.0.0.1:18731`; unauthenticated access returns 401.

The SSH tunnel is separate from the systemd service and may exit after a network interruption. Restore it with the command below only when local port 18731 has no listener; retain existing tunnel and service processes.

```sh
ssh -fN -o BatchMode=yes -o ConnectTimeout=10 -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -L 127.0.0.1:18731:127.0.0.1:18731 prd
```

The systemd unit uses an empty capability set, NoNewPrivileges, ProtectSystem=strict, ProtectHome, PrivateTmp, PrivateDevices, ProtectProc=invisible and RestrictSUIDSGID. Only `/var/lib/xdan-system3` is writable; private home and task workspace remain separate. Existing application directories and the environment-file directory are inaccessible inside the service. The service has a 2 GiB memory limit, 2 CPU quota and 256-task limit. Native workspace-write permissions remain enabled; subprocesses use the native credential scrub and bubblewrap.

The root-only `/etc/xdan-system3/runtime.env` reuses the existing `system3-dsh` virtual key and supplies `SYSTEM3_LITELLM_API_KEY`, `JEV_API_KEY`, the explicit JSON `SYSTEM3_SESSION_DATA_CLASSES`, and `DEEPSEEK_API_KEY` for the official DeepSeek API. Since 2026-10-07 that key serves every DeepSeek tier through the official API: the default model and the fast entry candidate as `deepseek-official/deepseek-flash` (DeepSeek-V4.1-Flash, which replaced the retired `deepseek-v4-flash`), the reasoning candidate as `deepseek-official/deepseek-v4-pro`, and the `web_search` tool. Fidoo still serves the GPT relay tiers, and its old DeepSeek entries stay listed so existing sessions resolve. The deployment sets `welcomeNotice: false`, because a remote browser would otherwise see the Harness testing notice on every page load. The acceptance environment declares only public material; operators must not put personal or confidential files into this workspace. Classification is a deployment declaration, not automatic sanitization. Credentials never enter build artifacts or frontend bundles. Native browser credentials persist in the private Harness home. DeepSeek session-log contribution and telemetry delivery are disabled.

Delegated Codex runs use the bundled Codex CLI with the service-owned `CODEX_HOME` `/var/lib/xdan-system3/codex-home` (mode 0700). Each release installs `deploy/system3/codex/config.toml` there with mode 0600: it sends Codex to the Fidoo Responses API with `gpt-5.6-sol-relay`, reads the key from `SYSTEM3_LITELLM_API_KEY`, sets `approval_policy = "never"` and `sandbox_mode = "workspace-write"`, and disables update checks and analytics. No personal ChatGPT login, plugin, or MCP server enters this home. The unit sets `SYSTEM3_CODEX_HOME`; `runtime.patch.yml` passes it and the key only to the Codex child. Codex sandboxes its own commands with its bundled bubblewrap. On 2026-10-03 a Codex 0.153.4 run on this host under the unit's hardening (transient unit with the same user, NoNewPrivileges, empty capability set, ProtectSystem=strict, ProtectHome, PrivateTmp, PrivateDevices and ReadWritePaths) fixed a file and passed its tests in 38 s, and a write outside the workspace failed with a read-only file system error although the unit itself allows that path. Codex refuses to create its sandbox helper links when `CODEX_HOME` is under `/tmp`, so the home must stay under `/var/lib/xdan-system3`. DSH starts Codex as a plain managed process, so Codex's sandbox is not nested inside the DSH bubblewrap.

Since 2026-10-03 the Harness is also reachable at `https://system3.xdan.work/`. The host's nginx terminates TLS with a certbot HTTP-01 certificate and proxies to the loopback port; the unit passes `--trusted-host system3.xdan.work` so the Harness accepts that host. The Harness authenticates every request itself: an anonymous or wrong-token request receives HTTP 401, the launch URL exchanges its process token for a signed cookie valid for 30 days, and that cookie survives service restarts and releases because its signing secret is stored in the Harness home. The launch token changes on every start. The site file is `deploy/system3/nginx/system3.xdan.work.conf`, and the operator keeps the current public launch URL in the mode-0600 file `~/.config/xdan-system3/public-launch-url`. The access log omits query strings so launch tokens never reach disk. Each new browser opens the current launch URL once and selects the `workspace` workspace once. The Harness has a single operator: everyone holding a valid cookie shares its sessions, workspace and credentials, so give the launch URL only to trusted people. Basic Auth in front of the Harness was removed on 2026-10-05.

## Release and recovery

Run `deploy/system3/release.sh <immutable-release-id> <source-commit>` on the server from a reviewed source archive. The script installs dependencies from the lockfile and builds Linux artifacts in the pinned Node image, extracts the application and matching Node/bubblewrap binaries, creates a root-owned release directory, selects it atomically, then restarts only the System3 unit. The source commit is embedded in client metadata and the image label. Release health requires an active process and HTTP 401 for an anonymous API request. Only a healthy publication updates the previous-release pointer; failed publications retain the existing rollback target. Each release saves its own `service.unit`; an active legacy release receives its current unit once before replacement.

`deploy/system3/rollback.sh` selects the compatible predecessor with that release’s saved unit and preserves sessions. A successful rollback consumes its target; a repeated invocation fails without restarting or changing the unit. A failed rollback restores the original release and unit and retains the target. Application rollback does not reverse session-format or database migrations; take a stopped-service backup before releases changing persistent formats. `Restart=on-failure` and the enabled systemd unit recover after process failure or host restart. Availability checks do not establish task acceptance: separately verify browser authentication, actual Jev selection, Fidoo output, Skill adoption, native shell execution, artifact correctness, cancellation and persistence after restart.

## Verified deployment constraints

The earlier `litellm` target ran TencentOS x86_64, kernel 6.6.117, glibc 2.38, systemd 255 and Docker 29.8.1. Latency measured from this host on 2026-10-03: Jev decisions on a reused connection p50 274 ms and p95 406 ms over 48 requests, 1051 ms on a new connection, and 700 to 940 ms after 5 to 30 s idle with Node's default keep-alive; Fidoo first token p50 463 ms for deepseek-v4-flash (one outlier at 10.6 s in 5), 806 ms for deepseek-v4-pro and 1576 ms for gpt-5.6-sol-relay. The pinned Node image runs 24.21.0. The dedicated System3 key successfully listed both configured Fidoo models; the A100 Jev health endpoint reported ready/high32. The baseline rc.2 Linux build passed native compilation, Host and Client TypeScript/bundling, desktop bundle and Web build (343 client artifacts). On 2026-10-03 release `s3-delegation` replaced the `g1-stable` release, which remains the rollback target; the eight release-script cases passed first. A browser end-to-end run through the SSH tunnel then routed a translation to DeepSeek Flash, a protocol question to DeepSeek Pro and a system-design request to GPT-5.6 Sol, and kept GPT-5.6 Sol for a follow-up; in-product entry decisions took 638 to 1039 ms and the route line appeared 1.2 to 1.45 s after submission, tunnel included. GPT-5.6 Sol produced about 18 output tokens per second through the Fidoo relay, so a 10,067-token answer took 553 s. An explicitly requested Codex delegation started in 12 s, accepted a mid-run steer in 0.7 s, raised one stalled and one overtime alert, finished in 374 s and passed all 13 hidden acceptance tests and the 6 existing tests; the steered README was written.

The kernel has no active Landlock LSM. A non-root container with default Docker seccomp could not create the bubblewrap namespace; a diagnostic container without that filter still could not mount the private proc filesystem. The deployment therefore uses native systemd instead of weakening container controls. Bubblewrap on the host and under the selected systemd hardening both passed workspace writes and rejected writes to the same user's home with a read-only-filesystem error. The native environment scrub also passed a child-process check with both deployed credential names present only in the parent. Eight isolated release-script cases passed: publish/manual rollback, activation failure, HTTP/auth health failure, extraction failure, invalid release identifier, failed third publication preserving the earlier rollback target, repeated rollback without service mutation, and failed rollback restoring the original release/unit pair. Initial browser task evidence is in `deployment-preflight.json`. Reviewed tag `system3-g1-reviewed-rc2` remains active as the stable release after a successful same-commit rollback from the verification release; the rollback target was consumed. Both Linux builds and release health checks passed; the actual CLI reports `0.1.7-rc.2` on Node 24.21.0. Anonymous API access returns 401, untrusted Origin/Host requests return 403, and the enabled non-root service binds loopback only. Infrastructure evidence, including the exact source commit, is in [deployment-final.json](deployment-final.json); the real browser task, credential scrub, cancellation, model reset, strict artifact oracle and same-session browser replay after both restart and rollback passed. The initial artifact had an extra field; a native continuation removed it before final oracle acceptance. The real entry decision abstained on low confidence and used the configured baseline; the Skill decision injected the selected instructions into the actual Fidoo request.

On `prd`, the eight release-script cases passed before the first release, and a fresh install needs the service workspace `/var/lib/xdan-system3/workspace` added once in the Web workspace picker. The browser run then routed a translation to DeepSeek Flash and a protocol question to DeepSeek Pro (the first route line took 3.8 s on a cold Jev connection, the next 1.4 s), and an input saying to hand the task to Codex delegated without a Jev request, recorded `explicit: true`, finished in 389 s and passed all 13 hidden acceptance tests. Codex wrote the README a mid-run steer asked for, but the main model deleted it while cleaning up after its review, because steers are not visible to the main model. After the delegation tool began restating accepted steers to the main model, a rerun on `prd` kept the steered README, restated the steer at the end of the tool result, and passed all 13 hidden acceptance tests in 321 s.

The pilot top-three release on 2026-10-04 enables `processSupervision` (advise), `entryRouting.routeHealth`, and `entryRouting.handoffPack`. In the browser, a command repeated after the same failure produced the repeated-error and failed-attempts notices and the model stopped to ask for confirmation; a file written without a check produced one missing-evidence reminder, after which the model verified it. A delegation preceded by naming and README rules forwarded them in 915 ms (Jev probability 0.998); Codex followed both, and its 20 tests passed once pytest was available. That run exposed piped checks such as `pytest | tail` being accepted as evidence; the following release refuses piped commands as verification. No route reached the route-health thresholds during the run.
