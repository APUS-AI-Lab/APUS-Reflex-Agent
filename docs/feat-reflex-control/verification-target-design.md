# Verification target evidence addendum

English | [中文](verification-target-design.zh.md)

## Status and problem

The implementation adds opt-in static verification-target extraction; real-API acceptance is still pending. The structural collector extracts native read/list/search and file-change labels and paths. Codex may classify successful Python or pytest execution as `unknown`, leaving no path for semantic feedback. A passing command without a known verification target cannot demonstrate Goal-related verification under the current feedback rules.

## Native protocol evidence

The schema generated by the workspace-pinned Codex 0.153.4 exposes `command`, `commandActions`, `cwd`, `status`, `exitCode`, `aggregatedOutput`, identifiers, duration and optional plugin metadata on command execution items. `commandActions` is explicitly best-effort. There is no general argv, test-target or assertion-result field. The optional `scriptPath` identifies a first-party plugin script; it is not a general verification target. No raw command, output or query belongs in the Reflex summary.

Existing semantic/supervision/recovery reports retain only bounded operation evidence or action-type metadata; they do not retain the native command envelope. The isolated browser Codex home at `/private/tmp/reflex-ux-acceptance/codex-home/sessions` contained no rollout JSONL files when checked. The actual distribution of bare commands and shell wrappers is therefore unverified. User-default Codex history was not inspected. The next already-planned real E2E may record only an envelope enum and counts, never command text, to resolve this gap.

## Proposed extraction

Use the existing locked `@yarnpkg/parsers` 3.1.0 static `parseShell` implementation in the provider process. The webworker runtime already uses it; its `dsh-shell-parser-only` bundler plugin selects the shell entry and excludes the unrelated Syml grammar. The Codex provider declares its own direct dependency and uses the public root export, without importing the experimental worker or a private parser subpath. The parser exposes a shell AST, not execution; its accepted grammar and literal/glob distinctions still require focused rejection tests. Parse without execution, variable expansion, environment lookup or file reads. Impose a deployment-owned command-length budget before parsing and retain the existing action/path budgets after extraction.

With `evidenceSummary.verificationTargets: { maxCommandChars: 4096 }`, admit one literal `pytest <file.py>`, `python -m pytest <file.py>` or `python -m unittest <file.py>` invocation; `python3` is also supported. Require explicit ASCII file targets; all option forms and node selectors are unsupported. Reject assignments, expansions, substitutions, pipelines, redirects, command chaining, glob targets and unknown options. Arbitrary Python scripts remain ordinary execution: a script name or exit zero does not establish that the script verifies anything.

POSIX support must cover both bare commands and exactly one recognized `sh`/`bash`/`zsh` wrapper using `-c` or `-lc` with one literal payload. Parse the outer command and the payload independently. Reject additional wrapper arguments, nested wrappers or unsupported syntax; never repeatedly strip strings until a recognizable command appears. Windows PowerShell/cmd syntax is outside the first implementation and must remain unsupported rather than being parsed as POSIX. Real native envelope evidence is required before claiming the POSIX path works in product use.

Add a distinct structured `verification-target` action rather than inventing a read action. Resolve literal targets using the native command cwd, retain only workspace-relative paths, and omit outside or over-budget targets. Pytest node identifiers, query selectors and parameterized values are rejected rather than transmitted. A cwd alone supplies no target. Persist exactly the admitted summary before sending it through the existing workspace-data privacy policy. Keep native outcomes and summary omissions explicit.

## Feedback and limits

Feedback requires a successful verification observation with a complete `verification-target` action; a read-only test-file summary cannot establish improvement. Native exit code zero is required for a parsed verification target to have a successful outcome. The model may compare an admitted verification target with the unchanged Goal and requirements. Even related pytest targets with exit zero establish only the observed invocation's result; they do not establish that all Goal acceptance criteria ran or passed. Unsupported commands, missing targets, uncertain relevance or denied workspace admission remain inconclusive. This extension must not change permissions, cache prefixes, user messages or context projections.

## Change and acceptance scope

The implementation adds a parser dependency, provider-local extraction and configuration, the new action kind, consuming schemas/feedback, type documentation and persistence acknowledgements, and TypeScript/Python recorded-session fixtures. It requires a fresh coordinated build after the current context/SDK acceptance. It is not a documentation-only completion of the current limitation.

Acceptance requires literal-target and wrapper cases through the real 0.153.4 channel, with envelope-only reporting; parser rejection tests for unsupported syntax and secret-bearing arguments; workspace, truncation and privacy tests; missing/ambiguous-target feedback; both SDK record/replay cases; and a real pytest or standard-library unittest run with independent artifact verification. Tests must not replace an actual wrapper with a simpler bare fixture or claim arbitrary Python scripts are verification.
