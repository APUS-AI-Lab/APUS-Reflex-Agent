# System3：有先手的任务工作台

[English](system3-experience-review.md) | 中文

本页是针对 [原设计](system3-native-v1.html#experience) 的产品交互提案与评审记录，全部新增体验均为待实施设计。[可点击体验稿](system3-experience-v2.html) 使用离线样例，不调用 Jev 或 Harness。目标用户先按桌面中的开发、资料处理和持续任务使用者设计。

## 直接执行：体验方向

System3 应让用户感觉任务被迅速接住、处理方式合适、关键约束一直被记住、遇到问题有下一步。用户用自然语言交付目标，工作台把目标、当前动作、逐步出现的成果和需要参与的事项放在同一任务中。Jev 的判断通过实际改变的行动体现；Harness 把判断变成可控制、可恢复、可核验的工作。

### 一段完整体验

用户说：“按我们上次的约束升级接口，生产库不要动，改完跑回归。”输入就地回显为任务回执；Host 接受后显示“已接收”。需要做选择时出现“正在选择处理方式”，选择被采用后更新为“已选用 Pro”，紧接着开始真实工作。固定模式跳过入口 Jev；界面响应与后端完成分别呈现。

回答旁出现“已使用：迁移核对清单”和两条可点开的原始约束。用户不用重新解释过去的约定，仍可以看到来源或排除后续使用。资料变多后，状态简短更新为“已整理上下文”，点开能检查保留的事实和可查回的原文。信息不够时，工作台显示实际查回的记录，随后继续任务。

回归失败时，失败证据留在原位置。Jev 从合法诊断候选中建议先检查错误详情；System2 实际读取之后，界面更新为“已取得失败日志”，再出现修改成果。需要代码专家时，任务中出现接力记录：专家负责哪件事、正在做什么、已有哪份成果。结果回到父任务整合，用户能停止整个任务或在支持时单独停止专家。

用户离开一会儿回来，先看到变化摘要：“方案已更新，仍有一项回归未通过。”Goal 显示明确验收项，不使用估计百分比。重启之后，任务资料可以恢复，执行显示“等待你恢复”；用户确认恢复后才继续。所有跟进围绕真实变化，避免定时刷“还在处理中”。

### 体感如何形成

| 体感 | 界面表达 | 实际机制 |
|---|---|---|
| 有先手 | 任务被接住后立即进入实际动作；重要选路就地更新 | 原生准入、Jev 有界选择、所属服务采用；不人为延迟展示 |
| 懂任务 | 使用合适的技能或专家，直接开始对应工作 | 真实候选能力描述、Skill 注入、原生委派；不编造 Jev 推理理由 |
| 记得住 | 当前任务旁可检查原有约束与来源 | 有范围的检索、实际上下文注入、压缩保护及原文查回 |
| 有韧性 | 失败保留，下一份诊断证据和新成果随之出现 | tool/result、有限证据选择、System2 诊断；不盲目重放写操作 |
| 有掌控 | 停止、Goal 暂停/恢复、下一回合模式一直可达 | Host 确认、明确生效时点；取消信号与收尾分别表达 |
| 安静可靠 | 普通选择压成一行；只有变化、阻塞和风险展开 | 同一任务的状态聚合、事件去重、变化摘要 |
| 有完成感 | 可打开的成果与验收证据逐项到位 | 真实产物、非空检查集合、独立验收；有输出不等于任务完成 |

## 界面结构与反馈层级

保留唯一原生 Conversation。左侧仍是任务/会话导航；中间是目标、交流和关键变化；右侧复用现有 sidebar slot，在“成果、上下文、目标、记录”之间切换。输入区扩展已有模型选择器，不再另建路由控制中心。窄窗把右侧内容放到任务下方，主操作仍在输入区。

默认层只回答四件事：现在做什么、有什么成果、还差什么、我能做什么。第二层展示本次实际使用的技能、记忆、专家和数据去向。第三层才是建议、采用、请求、输出以及供应来源；分数、协议和候选版本留在诊断详情。

“Jev 快决策”可以在处理方式旁作为可展开的产品标识出现。正常入口选择用一条状态；Skill 加入、诊断方向变化、专家接力或等待用户时，在任务内留下简短、持久的变化记录。并非每次 Jev 调用都生成新卡片。

成果区应随着实际产物出现而更新：方案草稿、文件修改、测试报告逐个可打开。未验收草稿标明状态；没有实际内容时不填充虚构报告。后台成果在应用内用持久任务状态承接，短暂操作结果使用共享 Toast，避免用户错过一次性提示后无处查找。

原稿第 145—148 行的下拉演示和第 236—238 行的 render 一次性显示四格状态，适合检查事实链，无法体验任务推进。建议在第 5 节首先放完整任务旅程，再保留状态审计作为详情；原有架构和真实性约束继续作为设计依据。

## Jev 能力怎样进入体验

Jev 的 choice 负责在合法候选中选路；score 负责局部相关性或有序等级判断；noul 负责有限命题判断。具体节点按需求选择协议，不为把三种协议展示齐全而增加调用。协议分数尚未校准，不能变成“任务成功率”或触发权限升级。

| 节点 | 判断后真正改变什么 | 用户感知 | 采用条件 |
|---|---|---|---|
| 入口 | 本回合模型或获准处理路径 | 不必每次自己挑模型，处理方式可检查 | 合法候选、人工意图、输入准入与有效选模 |
| Skill | 下一请求使用的任务指令 | 专业方法已经用上 | 有来源的正文、版本、Scope、去重和实际请求关联 |
| 记忆 | 下一请求装入的相关历史 | 不用重讲约束，可查原话 | 可读范围、实际注入、版本与排除检查 |
| 压缩 | 少量块保留原文、摘要或按需查回 | 长任务继续得下去，关键约束仍可见 | 原生压缩事务、System2 摘要、必需事实检查与可恢复原文 |
| 诊断 | 下一份值得读取的证据 | 失败后动作有方向 | 已结算结果、建议采用、实际工具读取；不代替复杂修复 |
| 专家 | 获准任务交给哪个已安装 provider | 合适的人接力，成果能回到主任务 | 原生父子归属、取消、结果回传；模型别名不是委派 |
| Goal/沟通 | 建议继续、等待或报告重要变化 | 知道还差什么，减少空转与打扰 | Goal revision、实际续轮、预算和独立检查；Jev 不标记完成 |

## 本地 9B/27B 的位置

未来本地通用 9B/27B 可作为 System2 的 Lead 角色，在 Harness 里处理已验证的本地常用能力和本地数据，生成工作安排、跟踪任务，并通过原生 subagent 服务调度专业 Agent。Jev 为入口和中间节点提供有界候选判断；Lead 负责复杂生成与编排；Harness 仍是唯一执行和状态所有者。

用户届时可以看到“本机处理中”的实际执行位置、具体的本地成果，以及专家接力发生时获准外发的材料范围。图和界面必须同时表达 Jev 决策执行域、Lead 的执行域以及专家/云模型的执行域；自有 9B 不等于设备本地，进程内子 Agent 也不等于模型本地。未验证前，本地 Lead 显示为演进能力，不能把现有 Flash/Pro 改名成它。

## 状态、接口与复用约束

新增设计沿用原稿的接口草案。前端消费 Host 投影和持久事件，瞬态请求状态来自同一请求所有者。重连先恢复事实与补档，不再次调用 Jev。各任务的状态绑定 input/turn/step；迟到的旧决策不能覆盖当前任务。

| 交互 | Host 必须提供 | 失败及恢复 |
|---|---|---|
| 提交与入口 | 本地提交/Host 接受/入口处理中/结算状态；实际采用与请求关联 | 准入失败保留输入；Jev 超时保留获准 baseline；历史缺档局部显示未知 |
| 自动/固定 | 持久模式 revision 与 effectiveFrom | CAS 冲突刷新实际模式；保持当前已开始配置 |
| 上下文检查 | 来源、内容版本、实际进入请求的回执 | 来源不可读保留当前任务；排除只影响明确的后续范围 |
| 压缩/恢复 | summary 与实际 replacement 分开；保护事实清单、可查回来源 | 检查失败不提交压缩；原文缺失明确说明 |
| 专家与停止 | parent/child run、实际状态、取消接纳和收尾 | 保留部分成果；取消不撤销已发生外部写操作 |
| Goal | phase 与 activation、必需检查和证据、实际续轮 | 重启 disarmed 不显示运行；预算和验收接口未补齐前不承诺自动完成 |

当前 entry decision 回执在调用结算后写入，现有 projection 只是 Host 的 latest shadow receipt，尚不能支撑完整任务的前端状态。现有选模 wire 只有 lastUsed/next，缺模式意图和生效时点。实现需要补这些原生投影，而非由前端猜测或计时模拟。参见 [入口消费者](../../packages/experimental/system3/src/entry-routing.ts)、[当前投影](../../packages/experimental/system3/src/decision-projection.ts)、[选模类型](../../packages/api/session-controller/src/types.ts)。

## 动效与节奏

动效只帮助反馈、定位和状态连续。任务回执即时回显；已收到、选择中、已采用在同一位置更新。快速完成的决策不强制停留、不排队播放四个阶段。成果首次出现可用约 120—180ms 的透明度/小幅位移反馈；普通颜色反馈约 120ms；偶尔打开的详情可在约 180—220ms 内展开。以上是交互设计起始值，需实机验证，并非模型延迟承诺。

不建议给 token 流逐字加动画，不给每次决策发弹出通知，不用循环发光证明“聪明”，不动画键盘切换/焦点，不用虚构百分比或“无损”徽章。减少动态效果时即时切换；屏幕阅读器只播报一条当前状态，完整记录仍可主动读取。

## 文件范围与验证计划

本轮交付只涉及同名 worktree 的设计目录和 tasks。产品实现范围沿用 [原设计交付节](system3-native-v1.html#delivery)：SessionController 的模式/准入投影、System3 Host/Client 分面、原生 Conversation 节点及 sidebar slot、Skill/Compaction/Goal/Subagent 的最小消费者扩展。所有产品文案进入 typed locale，复用已有主题、Toast、Menu 与 Tooltip；不建立第二 Conversation、AgentLoop 或任务数据库。

体验稿验证覆盖所有场景推进、自动/固定下一任务生效、暂停/恢复、停止收尾、来源查看和后续排除、窄屏、明暗主题、键盘与减少动态效果。它只能证明样例交互，不证明后端能力或端到端速度。产品实现仍需真实入口/过程采用、错误/取消/并发/重连回放、keyless snapshots、双 SDK 投影和相关行为测试。

体验收益应以首次有效成果、任务成功率、返工、用户重复解释、重要等待是否被理解来衡量；同时统计 Jev 额外延迟、弃权、摘要/查回和完整任务成本。单次 SDK smoke 不代表真实 p50/p95；Token 减少不等于费用减少。用户测试可让参与者独立找出当前动作、下一步和接管操作，再验证任务结束的理解。

## 深度交互：保留的取舍

充分发挥 Jev 的价值来自少数正确选择累计降低返工，而非增加判断频率。用户可以明显感到入口有先手、过程有调整、记忆不中断；正常运行仍应给成果让出空间。每个新增节点都需要真实行为收益，规则足够的地方省掉一次判断。

“本地掌控、专业接力、长期记忆”是有吸引力的整体方向，但不能预设 9B/27B 在所有本地工具任务上胜任。先选择有明确验收的本地任务族，再扩展 Lead 的编排能力。用户感知到的可靠性应来自能读懂状态、能查来源、能接管和确实完成任务。
