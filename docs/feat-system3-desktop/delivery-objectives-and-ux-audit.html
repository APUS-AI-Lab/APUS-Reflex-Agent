1. 本次记录的任务目标

面向外部使用者交付 System3 Harness + Agent 工作台。入口智能、过程智能、体感智能共同贯穿提交、准入、执行、补充要求、阶段成果、控制和验收；三者不拆成独立功能页面。桌面优先，Web/API/双 SDK 共享任务事实与控制含义。

  • 入口：在权限、材料范围和预算约束下，Jev 做有限候选判断；Fidoo 路由承担生成。用户能区分已提交、已收到、已准入、实际执行，固定选择和合法基线始终有效。
  • 过程：Skill、来源明确的记忆、压缩保护和查回、失败取证、专业 Agent 与持续 Goal 实际改变工作；至少一个 Jev 过程节点必须真实采用，随后完成 G1—G6 全部约定范围。
  • 体感：用户默认看到当前动作、成果、缺项与下一操作，能够调整、停止和恢复；界面根据真实事件变化，性能与费用按完整任务评估。
  • 前端：复用 dataelement 桌面载体与唯一原生 Conversation，接入自有 Harness runtime 和共享 Client Module。部署位置、数据去向、凭据配置、版本与能力不匹配都能准确说明。
  • 未来本机 Lead：通用 9B/27B 处理常用任务和本地数据，并提出专家编排指令；Harness 执行。其能力验证单列，不把 Jev 9B 决策 API 等同于通用生成模型。

4. 前端对接不是给 HTML 加几个请求

明确接入仓库：/path/to/projects/APUS-Reflex-Frontend。用户已再次确认该前端目标，三层智能的产品交互必须落到这个仓库及其复用的原生 Client Modules 中。

现有接入点已定位：src/main/index.ts 解析 dshEntryPath；src/main/runtime/harness-runtime.ts 启动原生 Web profile；build/dsh-desktop.patch.yml 装配模块；packages/dsh-desktop-client-ui/ 已通过模块加载器扩展 Conversation/API 和原生 slots。当前加载的是官方 npm runtime，尚未装配自有 System3 产物。优先扩展这些已有位置，是否拆共享模块以代码复用和发布依赖为依据。

v3 在浏览器内保存样例 sessions、phase 和成果，由“下一事件”推进；文件选择仅取文件名。这些代码用于设计回放。生产组件从 Harness 的原生身份、事件、投影与控制回执读取事实；本地只保留草稿、展开、焦点和阅读位置等 UI 状态。

  1. 运行时装配：固定桌面和自有 Harness 版本、补丁与产物来源，验证启动实际加载的 Host/Client/Core/System3。开发环境可运行不替代安装包可运行。
  2. 事件与投影：复用 SessionController 与现有流，贯通 request/turn/step、采用、使用、成果和子任务；按需要补收到状态、模式与生效点、控制结算。TaskView 仍是设计草案，先判断哪些字段可推导。
  3. 客户端模块：在现有 Conversation 与 sidebar slots 中实现共享 UI；后端导出类型，前端消费它们。模块注册、静态资源、locale 与能力发现都进入固定组合，不建立第二 AgentLoop。
  4. 真实操作：提交/补充/排队、模式切换、材料批准、取消/复合停止、恢复、来源排除逐项映射 API；对不支持的动作明确说明。后端确认前不能把控制画成成功。
  5. 持久与安全：覆盖断线补档、冷启动、能力缺失、凭据错误和历史日志读取；前端不直接持有 Jev/Fidoo 凭据，也不直接调用模型来绕过 Harness。

字段草案、服务所有者和两仓职责以跨终端接口及两仓职责为准。本页不再定义一套 API。

5. 接下来按完整任务分批交付

产品落码前优先收敛三项生产交互：运行中补充/另起任务、逐对象材料批准、部分停止失败后的恢复；它们决定任务归属、数据授权和用户控制。按目标用户操作观察检验，之后再固定对应组件与接口。

G1—G6 范围保持完整。建议首批使用隔离工作区的接口升级核对任务；这是实施建议，尚未获得用户对任务族的单独确认。

  1. G1：桌面加载自有运行时，完成模型和服务配置/健康/不可用反馈；核对公网 Jev 新端点与凭据引用，统一 SDK，分别验收开发与安装包。
  2. G2 + G3 首条链：真实输入 → Jev 选模 → Fidoo → Skill 实际注入 → 阶段成果 → 必需检查；同步交付真实状态展示、固定切换、停止和中断恢复。
  3. G4 + G5：每扩展记忆、诊断、专家和持续 Goal，同时扩展来源、权限、控制、异常和验收 UI。不能把 UI 接入全部留到后端做完。
  4. G6：跨终端回放一致、真实安装包、多任务/长任务与目标用户验收；按规则/固定模型基线测量质量、总成本和返工。

每批必须同时提交后端事实、界面表达、用户控制与失败恢复的证据。第一条链可用于提前验证价值，但不据此宣称整体目标完成。

6. UI/UX 与前端接入完成的判定

  • 从真实桌面提交目标，所用材料、Jev 建议、Harness 采用、Fidoo 实际输出、过程使用和产物能追到同一任务。
  • 用户可以解释“现在做什么、谁在处理、什么材料已用、有哪些成果、还差什么、我能怎么干预”；界面不得依据缺失事件推断成功。
  • 模式、材料和批准的生效范围正确；超时、冲突、取消、部分失败、重连和重启都不丢失事实或重复执行。
  • 长内容与多任务不妨碍阅读、输入和控制；键盘、读屏、输入法、缩放和平台窗口适配通过真实产品检查。
  • 交互方案由目标用户任务验证；至少一个 Jev 过程节点真实采用，对照任务质量没有下降；效率收益只报告实际测量结果。

内部工作区计划已私有归档；公开跟进见架构跟进清单。所有项必须有明确证据，不能用原型截图或单独 API 成功替代。

8. 入口智能与体感速度：先缩短关键等待，再改善表达

本轮为代码审查与优化候选设计，未测出生产前后差值。优化同时约束首次可见反馈、首个有用输出、首个有效成果、完整任务质量/耗时/成本；“已收到”或填充句不能算有用成果。界面更新不能比真实事件提前宣称采用或执行。

确认的现状

A100 最新指南记录：15个成功决策请求（含并发）中位数3.52秒、范围2.91–9.58秒；包含公网/TLS，属于小样本功能验收，不是入口单问题SLA或提速证明。8086提供结构化决策且不接受stream；8002提供标准vLLM及SSE，两者共用high引擎，会竞争容量。前端接入继续经Harness；标准生成协议成功不等于该决策模型已具备通用Lead能力。

  • 原生 Conversation 已有本地 pending submission，sendSession 在请求前执行 beginSubmission → nextPaint → 序列化材料 → prompt。应保留并接通真实状态，不能重复造一套乐观回显。
  • 可路由纯文本入口依次等待 Jev route → resolveCallConfig → 准入 → AgentLoop 生成；人工固定及不适用入口已有旁路。Jev 调用是该自动路径上的前置等待，但实际各段耗时仍需测量。
  • 当前 Jev Fetch provider 默认 HTTP 超时为30秒，在凭据解析后才开始；入口前后的模型准备也不属于该计时，尚无覆盖整个入口操作的独立截止。当前 Fetch 没有通用自动重试循环；迁入 SDK 时必须重新审查重试和总截止。
  • 原生文本流发布采用连续三个 requestAnimationFrame 合并更新，首块没有单独的即时发布分支；这是现有吞吐策略，首块→绘制收益需实测。桌面已存在预热与零稳定等待窗口，不能把它们当作尚未实现的优化。
  • 入口已使用一个有界 Choice 请求。Fidoo 对应的 Pi AI resolveModel 当前读取本地 snapshot；串行解析候选不等于逐模型请求网络，不应先假定它是主要瓶颈。
  • 旧入口 low 档约0.76/1.08秒与公网 high 三问题约3.74–5.22秒来自不同条件，仅是历史样本。不能用两组数推导提速比例或把 high 改为 low 直接宣布优化。
环节 / 优先级拟议优化条件与验证
提交与接收 · P0复用现有立即回显，保留草稿失败恢复；补 Host 收到/准入反馈。取消请求即时在本地反馈，最终收尾由 Host 确认。建议本地回显 p95≤100ms 为待校准体验目标，不是当前实测或发布 SLA。真实输入测到实际绘制；含中文输入法、附件编码和长会话。收到前不声称已准入。
入口是否需要判断 · P0保留固定模式旁路；对经过权限/能力检查后没有实质选项的请求设计确定性路径。只有选择能影响结果时才增加 Jev 判断，避免再加一个 LLM 先决定是否调用 Jev。不能按字数简单判断任务难度，也不能绕过数据准入。记录规则路径与实际模型；比较“固定基线 / 规则 / 规则+Jev”的质量、返工和总时延。
决策时间预算 · P0增加覆盖入口准备、凭据、Jev 和采用前解析的总截止；保留生成启动所需预算。超时后取消在途判断，重查候选/用户意图后使用合法基线；迟到结果失效。预算由真实入口单问题负载与收益曲线校准，配置化；不把公网 high 一律截到任意500ms而导致永久降级。无合法基线则明确阻塞，用户取消不得当作可继续生成的超时。
第一份有用输出 · P0直接沿原生流输出有效内容；任务允许时先生成可使用的小成果，再补充分析与验证。报告、差异和证据各自到达即呈现，草稿明确未验收。当前 produced-files 稳定入口在回合收尾，过程工具另有呈现；可验证从已结算产物事件提前开放入口，不从流文本猜文件已存在。不另调一个模型生成安抚句，不用空标题或“正在思考”计入提速；真正的检验和权限前置不省略，最终完成仍由必需检查决定。
流式渲染与阅读 · P0试验将首个有效内容从现有三帧合并路径中单独即时发布，后续保留原生合并；比较 chunk→paint 与渲染开销后再决定。稳定消息身份，仅更新变化区域；昂贵解析与不可见详情按需处理；不在模型流上再叠加打字机延迟。先查现有实现与真实浏览器性能，避免增加第二层节流；结算、错误、取消及时刷新，全文一致。保持滚动锚点、正在选择的文字、输入焦点与减少动态偏好。
桌面启动与准备 · P1保留已有预热，分测 runtime ready→缓存/认证清理→loadURL→首个可操作界面；不绕过安全清理。启动失败允许诊断/重试；必要时预加载模块及合法候选静态配置。区分冷/暖启动和内存/CPU成本，不让设置、插件市场或历史全量加载阻塞首次任务。未发送输入不得预先传给模型；后台准备不能改变权限或自动运行任务。
连接与提交准备 · P1分测公网新连接/复用连接的 DNS/TLS、网关排队与推理；附件编码等昂贵准备期间观察取消信号，避免取消后继续无用准备。当前图片 FileReader 编码没有接收 signal；沿原回显退休和草稿恢复流程验证，不改成主线程手工字节循环。公网 health/鉴权样本也有秒级耗时，但不能据此推断模型推理占比。
模型与过程策略 · P1针对具体任务评估模型及 reasoning effort、稳定前缀、工具往返和上下文规模；过程 Jev 只在新证据或目标变化且有选择价值时触发。无依赖且获准的只读准备可并行。默认 high/low 不在本轮变更，按同一任务集分别测质量与成本；保留关键事实和必要校验。Jev 尚未决策时不抢跑生成/写操作，不为提速重复计费或外发。
持续体感 · P1短暂中间状态可合并；长等待显示当前动作与可执行控制。回来后先看新增成果、阻塞和需参与事项，技术记录展开。动效短、可打断，保持控件空间位置。不强制把已经完成的阶段排队播完，不伪造百分比或时间；以真实等待和目标用户操作判断是否减少误解与重复提交。

第一轮测量与实施卡

用户操作：桌面首次提交/暖会话提交、看到有用结果、打开首个成果，以及执行中取消。工作负载：公开固定短改写、复杂接口分析、已授权文件处理、长会话；另外独立测冷启动、并发排队、超时/失败和取消，不把附件旁路与文本自动路由混为一组。

计时：客户端同一单调时钟记录提交→回显绘制、首块绘制、有用成果可操作；Host/供给各自记录解析、路由、凭据、网络/排队/推理、采用、生成与工具阶段。按原生 request/turn/step 关联，不能直接相减不同机器的时钟。对外报告端到端样本分布，并把未完成、降级与返工计入，不只保留成功快样本。

比较：先测未修改的真实构建；固定模型、规则、规则+Jev 在相同权限、材料与任务上比较。冷/暖、供给、模型/effort、并发和网络分别记录。保留原始样本，报告 p50/p95 与样本规模；少量样本不作稳定尾延迟结论。性能任务串行测量，避免与自有构建互相干扰。

资源与停止规则：同时记录 renderer 主线程长任务/渲染次数及内存、Host 资源和所有模型调用成本。一次只改变一个原因；只有真实终点改善且质量、取消、顺序、恢复和权限不退化才保留。优化前后运行所属行为与回放检查；构造受控延迟或回退原行为，确认测量能识别目标回归。
