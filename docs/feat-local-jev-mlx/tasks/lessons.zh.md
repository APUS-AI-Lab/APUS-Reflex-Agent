## 2026-10-14 · 运行时选型先问评判标准，再比方案

- **发生了什么**：我以「分布精确性」为隐含标准否定了 Ollama，连续几轮都把它写成「不作为产品路径」。用户追问「如果集成 Ollama 是不是兼容性更好」「便利易用性是关键」之后才改判。
- **根因**：没有先确认评判标准就开始比较；把一个可量化、可有界处理的代价（top-20 截断）当成了硬失败，也没有去找模型作者已经发布的 Ollama 评测文件。
- **规则**：
  1. 做选型前先写出评判标准与权重，标准不明确时直接问。
  2. 宣称某方案「硬失败」之前，先找第一方实测数据（模型仓库的 `evaluation/`），并算出失败的实际规模。
  3. 区分「影响选择结果」与「影响概率数值」——前者才可能是硬失败。
  4. 我写进文档的能力（如续传）必须有证据，没实测的标注「待 P0 确认」。

## 2026-10-14 · 批量处理 worktree 前先确认它真是 linked worktree

- **发生了什么**：磁盘清理时，`xDAN-MultiModal-Mediation-Agent-Expert` 这个主检出出现在另外三个仓库的 `git worktree list` 里，脚本把它当成 linked worktree 做了 WIP 提交。git 拒绝删除主检出，提交随后用 `reset --mixed HEAD~1` 撤回。
- **规则**：对任何路径做提交或删除前，用 `git rev-parse --absolute-git-dir` 与 `--git-common-dir` 比较；两者相同就是主检出，一律跳过。路径在多个仓库的列表里出现时也要跳过并报告。

## 2026-10-14 · 设计前先确认「消费者在目标产品里真的存在」

- **发生了什么**：设计稿把「云端判断不稳 → 改本机」「隐私拦截 → 在本机判断」写成桌面引导时机，但开工后才发现标准 DSH 桌面根本不装载 System3/Jev，只有独立的 System3 桌面前端装载。交付形态因此在实现阶段改为「可选 bundle + 运行时切换」两条路。
- **规则**：设计任何「在产品 X 里接入能力 Y」之前，先在 X 的 profile/打包闭包里（`packages/bundle/*`、`OPTIONAL_BUNDLES`、`apps/*/package.json` 依赖、`deploy/*` patch）确认 Y 的上下游插件确实被装载，并把证据写进设计的「现状」表。

## 2026-10-14 · 先查仓库的文档门禁，再按全局约定落盘

- **发生了什么**：按全局约定把交接文档写成只有中文的 `docs/<worktree>/tasks/*.md`，集成时 `test:docs` 报配对、换行、提交号三类失败，需要补英文译本、重排段落。
- **规则**：在本仓库，`docs/**` 下的任何 Markdown 都必须是中英配对（`X.md` 英文、`X.zh.md` 中文、`X.i18n.yaml` 记录），一段一行，不写提交号。新建文档时直接按配对创建，每次修改同步两种语言并运行 `pnpm run verify-translation-pairing --write <X.md>`。
