一、三条铁律

这三条决定了所有文案和状态的写法。违反任何一条，用户都会产生一个我们无法兑现的预期。

决策模型不是聊天模型

APUS Reflex 收「状态 + 指令 + 2–16 个候选」，输出候选上的概率分布。它负责判断，不负责回答。所以「本机」不等于「离线可用」，功能名必须叫本机决策引擎，绝不能叫「本地模型」或「离线模式」。

首次价值路径上不放下载

新用户到第一次成功对话之间，不允许出现数 GB 下载。配置密钥约 30 秒即可用；本机决策引擎是用起来之后的加深项，用渐进披露的方式邀请，不做阻塞门。

本机失败不偷偷换云

延续现有「仅本机策略会阻塞，绝不会悄悄换云」。本机判断超时或崩溃时，沿用既有确定性兜底（fallbackTimeout / fallbackUnavailable）并在界面说明，切云端必须是用户当次的显式动作。

二、用户心智：两个轴，三种档位

当前产品把「账号已登录」和「模型已配置」混在一起判断，这是弹窗逻辑出错的根源。正确的模型是两条互不相干的轴。

轴含义取值缺失后果
生成谁来写出回答账号 / API 密钥 / 第三方 / 本机端点应用不可用 —— 这才是弹窗的真正触发条件

两轴组合出三种对用户有意义的档位。设置页按这个顺序呈现，不要让用户自己拼。

四、关键界面

S1 · 登录后就绪弹窗

触发条件是生成轴不可用的边沿，而不是「没有 API 密钥」。如果账号登录本身已经提供可用的生成线路，就不该弹——对一个刚登录成功的用户索要密钥是缺陷，不是功能。代码里已经有正确的判据（模型页的就绪判断函数会区分「有可用提供商」「缺密钥」「不可用」三类），而登录成功通常本来就让账号路由变成可用提供商。

所以真正要修的不是新增一套判断，而是三处既有行为：桌面端把自动缺密钥提示无条件关闭了；桌面引导只在未登录时检查密钥，已登录路径完全不做就绪检查；原生 welcome 窗口的判定是「未登录且无密钥」，登录成功后就不再看。

Ollama 的实测并不差（raw 模式选择 80/80 一致），它唯一的优势是我们少写 1–2 周代码；但多一步安装和截断都直接落在用户体验上。

延迟是本功能的生死门，不是优化项。训练契约把状态放前、任务放后，所以每次判断都要重算任务段，约 0.4–0.6 秒是结构下限；新对话首次判断约 1 秒 / 1k token（M5 基础款），旧芯片更慢。一个 4 问请求暖态约 2 秒、冷态约 6 秒。P0 必须拿真实决策点和云端判断做对比；暖态 p95 若不优于云端，本机决策引擎默认不开启。

九、协议落差：Harness 的请求与训练契约不是一一对应

这是整个方案里最被低估的部分。现有 JevRequest 与模型契约有三处实质差异，不处理就会静默产出错误的判断。

维度Harness 请求模型契约后果
每次请求的问题数一次最多 16 个问题一次一个 primitive + 一组候选一个请求要跑 N 次模型调用，延迟按问题数放大；N 个问题共享同一状态前缀，是前缀缓存的用武之地
每题候选数最多 255 个标签只有 A–P，16 个超过 16 个候选的问题本机无法表达，必须显式拒绝并退回确定性兜底；不得分批或淘汰赛
score 语义有序档位，答案是 Σ i·pᵢ 的数值score_level 要求规范的是非候选集，返回 yes 概率不能直接映射。必须把有序档位渲染成 choice（A–P），再在本机按 Σ i·pᵢ 还原数值与档位说明
noul可选是非描述，答案是真值概率同样要求规范是非候选集可直接映射

以及一处不会报错的实现陷阱

训练契约的 prompt 由 Python json.dumps(task, ensure_ascii=False, sort_keys=True) 渲染。TypeScript 里用 JSON.stringify 直译会产出不同的字符串——Python 默认分隔符是 ", " 与 ": "，JSON.stringify 不带空格。

渲染方输出片段
Python 契约{"criteria": [{"description": "Close…", "label": "A"}], "instructions": …}
JSON.stringify 直译{"criteria":[{"description":"Close…","label":"A"}],"instructions":…}

字符不同即 token 不同，模型收到的是一个它没被训练过的 prompt。它不会报错，只会给出偏移的分布——这类缺陷在功能测试里完全看不出来。因此 prompt 渲染必须有一组由 Python 契约生成、随仓库固化的黄金样例，覆盖中文、引号、换行、emoji 与控制字符，并逐字节比对；同时保留候选字母「在作答位置必须是单 token」这项校验，缺一不可。

十一、待产品确认

运行时（随包 llama-server）与格式（GGUF）已定稿。剩余：

  • 首发是否只做 mac-arm64。
  • 账号登录若已提供可用生成线路，是否仍要求配置官方 API 密钥。本设计默认不要求。
  • 权重下载走 Hugging Face 直连与镜像，还是迁到自有 CDN 或魔搭。
  • 本机判断失败时，是否允许用户在当次任务里显式切到云端；默认隐私策略是否保持仅本机。
  • 自检通过后是否自动启用（本设计默认是，配 Toast 撤销）。
  • 是否接受 runner 的长期维护责任：安全更新、上游跟进、每次升版的分布复验。
