二、一条消息的完整流程

以“运行中补充要求、交给 Codex 的任务”为例。虚线框是规划中的环节。

  1. 用户 → 输入框
    用户发出消息；说“交给 codex”会直接委派。
  2. System3 · Jev
    入口路由：一次 Jev 判断（0.3–1 秒）选出模型或委派；路由行立即出现在这一轮开头。
  3. System3 · 后台
    任务卡：第一条消息建立任务卡（或用 /goal 的目标）；之后每条消息在后台由 Jev 判断要不要记，不让步骤等待。
  4. DSH · 主模型
    主模型执行；任务卡作为运行时上下文追加在历史末尾，缓存前缀不变；委派时交接包把更早的要求原话带给 Codex。
  5. System3 · 工具前后
    日志折叠去掉重复的失败输出；过程监督在重复失败、没有进展、没验证时提示模型。
  6. 用户 → 排队
    用户运行中补一句；插话分流约 1 秒判为当前任务的要求、纠正或打断，就插入正在运行的这一轮，并通过 steerByParent 转给运行中的 Codex；dock 提示“已插入正在进行的这一轮”。
  7. Codex · DSH
    Codex 照做；Codex 卡片显示进度和“已补充”；主模型核对产物后回复。
  8. System3 · 规划
    完成核验：标记完成前按任务卡逐条核对；约束守护：修改前检查是否违背用户原话。

每一步的判断都写入会话日志（完整的 Jev 请求与响应），刷新或回放时不再调用模型。

六、下一批 P0：可靠执行的三个增量

拟议定位：接得住要求，执行有约束，完成有证据。

保留已经批准的完成核验和线路质量监控；mu 的三个增量按下表提前。总顺序为任务卡验收 → 执行前约束 → 完成核验 → 普通任务续跑 → 卡住恢复，线路探针并行。新增能力的具体设计待确认，尚未实现或通过真实 E2E。

新增顺序拟议招牌表达架构接入真实验收
1 · 执行前约束你说别改的地方，动手前拦住独立人类指令来源 + 原生权限 + tools/pre-execute；覆盖只读工具与受支持委派，模型目标不能撤销要求初始与追加要求不丢失，禁止文件 hash 不变、禁止只读工具未执行，替代修复通过；撤销与子代理反例
2 · 普通任务续跑说了接着做，就真的接着做自然停顿处语义判断；复用原生 steer、取消与预算，避开 goal 的现有续跑真实承诺变为工具执行；已完成、等人工、等审批及用户停止零额外轮次
3 · 卡住恢复卡住会换路，结果能验证过程规则触发 Jev 语义复核，按执行证据提示换方法；不自动回滚文件重复失败后实际换方法并通过测试；合法轮询、必要排查和收敛调试不被误伤

完成核验本轮已用真实 DeepSeek、Jev、原生 Goal 和文件工具通过基础及追加要求两个场景，并验证日志重开；另有当前本地 built Web 提前拒绝→真实读写→完成及刷新复现；结果不替代生产升级、专用依据 UI 和独立题库评测。具体文件、接口、降级与正反例设计 · 14 项招牌、8 组原生能力与新增 P0 的验收排程
