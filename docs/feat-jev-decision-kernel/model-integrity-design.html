模型降智与偷换监控（模型线路核对）

目标：每条模型线路都能回答“它还是不是它声称的那个模型、有没有变差”。只展示证据，不做未经证实的归因；证据充分时自动避开这条线路。

1. 真实可行性验证（今天已跑）

同一批题目（每次随机生成操作数，中转站无法缓存答案）发给 6 条线路，每条 25 次请求。对照组设计：官方 Pro 对中转 Pro 是阴性对照，同一个模型，应该一致；官方 Pro 对官方 Flash 是阳性对照，模型不同，应该能区分。

有效：分词指纹

固定提示的 prompt_tokens 由分词器和服务端模板决定，结果确定、成本约 40 token。阴性对照两组都完全一致（88 = 88，35 = 35），阳性对照能区分（88 ≠ 35）。

新发现：GPT-5.6 中转注入了约 4.4K token 的隐藏提示

同一句 “Reply with exactly: OK”，GPT-6 线路计 11 个 token，GPT-5.6 线路计 4391 个。说明中转在请求前加了一大段我们看不到的提示，每次请求都要为它付费，也可能影响回答。这正是监控要暴露的问题。

有效：上游通道变化

LiteLLM 响应头 x-litellm-model-id 标出实际走的上游通道，通道一换就能记录下来，例如 0.4x 换成 0.2x。这能说明配置变了，但说明不了模型变了。

无效：回包里的 model 字段

6 条线路都原样回显请求时用的别名，用它核对等于没核对。模型的自我介绍也不可信：GPT-5.6 和 GPT-6 都自称 “GPT-5”。两者都不作为判断依据。

需加强：能力题

4 位乘法、数字母、数位和、倒写这几道题，Pro 和 Flash 都是 17/18，区分不开。降智检测需要更难、能拉开差距的题，每条线路累计至少 20 个样本，并用置信区间比较，不能凭一两次失败下结论。

注意：错误率要在服务器上测

本机测试里，官方线路也出现 SSL 中断（2–3 次 / 25），是本机网络的问题，不是线路的问题。延迟和错误率只采信 prd 服务器上的线路健康数据。

2. 判断依据与动作

依据怎么测基线异常时
分词指纹每条线路定期发送一组固定提示（3 条长度不同），记录 prompt_tokens有官方直连的模型（DeepSeek）用官方线路的值；没有直连的（GPT 中转）用这条线路首次核对的值，并人工确认连续 2 次不一致：状态改为“已避开”，dock 和线路行显示证据
隐藏提示同一组固定提示的 token 数减去分词基线同上多出 500 token 以上：提醒，不避开（可能只是中转的配置）
上游通道记录探针响应头 x-litellm-model-id上一次的值变化就记录一条“配置变化”，并把能力题基线标为待复核
能力题随机操作数的精确答案题（改为更难的一组），累计样本该线路最近 7 天的通过率；有官方线路的同时对比官方通过率比基线低，且 95% 置信区间不重叠：状态改为“可疑”；连续两个窗口都可疑才避开
延迟与错误沿用现有线路健康（prd 实测）现有阈值沿用“已避开较慢的线路”

Jev 的位置。判定以可复核的规则为准，因为精确率优先，避免误伤正常线路。Jev 先以影子模式回答一个封闭问题：给定这些派生出的证据，这条线路是“正常 / 配置变化 / 疑似降级 / 证据不足”中的哪一种。标注集达标后，才允许 Jev 参与“可疑”这一档的判断；“已避开”始终要求规则证据。

4. 实现方案

  • 新模块 packages/experimental/system3/src/route-integrity.ts：挂在现有线路健康的探针调度上，不另起定时器。探针不走 pi-ai，而是按 provider 配置（baseURL、apiKeyEnv）直接发 HTTP，因为 pi-ai 不暴露响应头。
  • 配置（cordis.yml 的 routeIntegrity，全部可调）：mode（off / shadow / active）、intervalMs、fingerprintPrompts、referenceRoutes（例如中转 Pro 对应官方 Pro）、capabilityWindow、hiddenPromptTokens、dailyBudgetTokens。
  • 状态：基线和核对历史跨会话保存，存进 DSH storage 的 system3 命名空间，不写会话日志；线路状态并入现有线路健康的视图，路由避开时复用现有理由字段。
  • 会话日志：只有核对结果改变了本轮路由时才记录，即给已有的路由事件新增一个可选的避开理由 integrity（同版本内新增可选字段）。“模型可见的内容都能从日志重建”这一条不受影响。
  • 成本：分词指纹每次约 120 token，能力题每次约 2K token。按每条线路每 30 分钟一次计算，6 条线路一天约 60 万 token，受 dailyBudgetTokens 封顶。

5. 验收计划

  1. 单元测试：覆盖率 100%，包括指纹比较、隐藏提示、通道变化、置信区间、预算封顶、出错回退。
  2. 真实 e2e：阴性对照，官方 Pro 与中转 Pro 连续核对 24 小时，要求零误报；阳性对照，配置一条测试线路，宣称是 deepseek-v4-pro，实际指向 deepseek-flash，要求在 2 次核对内标为已避开。
  3. prd 浏览器验收（新增 accept.py 场景 route-integrity）：在 prd 用 overlay 打开这条“偷换”测试线路，从用户视角确认 dock 显示“已避开：…（分词指纹与基线不符）”，执行依据可展开看到证据，正常线路没有任何提示。
