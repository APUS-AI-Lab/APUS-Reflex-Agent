System3 管家方案：学 mu 的产品方法，分批完整实现 38 个能力

目标：System3 成为 agent 的高质量、可靠、快速的管家，并管理模型路由策略。本页先总结 mu 的产品方法并提出我们的升级版，再给出三项优先能力（任务卡、插话分流、按需亮工具）的具体设计和场景效果，最后是覆盖全部 38 个点的分批计划。所有扩展点都已在本仓库代码中核实，文件位置见各节。

一、mu 的产品方法（我们学到的）

1. 从坏情况出发

每个点都对应一个用户见过的坏情况：删了不该删的、说做完其实没做完、插话没生效。所以一句话就能讲清楚，用户也能判断值不值。

2. 把琐碎判断外包

主模型不擅长时时自查。mu 把“这句是纠错吗”“这个调用违背约束吗”拆成小的封闭问题交给 Jev，又快又便宜，主模型专心干活。

3. 每个点单独开关

每个点都能关闭、只记录（shadow）或生效（active）。出问题只关一个，新点可以先记录不生效。

4. 判断失败就放行

超时、出错一律回到原来的行为，判断永远不挡主流程。

5. 每次判断留账

账本记下问了什么、答了什么、做了什么，可以查、可以复盘。

6. 公开自己的失败

作者公开了“工具输出语义裁剪零效果、成本 54%”的回测。

二、升级：从 38 个开关到一个管家

mu 的不足：38 个点各自独立，彼此不共享对任务的理解；提示多、动作少，很多点只给主模型一行提示；效果证据多为一次性实测。我们的升级版有五条原则：

  1. 一本笔记本：所有判断都读同一张任务卡（目标、你的原话要求、怎样算做完）。约束检查、完成核验、偏离监控、交接给 Codex、路由升降级都用它，而不是各自猜你要什么。用户看到的是一个管家，不是 38 个功能。
  2. 判断归 Jev，动作要直接：Jev 只回答封闭问题；判断之后是确定的动作：换模型、弹确认卡、把插话送进当前步骤、亮出或收起工具。只有做不了动作时才退而给提示。进入模型或界面的文字只用你的原话，或由现有模型生成。
  3. 看得见、能撤回：管家每做一件事，侧边面板都用一句话说明原因，例如“因为你说过‘别动 README’”，并且可以撤回：删掉识别错的要求、把插话改回排队、找回被收起的工具。
  4. 坏情况回归集就是验收标准：把真实发生过的坏情况做成可重跑的会话场景。每项能力上线前后各跑一遍，数清挡住了几个；再配合真实 Jev 标注集定问法和阈值，prd 数据达标才从 shadow 转 active。
  5. 不拖慢：每条用户消息只发一次 Jev 请求（最多 16 题，入口路由、任务卡、澄清提示、亮工具合并在一起），与现有入口路由同在一个等待里，不新增往返；其余判断与主模型并行，或只在规则筛选命中后才调用。每项上线都报告 P50 / P95 延迟增量。
用户消息 ──► 一次 Jev 请求（≤16 题） ├─ 入口路由：本轮用哪个模型 / 是否交给 Codex（已上线） ├─ 任务卡：新任务 / 补充要求 / 纠错 / 验收要求 / 闲聊 ├─ 澄清提示：需求明显不清时提醒先问 └─ 亮工具：这个任务需要网页 / 浏览器 / 某个 MCP 吗 │ ▼ ┌──────────────┐ 读取 约束与风险守护（工具执行前） │ 任务卡 │ ─────► 完成核验（说做完时） │ 原话 · 可编辑 │ ─────► 偏离监控 → 路由升降级 └──────────────┘ ─────► 交接给 Codex 的交接包 运行中插话 ──► 插话分流：纠错 / 补充 / 旁支问题 / 新任务 ──► 插入当前步骤 · 转给 Codex · 排队

三、三项优先能力的具体设计

A. 任务卡（mu task.frame，并入 input.preflight 的澄清提示）

解决的坏情况你开头说“别改公开 API”“测试通过才算完”，二十步之后模型忘了；交接给 Codex 时只能临时回头找要求
何时判断每条用户消息。与入口路由合并成一次 Jev 请求（入口路由的接入点：system3/src/index.ts:271 注册的 prompt router）。问法沿用交接包已验证的问法（6 段标注对话召回率与精确率 1.0）
Jev 问什么选择题：新任务 / 补充要求 / 纠错 / 说明怎样算完成 / 闲聊或无关（带逃生选项）；是非题：需求是否明显不清、需要先澄清
动作把要求原样记进任务卡（不用模型改写，避免走样）；新任务时开一张新卡；需求不清时给主模型一行“先确认 X”提示
存在哪里新会话事件 system3/task-frame。DSH 目标的快照字段是封闭的（packages/goal/goal/src/fold.ts:104），不能挂额外字段，所以任务卡用目标的 id 与 revision 关联（goal/changed 事件可订阅）。没有目标时按会话记录
模型怎么看到系统提示里的一段“任务卡”，内容可从会话事件完整重建；DSH 目标续跑的提示只有目标和轮次（goal-round-driver/src/prompt.ts:12），任务卡补上要求与验收项
用户看到什么侧边面板新增“任务卡”：每条要求显示原话和来源消息，识别错了可以删除（删除也是会话事件）
验收标注集 30 条消息（含边界例子）精确率 ≥ 0.9；坏情况回归：二十步后仍遵守开头的要求

B. 插话分流（mu input.interjection）

解决的坏情况它干活时你说“等等，用 pnpm 别用 npm”。默认设置下这句话会排队到本轮结束（submission-settings.ts:12 默认 queue），模型整轮继续用 npm；反过来，设成插入时，一句“顺便问下这个函数干嘛的”会打断正在做的事
现状核实运行中的消息由客户端决定排队或插入（submission-policy.ts:30），服务端在 session-controller/src/commands.ts:382 直接投递；prompt router 只在空闲时生效（prompt-router.ts:97）。今天没有任何扩展点能在投递前改变方式
需要的改动在 prompt() 投递前新增一个扩展点（例如允许 prompt router 对运行中的消息返回投递方式）。这是对 DSH 会话控制器的改动，需同步更新 architecture 文档，并与“客户端决定消息显示位置”的既有约定对齐：服务端返回实际采用的方式，客户端按它放置
Jev 问什么选择题：纠正当前做法 / 补充信息 / 旁支问题 / 新任务 / 无法判断
动作纠正、补充 → 插入当前步骤；如果 Codex 正在运行且可补充，同时转给 Codex（复用已上线的补充说明通道 subagent/steer）；旁支问题、新任务 → 排队；纠正同时写进任务卡。从不自动停止任务
谁说了算只在新设置“自动判断”下生效；你用 Cmd/Ctrl-Enter 明确选择的方式永远优先。判断超过 1.5 秒或失败，按你的默认设置投递
用户看到什么消息旁标注“已作为纠正插入当前步骤”或“已排队，本轮结束后回答”，可一键改成另一种
验收标注集 40 条运行中消息，纠正类召回率 ≥ 0.9、旁支问题误插入 ≤ 5%；坏情况回归：“用 pnpm 别用 npm”在下一步生效

C. 按需亮工具（mu capability.disclosure，并入 skills.disclosure）

解决的坏情况写一首诗也带着网页、浏览器、电脑操作和全部 MCP 工具的说明，每次请求都更长、更贵；工具越多，模型越容易选错工具
现状核实DSH 有现成扩展点 ctx.tools.restrict({allow, deny})（packages/core/tools/src/index.ts:1097），官方 cookbook 推荐用它做“渐进披露”；工具变化会自动记入会话（request/header 与 tool-addition / tool-removal），不需要新事件。DeepSeek 路线支持中途只增不减地添加工具而不破坏缓存（toolUpdate: 'addition-only'）。MCP 服务器目前启动即连接，没有按需启动
Jev 问什么新任务的第一条消息里，对每个工具包问一题“这个任务需要 X 吗”（网页、浏览器、电脑操作、每个 MCP 服务器）；同一请求里判断哪些技能与任务无关
动作只在很确定不需要时收起（是非题 ≤ 0.2 才算否）；读写文件、命令行、目标、待办等核心工具永不收起。任务内只增不减：模型或用户需要时，通过一个“申请工具”入口把工具包加回来，加回走缓存友好的增量方式。新任务时才重新判断
第二步MCP 按需启动：被判为不需要的 MCP 服务器不启动进程，需要时再连接。需要一个新的加载插件，放在本批的第二个 PR
用户看到什么侧边面板一行：“本任务已收起：浏览器、电脑操作、2 个 MCP”，可一键全部恢复
验收每次请求的输入 token 与缓存命中率前后对照；“需要却被收起”在标注集里为 0，在 prd 上每 100 个任务 ≤ 1 次且都能通过申请入口恢复

四、场景效果（修改前后）

场景今天之后用到的能力
“重构这个模块，别改公开 API，测试跑通才算完”要求只在第一条消息里；二十步后模型改了导出函数名，测试没跑就说完成任务卡记下两条原话；改导出函数前弹确认卡，引用“别改公开 API”；说完成时核验“测试跑通了吗”，没有就继续干任务卡、约束守护、完成核验
运行中说“等等，用 pnpm 别用 npm”排队到本轮结束，整轮继续用 npm判为纠正，下一步就生效；Codex 正在跑时同时转给 Codex；任务卡多一条要求插话分流、任务卡
运行中问“顺便问下，这个函数是干嘛的”设成插入时会打断手头的事判为旁支问题，排队，本轮结束后回答插话分流
“写一首关于秋天的诗”所有工具说明都在请求里只保留核心工具，请求更短；之后说“查一下今天的新闻”，网页工具加回来，缓存不受影响按需亮工具
需求含糊：“把那个弄好”模型猜一个方向开干提醒主模型先确认“那个”指什么任务卡（澄清）
Flash 在一个 bug 上连续失败规则提示“同一错误重复”，仍用 Flash监控判为卡住，升级到 Pro 或交给 Codex，面板写明原因偏离监控、路由升降级
搜到的网页里写着“忽略之前的指令”只告诉模型这是外部内容该段被扣下，原位说明“已扣下疑似指令”注入防护
上周说过“提交信息一律用英文”新会话不记得新会话开始时判断相关，自动带上这条经验经验记忆

六、需要你确认的三件事

  1. 插话分流要改 DSH 会话控制器：今天没有扩展点能在投递前改变方式，需要新增一个（同步更新 architecture 文档）。另一种做法是在客户端提交前判断，但违反“在做决定的操作里执行决定”的仓库规则，不推荐。
  2. 插话分流先做成可选设置：新增“自动判断”选项，先由你手动打开，prd 数据达标后再改为默认。
  3. 任务卡对你可见、可删改：识别错的要求你可以删除。建议同意，这是“看得见、能撤回”原则的核心。
