Jev 判定内核：约束检查与过程监督复核

落实 mu 对照分析里证据最硬的三项：统一判定格式、修改前检查用户约束、规则触发后让 Jev 复核。确认后再开发。

一句话：把“问 Jev 一道题、按阈值决定动作、失败回退、写进会话日志”做成一套统一格式，在它上面实现两个新判定。修改文件或执行命令前，检查是否违反用户说过的要求，违反就请用户确认。过程监督的规则触发后先问 Jev，Jev 确认了才提醒，以去掉误报。新判定默认只记录（shadow），用线上数据证明有效后再开启。

为什么做这三项

一、统一判定格式（判定内核）

interface System3DecisionSpec<Input, Outcome> {
  id: string                       // 例如 'constraint.check'
  version: number
  mode: 'off' | 'shadow' | 'active' // 部署配置决定，默认 shadow
  deadlineMs: number               // 超时即回退，不阻塞主流程
  questions(input): JevQuestions   // 一次请求可含多题
  decide(answers, input): Outcome  // 按阈值得出结论，含“拿不准”
  fallback: Outcome                // 超时、出错、隐私拒绝时的结论
}
  • 阈值规则统一：是非题 ≥ yes 阈值算“是”，≤ no 阈值算“否”，中间算“拿不准”并走回退（借鉴 mu 的 0.8 / 0.2；按每个判定的实测数据单独配置）。
  • 记录：每次判定写一条 system3/judgement 会话事件：判定 id、版本、模式、完整请求与响应、结论、是否实际生效、耗时。shadow 模式也完整记录，用来事后统计误报率。
  • 隐私准入：复用现有的数据类别与执行位置准入，不通过就回退。
  • 范围：本期只让两个新判定使用内核。入口路由、Skill 选择、交接包保持现有事件格式不动（已有会话数据），下一期再迁移。

二、修改前检查用户约束

约束从哪来

  • 每条用户消息进入时，用一道是非题判断它是否包含“仍然有效的工作要求”（复用交接包已实测的问法，召回率与精确率均为 1.0）。
  • 判为“是”的消息原文写入 system3/constraint 会话事件，保留最近 6 条。这一步并行执行，不增加用户等待。
  • 交接包改为直接读取这份约束清单，不再在委派时临时识别，省掉一次 Jev 请求。

什么时候检查

  • 只在有约束时检查，且只检查会修改东西的调用：write、edit、委派工具，以及 bash（先用规则排除明显只读的命令，如 ls、cat、grep、测试命令）。
  • 一次请求、每条约束一题：“这个调用会违反用户这句话吗？”，附调用的工具名与参数摘要（文件路径、命令文本，不含大段内容）。

违反时怎么办

模式行为
shadow（默认）只记录判定，不影响执行；dock 显示“这一步可能违反你说过的要求”的提示
active返回 ask：弹出原生审批卡片，说明“你说过：〈原话〉”，由用户决定是否继续；用户拒绝时，模型收到拒绝理由并换做法

不做硬拦截（deny）：用户可能改主意，判定也可能错，最终决定权留给人。

三、过程监督复核

  • 现有规则（同一错误重复、失败次数、连续无进展、缺少验证）照常发现疑点。
  • 触发时把最近若干步的工具调用与结果摘要交给 Jev，问一道题。例如“连续无进展”问：“这几步是在有效推进（如查资料、读代码定位问题），还是在原地打转？”
  • Jev 确认才提醒主模型；否定则只记录，不打扰。拿不准时按规则原样提醒（保持现状，不降低安全性）。
  • 只在规则触发时调用，平时零开销。

验证计划

  1. 单元与组合测试：新代码覆盖率 100%；每个判定都测超时、出错、隐私拒绝时的回退。
  2. 真实 Jev 标注集（先做，用来定阈值）：
    • 约束检查：20 个“工具调用 × 约束”样本，一半违反，一半不违反，含容易误判的近似情况（如约束“不要改 README”，调用为读取 README）。
    • 监督复核：20 段真实工具轨迹，含本项目线上出现过的 2 次误报与 1 次漏报原样，以及真正卡住的样本。
    目标：约束检查精确率 ≥ 0.9（宁可漏不可错拦），监督复核去掉已知误报且不漏掉真卡住。达不到就调整问法，不调宽阈值凑数。
  3. 修改前后对照：用 10-06、10-07 线上出现过的场景原样复现，对比修改前后是否提醒。
  4. prd shadow 运行：发布后先 shadow，统计判定次数、误报率、耗时，数据达标再按判定逐个开启 active。
  5. 门禁：build、typecheck、lint、全量单测（只允许已知的 3 个上游失败）、doc-sync。

代价与风险

项目估计缓解
延迟约束识别并行执行，不增加等待；约束检查每次修改类调用约 0.3–0.6 秒，只在有约束时发生；监督复核只在规则触发时发生每个判定设超时，超时放行
Jev 用量每条用户消息 1 次；每次修改类调用在有约束时 1 次只读命令先用规则排除；一次请求合并多条约束
误拦判定错误会让用户多点一次确认默认 shadow；active 用 ask 而非 deny；精确率不达标不开启

需要你决定

  1. 范围：三项一起做（约 3–4 天，含标注集与 shadow 观察），还是先做约束检查（约 2 天）？
  2. 开启方式：上线默认 shadow，观察一段时间看数据再开 active（推荐）；还是约束检查直接 active（用 ask 让你确认）？
  3. 入口路由等已有判定：本期不迁移到内核（推荐，避免改动已有会话数据格式），还是一起迁移？
