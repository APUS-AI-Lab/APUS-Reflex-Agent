mu 38 个判定点：横向对照与 Top 10

北极星：System3 是 agent 的高质量、可靠、快速的管家，也是模型路由策略网络的管理层。文章写 35 个，是 mu 旧版 README 的数字；代码里是 38 个（10-05 新增注入检测、继续判断、批量判断工具）。本页按“目标维护、跟踪、监控”主线，把 38 个点去重合并成 10 项能力，并说明每项如何利用 Jev 的特点、如何避免与 System3 和 DSH 已有能力重叠。

结论
  • 目标是主线：DSH 原生 goal 包已能保存目标、让模型自报完成、空闲时自动续跑，但完成与否全凭模型自己说，没有验收项、没有偏离判断、没有独立核验。前三项（目标框架、完成核验、进度与偏离监控）正好补上“监督”这一层，且不另建目标存储。
  • 去重：mu 里有 6 个点都在管“目标与完成”（task.frame、goal.met、turn.completion、turn.continue、turn.drift、board.read），合并成 3 项；工具执行前的 3 个点（tool.constraint、tool.risk、tool.approval）共用一次 Jev 请求；技能与能力披露并入现有的 Skill 选择。
  • 路由是管理层的一根轴：入口路由只在用户发消息时选一次模型。管家发现卡住、答非所问或任务比预想难时，应能在运行中升级到更强的模型或交给 Codex，简单的后续再降回 Flash。新增第 7 项“运行中路由升降级”：仍是同一套路由策略（同样的候选、健康度、拿不准就保持），只是多了运行中的触发点，不另建第二个路由器。原第 4、7 项本就共用一次请求，合并为“约束与风险守护”，腾出名额。
  • Jev 的位置：Jev 只做“是非、选择、打分”，不写文字。所有进入模型或界面的文字都用用户原话或现有模型生成，Jev 只负责判断，这是每项设计的共同约束。

Jev 的特点决定了怎么用它

擅长

  • 封闭判断：是非（概率）、选择（含逃生选项）、打分；输出带概率，可设阈值和“拿不准”区间。
  • 快且便宜：热连接单次约 0.3–0.6 秒（prd 实测入口判断 0.29–0.97 秒）。
  • 一次请求多题：一个请求最多 16 题，适合“逐条约束”“逐个片段”的批量判断。
  • 确定性：同样输入给出同样结果（交接包两次实测结果完全一致），便于回放与评测。

不擅长与约束

  • 不生成文字：总结、改写、经验措辞要交给现有模型，或直接用用户原话。
  • 问法敏感：同一判断换个问法，召回率可以从 0.38 变到 1.0（交接包实测），每个判定都必须用标注集定问法和阈值。
  • 远程服务：受隐私准入约束，失败必须回退；连接卡死需防护（已上线 resetAfterFailures）。
  • 上下文有限：只能给它判断所需的摘要，不能给完整会话。

挑选标准

每个点按五项打分后合并：价值（用户能感到的改善或防住的事故）、频率（多常发生）、证据（mu 实测或我们线上发生过）、Jev 适配（是不是封闭判断、能否批量）、不重叠（是否已被 System3 / DSH 覆盖）。与已有能力重叠的点不单独成项，只作为对应项的补强。
