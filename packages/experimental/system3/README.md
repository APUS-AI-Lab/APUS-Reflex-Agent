# @deepseek-ai/dsh-experimental-system3

English | [中文](README.zh.md)

## Summary

Mount this service for local-first route admission, evidence selection, completion supervision, shadow comparison, and usage accounting. Optional observation leaves AgentLoop behavior unchanged. Separately, `entryRouting` enables Jev model recommendations for idle text prompts admitted through the Session API; the API owns adoption and cancellation.

## Use this package

Mount it in an experimental profile. The default policy is `local-only`; remote routes require explicit configuration and remain subject to the per-call candidate metadata.

```ts
import { Context } from '@deepseek-ai/cordis'
import System3, { type System3RouteCandidate } from '@deepseek-ai/dsh-experimental-system3'

const ctx = new Context()
const candidates: System3RouteCandidate[] = [
  { id: 'local-9b', executionDomain: 'local', dataClasses: ['public'] },
]
await ctx.plugin(System3, { privacyMode: 'local-only', observeAgentLoop: true })
const decision = ctx.system3.route(candidates, 'local-9b')
```

`ctx.system3.snapshot()` exposes only operation counters, never user text or tool output. Callers persist the returned spans, supervision reasons, shadow comparisons, and cost records in their own durable Session/audit layer.

`frontLoadedDecisions` (default `true`) is a live switch for the decisions System3 makes before the main model: Session API entry routing, Goal entry routing, Skill selection, the task frame, and prefetch. Because it is volatile, the entry's settings form edits it and the next request reads the new value without a reload. While it is `false`, new requests take the native path: none of these decisions asks Jev, runs prefetch commands, or appends a System3 record, keep-warm sends nothing, and the `entryRouting` and `skillSelection` capabilities report `enabled: false`, with `suspended: true` when installed. Work already started finishes, a task frame recorded earlier stays in the prompt, and restored Goal delegations are still settled. Process and Reflex supervision, Reflex context, completion review, and output folding do not follow it.

The package is also a profile bundle: its `cordis.patch.yml` inserts the `system3` row with the APUS Desktop and Web product defaults (controlled privacy, the `jev` route on the network domain, and Skill selection). The products list it after the Jev bundle instead of inserting the row from their command-line overlay, because an overlay row would override every profile settings write; a `frontLoadedDecisions` edit in the profile patch therefore persists across restarts.


### Explicit Jev shadow decisions

Mount the Jev plugin beside System3, then call `shadowDecision(session, request, signal)` with classified decision facts and independent supervisor checks. System3 constructs the Jev state from those checks and goal metadata; it accepts no raw task or tool text. System3 generates the closed action candidates. The returned receipt retains the deterministic baseline even when Jev suggests completion. Timeout, invalid response, a missing provider, or denied privacy admission yields `unknown`. Caller cancellation records a cancelled receipt and rejects.

Privacy admission uses the execution domain of the Jev provider each decision resolves to: a provider that declares `executionDomain`, such as the local Reflex engine (`local`), supplies its own, and receipts record the domain admission checked. `jevExecutionDomain` (default `network`) applies only to providers that declare none, such as the built-in gateway provider; set it to `local` only when that gateway actually executes on the same host. A loopback SSH tunnel to RunPod is still `network`. A request built after an awaited lookup is pinned to the provider admission checked. Controlled remote execution requires the configured `jevRouteId` (default `jev`) and every input data class in the privacy allowlists. `jevEffort` selects `low` or `high` (default `low`).

Each explicit call appends `system3/decision` with a state digest, evidence references, model identity, full answer probabilities, usage when reported, and the unchanged baseline. The complete structured Jev payload is recorded for reconstruction; raw task text, tool output, and provider error text are omitted. `lastDecision(session)` reads the latest projected receipt from a live or restored Session without invoking Jev. Evidence references identify external checks; evidence storage remains the host's responsibility.

### Session API entry routing

`entryRouting` defaults to `false`. Enabling it requires `candidates`, `sessionDataClasses`, `minConfidence`, and `maxInputBytes`. Each candidate declares a unique `id`, task `description`, generation `provider` and `model`, optional `reasoningEffort`, actual `executionDomain`, and allowed `dataClasses`. Candidate ids use lower-kebab-case; `abstain` and `unknown` are reserved. Duplicate model/effort selections are rejected. `sessionDataClasses` conservatively classifies the whole session that generation may read, not just the new text; the host owns this classification.

Candidate and Jev network admission both use the privacy policy before sending task text. Candidate metadata must expose context capacity at least as large as the baseline and support every baseline input modality; unknown metadata excludes that candidate. Unsupported reasoning efforts reject configuration at the first model resolution. Jev receives only the current text, baseline model identity, and admitted choice descriptions, with an explicit abstain choice for missing context or uncertain selection. `maxInputBytes` bounds the complete resolved Jev request in UTF-8, including criteria and metadata. Oversized inputs are not truncated and retain the baseline.

`minConfidence` is an acceptance threshold, not a calibrated success probability. Abstention, low confidence, denied privacy, no compatible candidates, unavailable Jev, and provider failures return no override. With `retainOnAbstain: true`, abstention and low confidence instead continue the route chosen or retained by the Session's previous entry decision when that route is still an admitted, compatible candidate; the receipt records it as `retained` with the originating request id and carries no `selected`. Provider failures still keep the baseline. This option requires `sessionProjections`. A delegation candidate replaces `provider`/`model` with `delegate: { provider, tool }`, naming a registered subagent provider and its model-facing tool; it is offered to Jev only while that provider is registered and the tool is visible to the requesting Agent. Choosing it keeps the baseline model, records the target in the receipt's `candidate.delegate`, and injects one user message attributed to `system3-delegation` in the pre-step that first carries the input, asking the model to call the tool; the model may decline. The projection reports the injected instruction and the later tool call separately, and retention never continues a delegation. A delegation candidate's optional `explicitPatterns` lists case-insensitive regular expressions for mentions, such as `交给\\s*codex`; matching candidate ids enter the Reflex request as hints, never as execution authorization. Every delegation choice requires semantic selection, including affirmative requests. Negations, quoted examples and requests to analyze wording must not select delegation. Historical `explicit: true` receipts remain readable; new decisions do not emit that flag. Invalid or blank patterns fail at load. A candidate's optional `label` is recorded with the decision so the Client can name the route as soon as the decision arrives. `keepWarm: { windowMs, intervalMs }` sends Jev warm-up requests at that interval for `windowMs` after plugin start and after each turn ends, so the next entry decision reuses an open connection; set `intervalMs` below the gateway's idle connection timeout. Candidates must accept every input modality present in the Session: image input is required once a user message or tool result carries an image. Without the System3 runtime projection, candidates must accept every modality the baseline accepts. Cancellation rejects without authorizing prompt admission. A `system3/entry-decision` event preserves the exact Jev request (including text), validated response, and recommendation; `request` is null when no decision was dispatched. The host-only `providerId` in that request is omitted by the Jev HTTP serializer. The Session API's separate `model/automatic-selection` event identifies actual adoption with the same request id. Replaying either event performs no model call. Router registration is disposed with the plugin.

`entryRouting.handoffPack: { recentMessages, maxMessageChars, minProbability, deadlineMs }` reviews the person's earlier messages before the delegation instruction is injected. It takes the latest `recentMessages` (at most 16) committed text-only user messages of at most `maxMessageChars` characters, excluding the delegated input, and sends Jev one request with the delegated text in `state.task` and one yes/no question per message that quotes it and asks whether it is a working requirement still in force for the task, such as a naming rule, a file that must not change, or a check that must pass. Messages whose probability is at least `minProbability` are appended verbatim to the instruction, oldest first, with a request to write them into the delegated task and check the result against them. A `system3/handoff-pack` event records the exact request, the response, the outcome, and the ids of the forwarded messages before the instruction. Privacy denial, an absent or failing Jev, and a review exceeding `deadlineMs` send the instruction alone; cancelling the turn rejects the pre-step.

`entryRouting.deadlineMs` bounds baseline preparation, Jev advice, and selected-route preparation together (default 30000 ms; maximum `MAX_TIMER_DELAY_MS`). A timeout can admit only an already prepared legal baseline; incomplete baseline preparation rejects without inbox insertion. The baseline must match an admitted configured candidate or declare `baseline.executionDomain` and `baseline.dataClasses`; an independent remote baseline uses privacy route id `baseline`. Cancel and provider removal abort pending admission, and late advice never authorizes another admission. Native `resetModelSelection` restores automatic routing for later eligible inputs; a manual selection remains fixed until reset.

`entryRouting.routeHealth: { window, sampleTtlMs, minSamples, maxFirstTokenMs, minTokensPerSecond, minOutputTokens, maxErrorRate, probe }` measures every model stream that passes `llm/stream` in this context. Each completed stream records its first-token latency from the start of the stream, its output tokens per second after the first token when it produced at least `minOutputTokens`, and whether it ended with an error; cancelled streams record nothing. A route keeps its latest `window` samples younger than `sampleTtlMs`. With at least `minSamples` samples for a metric, a route is degraded when its error share exceeds `maxErrorRate`, its median first-token latency exceeds `maxFirstTokenMs`, or its median output rate falls below `minTokensPerSecond`, checked in that order. Entry routing leaves degraded model candidates out of the Jev request while another compatible candidate remains, records them with their reasons in the decision's `avoided`, and never avoids a delegation candidate. With `probe: { idleMs, maxTokens }`, each model candidate without a sample for `idleMs` receives a fixed request of at most `maxTokens` output tokens that contains no Session data, so an avoided route is measured again. Samples are process-local and start empty after a restart. The runtime projection exposes the avoided labels as `entry.avoided`, and the Client appends them to the route notice.

`delegationProgress: { intervalMs, monitor? }` writes `system3/delegation-progress` snapshots of every subagent run an Agent delegates to that Agent's Session: once at start, at most once per `intervalMs` while steps arrive, and once at the end with the stop reason. A snapshot carries the provider, start time, elapsed time, completed step counts per category, the step in progress, the time of the latest step, and the child's latest short progress note; it never carries commands, paths, tool input, or results and is not model-visible. With `monitor: { overtimeMs, stallMs, startupMs }`, System3 also writes `system3/delegation-alert` when a run has no first step within `startupMs`, once per stall after `stallMs` without a new step, and at every `overtimeMs` multiple. Snapshots also record whether the run accepts mid-run input (`steerable`). The runtime projection exposes the latest run as `subagentRun` with its note, unresolved alert, `steerable` while it runs, and the latest three `subagent/steer` texts it accepted; the Client shows the note, an alert with keep-waiting, steer, and stop actions, and a steer form that sends text through `subagents.steerByParent`. Only providers that report activity (Codex and Claude Code) produce running snapshots.

`processSupervision: { mode, repeatedError, failedAttempts, stalledSteps, delegateFailures, editTools, delegationTools, shellTools, progressTools, verifyPattern, failurePattern }` applies deterministic rules to each top-level Agent turn and writes `system3/process-notice` when one fires: the same tool failure `repeatedError` times (a failure key combines tool name, error code or exit code, and the first line of the result with digits folded), `failedAttempts` failed calls, `stalledSteps` consecutive calls without a successful edit, delegation, passing verification, or successful call of a `progressTools` tool such as web search or file reading, a turn about to end after edits or delegation without a passing verification (`missing-evidence`), and `delegateFailures` failed commands inside one delegated run. A shell call fails when its result is an error or reports a nonzero `exitCode`; because a command list or pipeline (`;`, `&&`, `||`, `|`) reports only its last command's exit code, one that exits 0 also fails when its output matches `failurePattern`. A verification is a successful shell call whose `command` matches the case-insensitive `verifyPattern`. Each rule fires at most once per turn and subject, and a person's new message starts fresh counts. `observe` only records; `advise` also gives the main model advice: tool-result rules attach it as additional context on the triggering result, and `missing-evidence` steers the turn once so the model runs another step. Delegated-run failures are recorded but never advised. Supervision never blocks, rewrites, or retries a tool call. The runtime projection exposes the current turn's latest five findings as `notices`, which the Client lists in the dock.

`outputFolding: { mode, shellTools, commandPattern, minLines, minChars, minNetChars, minNetShare }` folds repeated lines in the single-text result of a top-level `shellTools` call whose `command` matches the case-insensitive `commandPattern`, such as a test run that prints the same diff or stack for every failure. A run of at least `minLines` lines and `minChars` characters that repeats, byte for byte, earlier lines that stay becomes one marker naming the lines of the folded text it repeats, in order and with counts, so expanding every marker restores the output exactly; the marker also quotes the first line of the repeated block, shortened to 60 characters, so a person reading the terminal card can find it without line numbers. A run shorter than its marker stays. A result is folded only when it saves at least `minNetChars` characters and `minNetShare` of its text. Each fold writes `system3/output-fold` with the tool, folded line count, saved characters, and whether it was applied; `shadow` records without changing the result, `active` replaces the model-visible text. Error results, delegated sub-dispatches, and results whose `value` a later listener replaced are not folded; the tool's structured `value` keeps the complete output. The rule follows mu's test-log admission (MIT).

`taskFrame: { mode, yes, no, deadlineMs, sessionDataClasses, maxItems, maxMessageChars, interjection? }` keeps the person's goal and later requirements for each top-level Agent. Creating a DSH goal starts the frame from its objective, editing the objective updates it and keeps the requirements, and while the goal is neither complete nor cleared no message replaces it. Without an open goal, the first plain-text message of a Session starts the frame. Each later message up to `maxMessageChars` is judged after its step claims it, so the step does not wait unless Reflex context review is enabled: one Jev request quotes the current task and the message and asks a choice (`continue`, `side`, `switch`, `unclear`) and yes/no questions on whether it asks for concrete work, states a requirement or an acceptance criterion, stops or changes an action in progress, or corrects earlier work. A yes answer (probability at least `yes`) on a requirement, an acceptance criterion, or a correction, or on stopping an action while the choice is `continue`, appends the message, verbatim, keeping the latest `maxItems`; `switch` with concrete work and no correction starts a new frame from the message; anything else changes nothing. Every judgement writes `system3/judgement` with the exact request and response, and failures, the `deadlineMs` timeout, and privacy refusal change nothing. In `active` mode each change writes `system3/task-frame` and the frame reaches the model through the `system3:task-frame` runtime context once it holds a requirement; in `shadow` mode the frame stays in memory and only judgements are recorded; `off` asks nothing. With `interjection`, a plain-text message the person queues behind a running turn is judged when it arrives, and its claim at a later step reuses that judgement: in `active` mode a requirement, acceptance criterion, or correction of the current task moves into the running turn through the Session controller's queue `steer` action, the same action as the person's own steer button, and when a delegated run of that Agent is running and accepts input, its text also goes to that run through `subagents.steerByParent`, the path of the dock's steer form; side questions, new tasks, and remarks stay queued; `shadow` records the decision only. Each such message writes `system3/interjection` with the decision, whether it moved, and `forwardedTo`, the provider of a delegated run that also accepted it; a turn that has ended, or an item the person already edited or removed, leaves the message where it is. Moving needs an `active` task frame. Delegated child Agents, attachments, and longer messages are skipped. The runtime projection exposes the frame as `taskFrame`, which the Client shows in the dock as a count line that opens to the task and each requirement, and the latest moved message of the running turn as `interjection`, which the dock reports in one line until that turn ends. The questions were set on labelled sets run against the deployed Jev ([report](../../../docs/feat-jev-decision-kernel/task-frame-report.json)).

`skillSelection` classifies surviving ordinary text input and optionally selects one model-invocable Skill at the native `agent/pre-step` seam. Configure `sessionDataClasses`, `minConfidence`, `maxInputBytes`, `maxContentBytes`, `maxCandidates` (1–254), and `deadlineMs`. Jev receives the complete current text and a fixed intent choice: `conversation`, `retrieval`, `research`, `creation`, `action`, or `uncertain`. These labels describe the request; they never assert execution or authorize tools. A complete catalog adds Skill names and descriptions to the same request as consecutive groups of at most `maxCandidates` Skills, one choice question per group (`skill`, `skill2`, …, at most 15 groups beside the intent question), each with its own abstain option. Among the groups' choices at or above `minConfidence`, the most confident one is selected, the earlier group on ties; a choice below the threshold in any group with no accepted choice records `low-confidence`, and all groups abstaining records `abstain`. A catalog larger than 15 groups is first narrowed to that many Skills: those whose name and description share the most words or Chinese character pairs with the input, then the rest in catalog order. The receipt's `candidateNames` lists exactly the Skills Jev saw. Incomplete or empty catalogs still allow intent classification without claiming automatic Skill selection. Only supported intent values above the confidence threshold enter the receipt and Client view. Missing providers or credentials, privacy refusal, timeout or request-budget overflow leave native generation intact. Explicit `/name` invocations and non-text input retain their native paths. The Desktop profile installs this selector with a 3,000 ms total preparation deadline and at most 15 Skills plus abstention, uses the configured provider's effort and credentials, and leaves model routing, supervision and memory off. Configuring Reflex enables transmission of user text and eligible Skill descriptions to that endpoint; the three-second deadline is a fallback budget; one second remains a responsiveness target, not a guarantee. `skillSelection` status records installation, while `system3/skill-decision.intent` records classification and the exact instruction message records Skill adoption. `elapsedMs` includes catalog lookup, remote decision and optional Skill loading. The runtime view retains the finished-turn result and clears it when a new turn starts.

A `system3/skill-decision` records the exact request, validated response and reported usage, selection, and proposed native `injectionMessageId`. The loaded body uses `skill-invocation` instructions and becomes model-visible only when the loop commits that exact `user/message`; it grants no tool permission. The `system3Runtime` wire projection exposes `entry.suggested`, `entry.adopted`, and `entry.used` independently, `entry.executionDomain` from the recorded entry decision (null while deciding), keeps up to 100 earlier decisions whose input reached a turn in `history`, and `skill.selected` separately from `skill.injected`. Actual use requires model output or a streamed attempt carrying content deltas or completed content blocks in the exact input's turn. Usage, block placeholders, and finish-only errors or aborts do not confirm a response; content received before a later error still does. Admission alone never claims dispatch. Replay rebuilds these facts without Jev calls and exposes neither provider inputs nor complete probabilities to clients.

### Completion review

`completionReview: { mode, yes, no, deadlineMs, sessionDataClasses, maxRefusals, evidenceCalls, resultChars }` defaults to `false` and requires `taskFrame`; enabling it without one fails at load. An `active` or `shadow` review requires `taskFrame.mode` to be `active` or `shadow`; an `off` review may use an `off` task frame. Every field is required. When a top-level Agent calls `update_goal` with action `complete` for the DSH goal its task frame follows, one Jev request (decision `completion.review`) asks a yes/no question for the goal and one for each requirement in the frame (`goal`, `r1`…`rN`) before the tool runs. Jev reads only a digest of the latest `evidenceCalls` tool calls, each with its main argument (a command, path, action, query, or URL) and the first and last `resultChars` characters of its result; the model's own text and its `update_goal` calls are left out. A probability at or below `no` is a confident "not met" and one at or above `yes` is "met". In `active` mode a confident "not met" on the goal or any requirement denies the call, and the model receives the refusal as the tool result; after `maxRefusals` refusals of one goal in one Session later completions of that goal run without refusal. Independent root forks have separate allowances. If the task frame changes while a successful Jev response is pending, the old answer becomes `unsure`; active mode uses the same allowance to refuse that obsolete application and quotes the current frame for a new review. `shadow` records reviews without refusing, and `off` asks nothing. Unloading the plugin cancels pending reviews and delegates their calls to the remaining tool policies without a refusal or new review record. Caller cancellation still prevents execution. Decision calls already cancelled at entry dispatch nothing, and provider responses received after cancellation produce no judgement. Every review writes `system3/judgement` with the exact request and response, then `system3/completion-review` with `goalId`, `decision` (`complete`, `incomplete`, or `unsure`), the message ids of `unmet` requirements, `goalUnmet`, and `refused`. Privacy refusal, a Jev failure, and the `deadlineMs` timeout let the completion run as `unsure`. Delegated child Agents, nested calls, other goal actions, and goals the task frame does not follow are not reviewed. The questions and thresholds were set on labelled sets run against the deployed Jev ([test](tests/completion-review.e2e.ts)).

### Reflex prefetch

`prefetch: { mode, yes, no, deadlineMs, sessionDataClasses, maxItemBytes, maxTotalBytes, maxSourceFiles, maxSearchTerms, commandTimeoutMs }` defaults to `false`; every field is required. At the `agent/pre-step` that carries a top-level Agent's plain-text person input, one discovery command in the session's workspace lists the read-only facts the input could need: pending changes (`git status` plus staged and unstaged diffs), the tracked file list, the README, the project manifest, files the input names by relative path, lines containing up to `maxSearchTerms` words of the input, and, for a repository of at most `maxSourceFiles` tracked files, every tracked text file. Every candidate command starts at once through the `shell` service with a `read-only` sandbox policy and a `commandTimeoutMs` deadline, while one Jev request (decision `prefetch`) asks a yes/no question per candidate and the later pre-step listeners, such as Skill selection, run. Git runs without hooks or fsmonitor and diffs without external drivers or text conversion. In `active` mode the outputs of the candidates at or above `yes`, each cut to `maxItemBytes` and together within `maxTotalBytes`, enter the same step as one `system3-prefetch` message after the input; candidates past the total are named instead. `shadow` records only `system3/judgement`, and `off` asks nothing. Privacy refusal, a Jev failure, the `deadlineMs` timeout, a missing shell service or session workspace, and failed commands leave the step unchanged. Delegated child Agents, `/name` invocations, and non-text input are not prefetched. A live benchmark (`tests/fixtures/prefetch-bench`) runs the same workspace tasks natively and with prefetch.

### Reflex Goal supervision and context memory

Capability status reports enabled only while the required runtime services and registrations are present; dependency removal disables the reported capability.

`reflexSupervision` opts active, armed Goals into bounded Codex observation. Execution categories and fingerprints feed the Reflex decision service; autonomous advice uses a separately attributed steer path. Delivery acknowledgement and observed improvement are separate durable facts. Terminal feedback remains tied to the ended run: human input arriving or being claimed, task-frame changes, and Goal or activation changes invalidate an outstanding assessment. Invalidated feedback is inconclusive; disposal awaits cancellation without publishing late feedback. Delayed receipts retain the dispatched Goal revision. Goal, human-input, task-frame or recovery changes prevent a late acknowledgement from reopening feedback; native evidence arriving during acknowledgement remains eligible for feedback. Goal revisions, stopped runs and newer evidence invalidate pending judgements. Each evidence snapshot is judged once, including observe, uncertainty and provider failure; elapsed time alone does not repeat the request. After an adjustment, inconclusive and unchanged feedback remains attached to that adjustment and is reviewed again only when newer evidence arrives; it clears only on improved, invalidated or disposed state. New evidence or a Goal revision permits another assessment, and evidence arriving during a request remains eligible. Cooldown and intervention limits apply across runs of the same Goal; raw commands and outputs are not sent to the supervisor. Without semantic collection, this evidence supports repetition and progress checks, not semantic Goal alignment. Optional `semantic: { minObservations }` requires at least two complete native action/path observations in the latest contiguous complete suffix before Reflex judges whether that suffix persistently works on unrelated targets; related investigation, mixed evidence and uncertainty do not authorize realignment. A sufficient semantic suffix permits evaluation at the configured interval without waiting for the inactivity deadline; confidence, cooldown and Goal budgets still apply. The complete bounded audit history remains logged; each new unknown, truncated or pathless observation breaks the semantic suffix, rather than selecting evidence across gaps. Enable Codex `evidenceSummary` collection too. Only structured workspace-relative targets and action kinds enter this path, never raw commands, output, queries, diffs or private reasoning. Summaries require workspace data admission even when other configured classes are public. Missing, truncated or pathless summaries retain fingerprint supervision without claiming semantic coverage. In semantic mode, a successful verification establishes improvement only with complete target evidence and an affirmative Goal-relevance judgement; unrelated or unidentified passing tests do not reset semantic progress.

`reflexContext` waits for task-frame judgements of this step’s admitted messages before capturing removal constraints; later queued messages do not extend this wait, and cancellation stops it. It only edits unsubmitted, unfrozen tail text by original block and line range; submitted history and generated assistant text are frozen. Frozen memory is recovered by appending text, never by rewriting an old omission marker. Current input, retained requirements, structured blocks and tool pairing remain protected. Confident selections affect later requests through durable reversible projections; errors or uncertain answers preserve the text. `reflex_memory` searches omitted same-session text and restores original content, including after restart or summary compaction. Compacted originals return as logged `reflex-memory` messages whose source is attribution only; their body includes the original reference and historical text. Visible recovered text is not injected again on the next step. The original log remains intact. This controls Harness requests, not Codex's private internal history. Decision and restoration budgets are deployment configuration. Context review v3 separates ordered current user requests, the active Goal and the prior task frame. The latest request determines current relevance without discarding earlier unrevoked constraints. A previous task’s exclusion of a topic is not a permanent prohibition on recovering its facts; safety, permission, precision and original-file protection constraints remain in effect.

`reflexContext.compactionSweep` runs on `compaction/prepare`, where the provider prompt cache is rebuilt anyway, and may therefore hide frozen history. While Reflex is switched on, it splits every unprotected tool-output block outside the recent messages into passages of whole lines and hides certain noise (package-manager and download progress, page frames and advertising, inline images, and older exact copies of repeated output) and every passage for which three independent questions about the latest user request all answer at or below `no`. Passages naming errors, failures, requirements, or allergies are never asked or hidden. Shadow mode records the judgements without hiding anything, and a failed sweep leaves the surface unchanged. Hidden passages remain recoverable through `reflex_memory`.

The Client exposes Reflex delivery, feedback and context changes from committed events. Settings contains a dedicated Reflex configuration page; its connection check is independent of runtime capability results.

## Understand the implementation

The service owns no second agent loop. Its explicit `shadowDecision(session, request, signal)` consumer calls the optional `ctx.jev` provider only after admission by the captured privacy policy. Each policy method increments a non-sensitive counter and delegates to one pure package. When `observeAgentLoop` is enabled, it adds non-mutating listeners for `agent/pre-step`, `agent/request`, `agent/request-error`, and `agent/turn-stopping`; the resulting boundary counters are included in `snapshot()`. The privacy policy is captured at activation; a Jev preference remains advice and cannot override it.

<a id="model-experience"></a>

When delegation candidates are configured, System3 also routes native Goal rounds before the generation model can act. It checks the active, armed Goal revision, candidate data permissions, provider availability and tool visibility. Every objective requires a confident Reflex semantic selection; an actual affirmative user choice takes precedence over a candidate’s default workload guidance; delegate names, negations and quoted examples never authorize execution by keyword. Unavailable or uncertain choices abstain. The child runs through the existing subagent service with the original objective and confirmed task-frame requirements. `system3/goal-entry` records reservation, exact delegated input, actual start, terminal status and JSON-encoded result content; a `system3-goal-delegation` message carries the result without pretending to be human input. Each revision permits one attempt. New human input or Goal changes cancel stale work; queued human messages remain intact. Failed execution or an ownerless restored reservation blocks the Goal for inspection and explicit resumption. Resumption warns the child to inspect existing effects before repeating operations. A completed result not yet admitted to the model is restored from its receipt without rerunning the child. This path selects delegation only and does not switch the generation model mid-step. Plugin disposal cancels outstanding admissions and awaits child cleanup. Live 9B testing found that low effort can still abstain on short Chinese or English affirmative requests because confidence remains below the configured threshold; no keyword override or threshold reduction bypasses that uncertainty. The provider default remains high effort.

Optional `reflexSupervision.recovery` adds `reassessmentMs`, `nativeSilenceMs`, `retryLimit`, `interruptGraceMs`, `cooldownMs` and `maxRecoveries`. A binary Reflex judgment compares measured inactivity and retries with their configured budgets and checks the proposed read-only reconciliation against Goal constraints. Every assessment, including failed or uncertain responses, reserves the `reassessmentMs` interval before dispatch. Reflex judges only after a native activity or retry budget is reached; ordinary Goal duration never triggers recovery. Healthy streams, approval waits and in-flight tools are protected. Goal revision, current constraints and newer human input fence both interruption and continuation. `system3/reflex-recovery` reserves a Goal-wide budget before dispatch and records the outcome; restored intents are never resent. Same-thread continuation requires native interrupted confirmation, while unknown outcomes stop the process without automatic replacement.

The `reflex_memory` tool describes retrieval as task-dependent: an omission marker alone does not justify searching. The model is instructed to respect excluded topics and seek a specific missing fact, using an empty query only when that fact has no known searchable keywords. A later user request can make archived facts relevant again; search and restore remain available. These are model instructions, not a deterministic topic filter.

## Model Experience

### Unified System3 seam

#### What the model sees

Without entry routing, a host chooses which service results enter model history. Entry routing sends the current text in `state.input`, baseline selection in `state.baseline`, and bounded choice descriptions in `questions.route.criteria` to Jev. Its receipt is not added to generation history. An adopted model change follows the native Session API model-selection behavior. With `handoffPack`, the delegation instruction may end with the person's earlier requirements, and in `advise` mode, process supervision adds one user message with source `system3-supervision` per fired rule, in `active` mode output folding replaces repeated lines of a shell result with markers, the task frame adds a runtime-context snapshot, and in `active` mode a refused goal completion returns the completion refusal as the `update_goal` result, for example:

#### Token effect

Entry routing adds a Jev call for each eligible admitted prompt when privacy and size checks permit it; provider usage is retained when reported. The evidence method bounds caller projections, and usage records distinguish provider counts from estimates. Each supervision advice adds 50 to 100 input tokens, and a hand-off pack adds its forwarded messages plus about 60 tokens and one Jev request; `missing-evidence` in `advise` mode adds at most one model step per turn. Output folding calls no model and removes the folded characters from the tool result. The task frame discards answers for replaced frames; a queued message stays for the next turn, and one already claimed gets at most one replacement judgement. It adds one Jev request per later message, in parallel with the step unless Reflex context review waits for the admitted batch, and a runtime-context snapshot of the goal and the kept requirements each time they change. The completion review adds one Jev request per reviewed completion, which the `update_goal` call waits for up to `deadlineMs`, and a refusal adds about 80 tokens plus the quoted goal and requirements. Prefetch adds one Jev request per person input, which the step waits for up to `deadlineMs`, and at most `maxTotalBytes` of prefetched output plus about 60 tokens; it removes the model steps that would gather those facts through tool calls.

#### KV Cache effect

Observation and shadow receipts do not change the generation prefix. Automatic Skill injection appends bounded native instruction content before generation. Supervision advice is appended after the latest tool result, so the cached prefix is unchanged. A folded tool result is folded before it enters history, so later requests reuse it unchanged. A task-frame change appends a new runtime-context snapshot after the latest message and leaves the cached prefix unchanged. A completion refusal is a tool result appended after the latest message, so the cached prefix is unchanged. Prefetched facts are one message appended after the input, so the cached prefix is unchanged. An adopted generation-model switch may lose provider cache reuse; tool schemas are unchanged.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

- Entry routing covers the Session API's eligible idle text prompts, not headless, SDK, ACP, attachments, queued batches, or active steering. It does not dispatch experts or control task completion.
- The service does not enforce OS privacy isolation. Workspaces, environment variables, subprocess egress, and export consent remain host responsibilities.
- Entry decisions lack conversation history and must abstain when the new text needs it. Declared data classes and candidate descriptions are deployment facts; this package cannot verify their accuracy or prove routing quality and cost savings.
- The completion review relies on a 9B Jev model reading a bounded digest: it can refuse finished work or pass unfinished work, it sees only what the digest keeps, and it fails open. Once `maxRefusals` refusals of a goal are used, later completions of that goal run even when judged not met.
